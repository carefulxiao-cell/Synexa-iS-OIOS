## 1. 项目定位与目标

### 1.1 一句话定义
Nex₂U 不是一个点餐工具，而是一个**“结构驱动的餐食生成引擎”**。它将非结构化的健康餐饮、营养逻辑与供应链经验，转化为可计算、可执行、可复用的结构化规则系统。

### 1.2 核心目标（三层）
*   **业务目标**：解决健康餐饮中“营养要求高、原料变动大、供应链难匹配”导致的履约不稳定问题，实现降本增效。
*   **系统目标**：建立一个可将健康餐逻辑、营养结构、原料映射、供应链约束与出品规则进行统一组织的项目级规则系统。
*   **本阶段目标**：跑通从“用户需求”到“供应链匹配”的核心业务链条，完成首个 MVP（医院营养餐厅场景）的开发与落地。

---

## 2. 系统架构与边界（三层架构）

Nex₂U 整体遵循三层架构，明确各端边界：

### 2.1 Layer 1｜系统中枢层（System Nexus Layer）
*   **核心模块**：**Nex₂U**
*   **职责**：统一决策逻辑生成、系统协同、数据流动与规则演进。
*   **包含**：P1 高质效全维科学菜单引擎、用户画像与场景状态识别、口味聚合与爆品系统、标签系统与推荐逻辑、规则迭代机制。

### 2.2 Layer 2｜执行层（Execution Layer）
*   **当前承载模块**：**NuBō（优食运维 - B端供给管理）**
*   **职责**：将系统中枢生成的逻辑，转化为真实供给与生产行为。
*   **包含**：团餐公司协同、厨房执行体系、菜单标准生产、运营协同流程。

### 2.3 Layer 3｜交互与呈现层（Interaction Layer）
*   **核心模块**：**Nufō³（食全食美 - C端饮食体验）**
*   **职责**：C 端用户的个性化饮食决策与体验平台。
*   **包含**：点餐界面、推荐展示、轻量状态输入、个人饮食洞察面板（轻量反馈，不提供医疗判断）。

### 2.4 第三支柱｜NuStā（健康稳态知识体系）
*   **定位**：Nex₂U 的知识引擎与信任锚。
*   **职责**：提供营养逻辑、食物结构原则、标签命名依据，以及信任解释（为什么推荐）。

## 3. 核心业务逻辑与结构化要素

### 3.1 营养结构点体系（P·C·V·E·PR 编码体系）
所有食材、工艺、营养点必须进行模块化建构与标准化命名，确保轻松可换、结构稳定。
*   **P (Protein)**：蛋白质结构
*   **C (Carbohydrate)**：碳水化合物结构
*   **V (Vitamin/Vegetable)**：维生素与膳食纤维结构
*   **E (Energy/Fat)**：能量与脂肪结构
*   **PR (Process/Rule)**：加工工艺与约束规则

### 3.2 28个主题场景（分类与优先级）
场景映射是系统生成菜单的关键输入。
*   **高优场景（MVP 验证场景）**：医院营养餐厅（普通工作日、值班、恢复期、陪护期、特殊膳食要求）。
*   **扩展场景**：企业团餐、航食、外部送餐、特殊活动等。
*(注：28个具体场景的完整清单待用户进一步输入后补充至此)*

### 3.3 九维约束引擎
P1 菜单引擎的生成逻辑基于以下九维约束：
1. 用户接受度 2. 口味聚合 3. 爆品潜力 4. 场景适配 5. 运营协同 6. 实施落地 7. 成本效率 8. 健康友好 9. 反馈迭代。

## 4. MVP 定义与开发规划（第一阶段最小闭环）

### 4.1 MVP 场景与目标
*   **首发场景**：医院营养餐厅。
*   **目标**：跑通一个可复制、可扩张、可复盘的高质效最小闭环。

### 4.2 MVP 系统最小实现集合
1.  **菜单引擎（基础版）**：基于硬性/软性约束生成菜单。
2.  **标签系统（基础版）**：菜品与场景标签映射。
3.  **用户点餐系统（简版 Nufō³）**：前端展示与点选。
4.  **运营管理后台（简版 NuBō）**：菜单管理与订单处理。
5.  **数据采集与基础报表**：行为与结果数据记录。

### 4.3 第一阶段明确不做
*   不做复杂 AI 预测与复杂健康模型。
*   不做机器人与自动化设备接入。
*   不做过度个性化与重医疗逻辑。

## 5. 跨平台协同工作机制

为了高效推进开发，建立基于 GPT、Manus、Code 平台的协同机制：

### 5.1 角色分工
*   **GPT（数字系统架构师 D3）**：负责业务逻辑推演、营养结构设计、场景规则制定、文档结构设计。主导“想”和“设计”。
*   **Manus（执行型/协同型数字员工 D1/D2）**：负责执行层动作，包括代码开发、文件生成、GitHub 推送、系统架构图绘制、流程图输出。主导“做”和“落地”。
*   **GitHub（SSOT）**：所有输出文档、架构图、代码统一回写至 GitHub，两侧共享，保持全局状态一致。

### 5.2 结构化工作流（文字描述 -> 流程图 -> 编码打包）
1.  **需求输入**：用户在 GPT 侧输入业务逻辑（如具体的营养点、场景）。
2.  **结构化翻译**：GPT 将其翻译为标准结构化文档，更新 Master Doc。
3.  **同步与制图**：Manus 读取更新后的 Master Doc，同步生成/更新全局架构图（Mermaid/D2）。
4.  **任务拆解**：Manus 基于 MVP 规划，拆解前后端开发任务清单。
5.  **编码落地**：进入实际开发阶段，Manus 辅助代码生成与部署。
