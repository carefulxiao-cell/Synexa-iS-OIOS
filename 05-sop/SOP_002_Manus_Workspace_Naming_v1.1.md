# SOP_002_Manus_Workspace_Naming_v1.1

> **版本**：v1.1
> **生效日期**：2026-04-16
> **维护主体**：iS-Core（智核中枢）
> **定位**：定义超智体系在 Manus 平台上的工作空间（Workspace）与对话框（Session）的命名规范与管理机制。

---

## 1. 机制概述

为了确保 Synexa iS 体系在 Manus 平台上的多项目、多角色协同能够有序进行，必须建立一套标准化的工作空间与对话框命名规范。这套规范旨在：
1. **清晰识别所属主题组**：通过主题前缀，在「所有任务」列表中一眼识别该对话框属于哪个大的主题板块。
2. **精准定位组内分工**：通过功能角色前缀，明确该对话框在特定项目/系统内部的具体职责（如总控、执行、审查）。
3. **保持全局状态一致性**：确保 Manus 平台上的对话框结构与 GitHub 中央仓的目录结构、GPT 侧的 Project 结构保持高度映射。

---

## 2. 命名规范 (Naming Convention)

Manus 对话框的命名应遵循以下两层逻辑结构：

### 2.1 第一层：主题对话组 (Theme Group)

用于标识该对话框属于哪个大的主题板块（如 Core, SCO, PCS）。
命名公式：**`[主题前缀] - [具体内容描述]`**

- **示例**：`Core - 动态功能基线·FBR`
- **含义**：在 `Core` 这个大的主题对话组中，关于「动态功能基线·FBR」的对话框。

### 2.2 第二层：项目/系统内部的分工对话框 (Project/System Sub-Session)

因为同一个主题里面有多个不同的项目和系统，而每个项目/系统也有自己的主题对话组。在这个组里，需要区分不同的工作分工。
命名公式：**`[功能角色前缀] - [项目/系统代号]`**

- **功能角色前缀**：
  - `中枢`：负责该项目/系统的总控管理。
  - `执行框`：负责该项目/系统的具体开发与执行。
  - `审查框`：负责该项目/系统的审查与核验（如 FBR 全面审查）。
  - `SCO`：负责该项目/系统的策略推演。

- **示例**：
  - `中枢 - 超级项管·NexFlow`：在 NexFlow 项目的主题组里，负责总控管理的对话框。
  - `执行框 - 超级项管·NexFlow`：在 NexFlow 项目的主题组里，负责具体执行的对话框。
  - `审查框 - 超级项管·iS-NexFlow`：在 NexFlow 项目的主题组里，负责审查的对话框。

## 4. 管理机制与融合方案

### 4.1 目录映射与对齐

Manus 平台上的项目文件夹（Folder）应与 GitHub 中央仓的 `03-projects/` 目录结构保持一致。例如：
- Manus 文件夹：`【超级项管·iS-NexFlow】 - PCS`
- GitHub 目录：`03-projects/NexFlow/`

### 4.2 列表视图优化

通过上述两层命名逻辑，当用户在 Manus 的「所有任务」列表中查看时，可以通过前缀（如 `Core-`、`中枢-`、`执行框-`）一眼识别出该对话框所属的主题板块以及具体的职责分工，极大提升了多项目并行时的管理效率。

### 4.3 跨平台状态同步

- **GPT 侧**：GPT 侧的 Project 命名与结构应与 Manus 侧保持一致。
- **GitHub 侧**：所有对话框的核心产出（如 TBF, FBL, SOP）必须统一归档至 GitHub 中央仓，确保 SSOT（Single Source of Truth）。
