# 系统开发原则 (IS_DEV_PRINCIPLES)

**版本**: v1.0
**适用范围**: Synexa iS 体系下所有项目通用
**定位**: 约束开发行为的底层规范，确保系统架构的稳定性、代码的可维护性以及团队协作的高效性。防范“拼凑式”开发带来的系统性风险。

---

## 1. 架构与设计原则

### 1.1 先设计后实现
严禁在没有明确数据结构和核心业务流程设计的情况下直接编写代码。所有核心模块的开发必须基于已评审通过的架构草案或 API 设计。

### 1.2 高内聚低耦合
模块划分必须职责单一。一个模块只负责一类业务逻辑，避免跨模块的深度依赖。修改一个模块的内部实现，不应影响其他模块的正常运行。

### 1.3 容错与防御性编程
系统必须假设外部依赖（如第三方 API、数据库、网络）随时可能失败。所有外部调用必须有超时设置、重试机制或降级方案，严禁因单点故障导致全局崩溃。

## 2. 数据与状态原则

### 2.1 单一事实来源 (SSOT)
对于任何核心业务数据，必须明确其唯一的权威来源（通常是数据库）。严禁在本地状态（如前端内存、LocalStorage）和数据库中维护两套独立且可能冲突的数据逻辑。

### 2.2 状态同步与持久化边界
明确区分“临时状态”与“持久化数据”。临时状态可保留在前端，但任何涉及业务流转、资金或核心记录的操作，必须同步落库。本地状态必须具备从数据库随时重建的能力。

### 2.3 数据约束前置
数据的完整性与一致性约束（如非空、唯一性、外键关联）必须在数据库层面建立，不能仅依赖前端或服务层的代码校验。

## 3. 接口与安全原则

### 3.1 默认封闭与严格鉴权
所有接口默认对外封闭，必须经过明确的授权配置才能访问。严禁存在无鉴权即可操作敏感数据的“后门”接口。

### 3.2 零信任输入
系统必须对所有来自外部的输入（包括用户提交、第三方回调）保持“零信任”态度。所有入参必须进行严格的类型、格式和边界校验，并进行必要的安全转义。

### 3.3 敏感信息隔离
严禁在代码中硬编码任何敏感信息（如密码、密钥、Token、内部 IP）。所有敏感配置必须通过环境变量或安全的配置中心注入。

## 4. 代码与工程原则

### 4.1 消除魔法值
代码中严禁出现未解释的“魔法数字”或“魔法字符串”。所有具有特定业务含义的常量必须集中定义，并附带清晰的注释说明。

### 4.2 异常捕获与日志记录
所有可能抛出异常的代码块必须被妥善捕获，严禁将底层错误堆栈直接暴露给终端用户。关键业务节点和异常分支必须记录结构化日志，以便于问题追溯。

### 4.3 持续重构与消除技术债
在日常迭代中，发现重复代码或不合理结构时，应在保证业务正常的前提下进行小步重构。严禁将“临时方案”长期遗留在代码库中而不做标记（如 TODO/FIXME）。
