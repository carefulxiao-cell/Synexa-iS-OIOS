# SOP_003：执行框强制提交规范 (Execution Submission Standard)

> **版本**：v1.0
> **生效日期**：2026-04-17
> **维护主体**：iS-Core (智核中枢)
> **适用范围**：Synexa iS 体系内所有负责代码编写与交付的执行框（如 NexFlow-V2 执行框）

---

## 1. 机制概述

为了解决执行框“表面通过、实际失败”、“选择性执行指令”以及“架构规范漂移”的问题，特制定本强制提交规范。

**核心原则**：
1. **无报告不接收**：执行框在宣告任务完成时，必须严格按照本 SOP 提供的模板输出提交报告。格式不符或内容缺失的提交，PCS 策略室有权直接拒绝接收，并打回重做。
2. **生产环境感知**：提交报告必须包含对生产数据库实际状态的核查，不能仅依赖代码层面的测试通过。
3. **架构规范自证**：执行框必须在报告中明确声明未违反核心架构规范（如禁止原生 SQL、唯一迁移路径等）。

---

## 2. 强制提交报告模板

执行框在每次完成指令包开发并准备交付时，必须在对话框中输出以下结构的报告：

```markdown
## 提交报告 (Execution Submission Report)

**基础信息**
- **Commit Hash**: [填写最新的 Git Commit Hash]
- **执行的指令包**: [填写对应的指令包文件名，如 `nexflow_v3_1_health_dashboard.md`]

**完成情况**
- **完成项**: 
  - [列出已完成的功能点]
- **未完成项**: 
  - [列出未完成的功能点，并必须说明原因]

**架构规范自查 (强制门禁)**
- [ ] **无原生 SQL**：确认代码中未使用 `mysql2/promise` 或 `conn.execute` 等原生 SQL 方式操作数据库。
- [ ] **唯一迁移路径**：确认所有数据库结构变更均通过 Drizzle ORM 的标准迁移流程（`drizzle-kit generate` + `drizzle-kit migrate`）完成，不存在任何独立的 `.mjs` 或 `.sql` 建表脚本。
- [ ] **Schema 一致性**：确认 `schema.ts` 的定义与生产数据库的实际表结构完全一致。
  - **证明材料**：[必须附上在生产数据库执行 `SHOW COLUMNS FROM [相关表名]` 的截图或文本输出，以证明实际字段与代码定义一致]

**生产环境验证 (端到端)**
- **验证说明**：[简述在生产环境进行了哪些实际操作]
- **验证证明**：[必须附上生产环境操作成功的截图，或明确的日志输出]
```

---

## 3. 数据库迁移唯一路径原则 (强制基线)

本 SOP 明确确立以下数据库操作基线，所有执行框必须严格遵守：

1. **禁止独立脚本**：严禁编写和执行任何脱离 ORM 框架的独立建表或修改脚本（如 `migrate_hr_arch_v2.mjs`）。
2. **标准流程**：所有数据库结构的变更（建表、加字段、改类型等），**唯一合法路径**是修改 `schema.ts`，然后使用 `drizzle-kit generate` 生成迁移文件，最后通过 `drizzle-kit migrate` 应用到数据库。
3. **违规处理**：若 PCS 策略室或审查框在代码库中发现违反此原则的独立脚本，或发现直接使用原生 SQL 绕过 ORM 的行为，有权要求执行框**立即回滚**相关提交，并按标准流程重写。

---

## 4. 与 TBF 三态核查的联动

本提交报告是触发 TBF（任务目标基线文件）核查的前置条件。
- 执行框提交符合本 SOP 的报告后，TBF 状态进入 **⚠️ 待验证**。
- 审查框或 PCS 策略室根据报告中的“证明材料”和“生产环境验证”进行复核。
- 复核无误后，TBF 状态方可更新为 **✅ 通过**，并解锁下一阶段的指令包。
- 若报告缺失关键证明（如无 `SHOW COLUMNS` 截图），TBF 状态直接判定为 **❌ 未通过**，打回执行框。
