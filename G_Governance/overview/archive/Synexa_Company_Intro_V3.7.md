# CH 01｜公司定位

超智科技（Synexa）是一家协同智能公司（Collaborative Intelligence Company）。

超智致力于构建复杂场景中的智能集群方案，让人、组织、智能体、设备与供应网络协同持续优化，共同创造更高价值。通过场景认知、供应网络整合、智能体集群与持续运营能力的融合，为客户构建可交付、可复制、可持续进化的整体协同解决方案。

超智不在数字世界里抽象模拟场景，而是进入真实业务现场，将专业知识、供应链资源、运营服务、软硬件能力与数字系统整合为一体，形成可真实交付、可持续迭代的复杂场景解决方案。

## Human-Machine Double Anchor｜人智双锚原则

Synexa iS 中，人智不是系统的补丁，而是系统的方向锚与裁决锚。

人智在协同流程中有两个不可替代的位置：

| 人智锚点 | 所在位置 | 核心职责 | 不可替代原因 |
|----------|----------|----------|--------------|
| Human-at-the-Beginning｜前置定向 | L0 人智定向层 | 战略方向、边界设定、成功标准、价值判断、责任承担。 | 方向、价值与责任不能由系统自行生成。 |
| Human-at-the-Decision｜后置裁决 | L4 人智决策层 | 方案审核、风险判断、关键决策、拒绝或退回修正。 | 高风险选择、模糊判断与结果承担必须保留人类控制权。 |

# CH 04.1｜Synexa Project Portfolio & Positioning <span class="subtitle">项目组合定位与联动关系</span>

本章节用于在 L0 Master SSOT 中建立 Synexa 生态下各项目、业务模块、能力模块与文档体系的项目组合级定位共识。

L0 不展开具体项目执行细节，不替代 L3 Project Baseline。L0 只定义项目身份、生态位置、联动关系、成熟度状态、主基线归属与下位基线入口。所有 L3 项目基线必须以本章节为上位锚点展开，不得自行改变项目定位、项目层级、业务属性或与其他项目的关系。

## 04.1.1 项目组合定位原则

Synexa 项目组合定位遵循以下原则：

1.  **先定位，再展开**  
    所有项目必须先在 L0 中完成项目身份与生态位置确认，再进入 L3 项目基线展开结构、视觉、模板、系统界面、执行路径和交付物。

2.  **L0 管共识，L3 管应用**  
    L0 负责项目组合级共识，回答“它是什么、归属哪里、与谁联动、处于什么阶段”；L3 负责具体应用，回答“怎么做、怎么设计、怎么交付、怎么运行、怎么复盘”。

3.  **项目不是孤岛**  
    每个项目都必须说明与 Synexa iS、Nex·EC、Nex·PVC、供应网络、场景网络、品牌系统、数据系统和经验资产库之间的关系。

4.  **项目定位不得漂移**  
    项目名称可以优化，表达可以转译，视觉可以适配，但项目在 Synexa 生态中的基本身份、能力归属和战略位置不得未经审计自行改变。

5.  **成熟度必须显性**  
    所有项目必须标注成熟度状态。推荐使用：concept｜概念期；prototype｜原型期；pilot｜试运行；active｜运行中；validated｜已验证；scalable｜可复制扩展；archived｜归档。

| 上位关系 | 该项目继承哪个主基线、系统基线或全域标准。                         |
| 平行关系 | 该项目与哪些项目同属一个能力层、业务线或场景网络。                 |

## 04.1.5 项目组合不是项目列表

Synexa L0 中的项目组合，不是普通项目管理清单，而是全域协同架构的对象索引。

## 11.1 Synexa Human-Machine Decision Loop｜人机协同决策主流程

Synexa iS 的主流程不是“系统自动化替代人”，而是“人设定方向，系统完成感知、推演和执行，人保留关键决策与修正权，系统再通过反馈进化”。

| 阶段 | 输入 | 系统动作 | 人智动作 | 输出 |
|------|------|----------|----------|------|
| L0 定向 | 战略意图、边界、成功标准 | 形成任务上下文与约束条件。 | 明确方向、价值判断与责任边界。 | 方向指令。 |
| L1 感知 | 用户行为、场景数据、运营信号、供应信号 | 接收真实世界输入。 | 判断哪些信号值得纳入系统。 | 原始场景信号。 |
| L2 推演 | 清洗数据、结构化上下文 | 方案生成、风险识别、调度建议。 | 必要时参与原则校准。 | 方案草稿与调度指令。 |
| L3 执行 | 调度任务、供给需求、运营动作 | 引擎群与能力体执行，并回传状态。 | 处理异常升级和资源协调。 | 执行数据、异常、成本与状态。 |
| L4 决策 | 方案草稿、执行数据、风险提示 | 提供可审查方案。 | 通过、拒绝、退回修正或升级裁决。 | 决策指令或修正指令。 |
| L5 进化 | 执行结果、反馈、复盘 | 形成经验资产与下一轮优化建议。 | 判断是否需要战略校正。 | 经验资产、SOP、Skill、战略反馈。 |

## 11.3 Risk-Based Human-Machine Decision Rights｜基于风险等级的人机决策权限

| 风险等级 | 决策方式 | 人介入要求 | 记录要求 |
|----------|----------|------------|----------|

| Decide｜决策路径  | 决定自建、采购、集成、Codex 生成、Manus 落盘、Kimi 审校或暂缓。                          |
| Act｜执行交付     | 通过 Task Room、SIA、外部执行体任务包、质量门完成交付。                                  |
| PER｜经验沉淀     | Pattern / Exception / Rule 是每次项目完成后的经验沉淀入口，进入 iS-Cortex 与经验资产库。 |

V3.0 将现场设备、人、岗位、数据、异常纳入 Observe，将设备数据、现场异常、履约规则和健康反馈纳入 PER。

## 19.1 Double-Human-Gate OODA-PER｜双人智关口协同交付法

OODA-PER 在 Synexa iS 中应增加两个清晰的人智关口：

| 人智关口 | 对应阶段 | 核心动作 | 输出 |
|----------|----------|----------|------|
| 前置定向关口 | Observe / Orient 之前 | 明确战略方向、边界、成功标准、价值判断。 | 方向指令与任务边界。 |
| 后置裁决关口 | Decide / Act 之间 | 审核方案、处理模糊性、判断风险、决定通过或退回。 | 决策指令或修正指令。 |

## 19.2 Reject / Revise Path｜拒绝与修正路径

OODA-PER 不只允许从 Decide 进入 Act，也必须允许从 Decide 退回 Orient / Cortex 重新推演。拒绝理由、修正要求、风险判断和人类裁决依据，都应进入经验资产库。

# CH 26｜SSOT 升级治理机制

Synexa 认知基线文件属于高质量 Master SSOT，不是普通文案稿。每一次版本迭代，都必须同时进行 Forward Audit 与 Reverse Audit，确保新增内容被正确吸收，旧有核心内容没有因压缩、重排、改写或美化而悄悄丢失。

GOVERNANCE PRINCIPLE

<div>

## 26.1 三层文件机制

| 层级 | 文件类型                          | 用途                                   | 是否可删减                                         |
|------|-----------------------------------|----------------------------------------|----------------------------------------------------|
| L1   | Master SSOT 主基线                | 内部唯一真源。                         | 原则上不可删，只能增补、标记废弃或经红色变更确认。 |
| L2   | Versioned Working Copy 版本工作稿 | 每次升级编辑稿。                       | 可改，但必须留变更记录。                           |
| L3   | Audience Edition 分受众版本       | 客户版、官网版、投资人版、合作伙伴版。 | 可以删减，但必须标注“转译版，不是主基线”。         |

## 26.2 Forward Audit｜迭代审查

| 审查项   | 问题                                                 |
|----------|------------------------------------------------------|
| 新增内容 | 新版本新增了哪些章节、模块、概念、引擎、规则或附录？ |
| 调整内容 | 哪些章节被移动、合并、拆分或重命名？                 |
| 表达优化 | 哪些句子被改写？是否更清楚？是否改变原意？           |
| 能力增强 | 新版本是否增强了系统能力、场景能力或组织能力？       |
| 版本风险 | 新增内容是否引入理解负担、概念冲突或架构重叠？       |
| 适用范围 | 新版本适用于内部主基线、客户版、官网版还是投资人版？ |

## 26.3 Reverse Audit｜反向审查

| 审查项     | 问题                                   |
|------------|----------------------------------------|
| 章节映射   | 上一版本每个章节在新版本中对应哪里？   |
| 核心锚点   | 上一版本的核心概念是否全部保留？       |
| 高风险句   | 关键判断句、定位句、边界句是否仍在？   |
| 表格字段   | 原有表格字段是否完整迁移？             |
| 方法论     | 原有方法论是否仍完整？                 |
| 交叉引用   | 章节编号、附录编号、内部引用是否更新？ |
| 语义完整性 | 被压缩内容是否仍保留原有判断力？       |

## 26.4 红黄绿变更规则

| 等级 | 类型                                                                 | 处理方式                               |
|------|----------------------------------------------------------------------|----------------------------------------|
| 绿色 | 标点、错别字、行距、表格格式、视觉排版、明显重复语句。               | 可直接处理，但应进入轻量记录。         |
| 黄色 | 段落合并、表达改写、章节移动、表格重排、标题调整。                   | 必须进入变更记录，并说明是否影响语义。 |

## 26.5 版本治理底线

每一次升级前，必须先确认上一正式版本。每一次升级后，必须同时输出：新版本主文件、Forward Audit、Reverse Audit、删除 / 压缩 / 合并 / 改写记录、核心锚点保留表、版本迭代记录。没有完成以上审查的新文件，只能称为 Working Draft，不能称为 Master SSOT。

# CH 26.9｜Synexa Domain Baseline Alignment Protocol <span class="subtitle">超智全域基线对齐协议</span>

## 26.9.1 定义

超智全域基线对齐协议，是 Synexa 生态下所有基线文件、项目文件、报告模板、表格模板、官网页面、系统界面、品牌材料、客户方案、投资人材料、内部 SOP、机器可读文件与日常工作交互文件共同遵守的上位治理规则。

本协议的目标不是让所有文件长得完全一样，而是让所有文件在公司定位、项目归位、概念层级、命名规则、CI 识别、UI / UX 逻辑、字体系统、内容结构、信息排序、人机共读、版本治理与输出质检上，始终与 Master SSOT 保持一致。

所有 Synexa 生态文件可以因对象、场景、用途和媒介而形成不同表达形态，但不得形成独立于主基线之外的事实源、风格源、命名源或治理源。

------------------------------------------------------------------------

## 26.9.2 层级逻辑

Synexa 文件体系采用“主基线定义共识、项目基线展开应用、具体文件承接执行”的层级结构。

| 层级 | 名称                           | 定义                                                                                                        | 主要内容                                                                                               | 对齐要求                                                                   |

| L1   | Domain Baseline｜全域基线      | 面向 Synexa 全生态的统一规范，规定全域文件、模板、视觉、字体、命名、结构和输出方式。                        | 全域 CI、字体、色彩、版式、内容形态、命名规则、文档类型标准、基础 UI / UX 原则。                       | 必须与 L0 同步更新。                                                       |
| L2   | Global Standard｜全局标准      | 面向跨项目、跨业务线、跨团队共用的标准。                                                                    | 报告标准、PPT 标准、表格标准、官网标准、系统界面标准、数据字段标准、文件命名标准。                     | 必须继承 L0 / L1，不得自建另一套规范。                                     |
| L3   | Project Baseline｜项目基线     | 面向具体项目或业务模块的基线文件。                                                                          | 项目定位、项目与其他项目的联动关系、核心对象、视觉应用、内容结构、功能边界、交付形态。                 | 基于 L0 中的项目定位统一共识展开，不得自行改变项目在 Synexa 生态中的位置。 |
| L4   | Document Profile｜文档类型标准 | 面向具体文档类型的结构和版式标准。                                                                          | 战略报告、客户方案、投资人材料、项目简报、SOP、报价文件、合同附件、工作表格、日报周报、复盘报告。      | 必须引用统一命名、结构、字体、版式、版本和 QA 规则。                       |
| L5   | Output Instance｜具体交付物    | 每一次实际输出的 PDF、PPTX、DOCX、HTML、Markdown、JSON / YAML、网页、表格、图片或系统界面。                 | 真实交付文件、页面、表格、模板、系统组件、客户材料。                                                   | 必须通过输出质检，确认版本、样式、命名、锚点和语义未失真。                 |

## 26.9.3 项目定位归位原则

各项目的基本定位、生态位置、业务关系和战略优先级，应在 L0 Master SSOT 中保留“项目组合级共识”，但不在 L0 中展开执行细节。

L0 只回答四个问题：

1.  这个项目在 Synexa 生态中是什么；
2.  它属于哪个能力层、业务线、系统模块或场景网络；
3.  它与其他项目之间是什么关系；
4.  它当前处于 concept、prototype、pilot、active、validated、scalable 还是 archived 状态。

L3 项目基线负责在 L0 共识基础上展开具体内容，包括项目结构、功能边界、视觉应用、内容模块、页面结构、系统界面、运营文件、模板形态和执行路径。

项目基线不得脱离 L0 自行定义项目身份。L0 是项目定位的锚，L3 是项目能力的枝叶。

## 26.9.4 核心原则

### 1. 主源统一原则

Markdown / YAML / JSON 是内容与结构主源；HTML、PDF、PPTX、DOCX、网页、图片和系统界面均为输出形态。任何内容级修改必须回到主源，不得直接在渲染文件中形成事实版本。

### 2. 定位统一原则

所有对外和对内文件必须继承 Synexa 的公司定位、能力体系、核心术语、系统架构和项目归位。任何改变公司定位、项目属性、能力边界或系统关系的表达，均属于高风险变更。

### 3. 视觉统一原则

所有 Synexa 生态文件必须继承统一 CI、品牌色、字体系统、字号层级、设计令牌、版式密度、留白逻辑、表格风格和信息层级。不同文件类型可以进行场景化适配，但不得形成与 Synexa 视觉气质冲突的孤立风格。

### 4. 基础应用与细分应用并行原则

全域视觉规范分为两层：

- 基础应用：适用于所有文件的最低一致性要求，包括 Logo、品牌色、字体气质、标题层级、页眉页脚、版本号、表格边界、命名格式和输出 QA。
- 细分应用：适用于不同对象和环境的场景化规则，包括官网、后台系统、Dashboard、客户方案、投资人材料、合同报价、内部 SOP、工作表格、社交传播图、报告 PDF、演示 PPT 等。

基础应用必须统一；细分应用可以变化，但必须可追溯到基础规则。

### 5. 字体与内容环境适配原则

字体选择不能只看美观，必须同时考虑应用对象、阅读环境、输出媒介、机器解析和长期维护成本。

英文与数字应保持机器感、系统感与终端感；中文标题应保持战略判断感与认知基线气质；中文正文应保持清晰、克制、可信和低摩擦阅读。合同、报价、正式商务文件可优先兼容性；官网和系统界面可强化数字感；报告和主基线文件应兼顾判断力、密度和可读性。

### 6. 信息排序原则

所有文件的信息排序应优先服务“人类快速判断”和“机器稳定解析”两个目标。

常规排序原则如下：

- 第一层：对象名称、项目名称、模块名称、文件名称或关键判断；
- 第二层：分类、编号、版本、状态、责任主体、适用场景；
- 第三层：说明、逻辑、依据、备注、风险、后续动作。

在表格设计中，首列原则上不应默认使用“序号”。首列应优先放置最具识别力和检索价值的字段，例如项目名称、模块名称、文件名称、资产名称、规则名称、对象名称或任务名称。序号可以作为第二列或辅助列存在，用于排序、引用和追踪。

序号服务管理，不服务理解；命名服务识别，才是首列的首要价值。

### 7. 人机共读原则

所有正式文件应同时考虑人类阅读、机器解析、智能体调用和组织归档。章节编号、稳定字段、Concept ID、Anchor ID、版本号、文件名、日期、状态标签和变更记录，是机器可读的基础结构，不得因视觉美化而随意删除。

### 8. 内容形态标准化原则

报告、表格、PPT、SOP、客户方案、官网页面、系统文案、项目基线、合同附件、报价文件、内部复盘、会议纪要、日报周报均应逐步建立 Document Profile。每一种文档类型都应拥有固定的结构、模块、语言边界、信息密度、适用对象和输出质量门。

### 9. 允许适配，不允许漂移

不同项目、客户、场景和媒介可以拥有表达差异，但只能在上位基线之内进行适配。任何改变公司定位、核心概念、视觉主识别、字体系统、设计 token、章节逻辑、命名规则或治理规则的行为，均属于高风险变更。

## 26.9.5 版式与表格基础原则

| 原则         | 规则                                                                                               |
|:-------------|:---------------------------------------------------------------------------------------------------|
| 首列命名原则 | 表格首列优先放项目、模块、对象、文件、任务或资产名称，不默认放序号。                               |
| 序号辅助原则 | 序号用于排序、引用、追踪，可放第二列或辅助列，不应压过核心识别字段。                               |
| 名称优先原则 | 任何需要被人记住、被机器检索、被团队复用的对象，都必须有稳定命名。                                 |
| 状态显性原则 | 草稿、候选、试运行、已验证、归档、废弃等状态应有固定字段，不靠颜色或口头说明。                     |
| 版本显性原则 | 只要内容发生实质更新，必须产生版本迭代，不得使用“最新版”“最终版”“更新版”等非职业命名。             |
| 信息密度原则 | 主基线、报告和表格允许高密度；客户版和官网版需要更强可读性；PPT 只承载讲述结构，不承载完整事实源。 |
| 机器解析原则 | 表格字段应稳定、短名清晰、避免同义字段并存，必要时提供字段说明和机器字段名。                       |
| 备注降噪原则 | 备注、边界、例外情况应统一放在备注列、Callout 或 Appendix，不与主判断混排。                        |

## 26.9.9 底线

超智全域文件体系允许不断进化，但不允许各自为政；允许因场景适配表达，但不允许失去母体秩序；允许形成多种文档形态，但不允许多套事实源并存。

项目可以有个性，体系必须有主轴。模板可以为场景而变，命名必须职业化。视觉可以细分，基线不能漂移。序号可以帮助管理，但不能替代命名。输出可以像花一样开放，主源必须像根一样稳固。

Synexa 的每一份文件，都是协同智能系统的一片神经元。局部可以生长，全身必须同频。

## 26.9.10 Baseline Modular Architecture Anchor｜基线文件标准化模块架构锚定

所有 Synexa 基线文件必须采用“通用模块 + 层级模块 + 项目个性模块 + 机器模块”的标准化模块架构。不同层级的基线文件可以拥有不同深度，但不得缺失基本治理模块。

### A. 通用模块｜所有基线文件应具备

| 模块                   | 作用                                               | 是否必备 |
|:-----------------------|:---------------------------------------------------|:---------|
| Cover / File Identity  | 文件标题、版本、文件性质、适用对象、维护主体。     | 必备     |
| Baseline Protocol      | 说明文件的主源规则、人机共读原则、使用边界。       | 必备     |
| Executive Summary      | 用最短路径说明项目 / 体系的整体定义、定位、价值、当前阶段、核心结构、全域关系、文件用途和关键变化。概述首先服务项目本体理解，其次说明文件功能，不得以文件功能说明替代项目整体描述。 | 必备     |
| Scope & Boundary       | 定义文件适用范围、不可用范围、披露边界和转译规则。 | 必备     |
| Core Concepts          | 定义核心术语、概念、缩写和语义锚点。               | 必备     |
| Structure Map          | 展示文件结构、模块关系、章节编号。                 | 必备     |
| Governance Rules       | 定义版本、审计、变更、命名、输出质检规则。         | 必备     |
| Machine-Readable Index | Concept ID、Anchor ID、字段、机器读取建议。        | 建议必备 |
| Version Register       | 版本记录、变更摘要、上一版本映射。                 | 必备     |
| Output QA Checklist    | 输出检查清单。                                     | 必备     |

### A1. Baseline Overview Standard｜基线概述标准

所有基线文件的概述部分，必须优先回答“项目 / 体系是什么”，再回答“文件如何被使用”。概述不得只写文件用途，也不得只写抽象使命；必须优先完成项目 / 体系本体说明，再说明该文件如何支持执行、系统建设与经验资产沉淀。

基线概述应至少覆盖：

| 模块 | 说明 |
|---|---|
| 项目 / 体系一句话定义 | 让读者立即知道这是什么。 |
| 项目定位与战略价值 | 说明它在 Synexa 全域中的位置与存在价值。 |
| 当前阶段与核心问题 | 说明为什么现在要建立或升级这份基线。 |
| 核心组成与运行逻辑 | 简要说明项目由哪些关键模块构成，如何运转。 |
| 与全域系统的关系 | 说明它如何连接 Synexa iS、Nex·EC、Nex·PVC 与项目组合。 |
| 文件三层服务对象 | 说明该文件如何服务项目执行层、系统建设层与经验资产层。 |
| 使用对象与使用边界 | 说明给谁用、怎么用、不能怎么用。 |

项目本体描述缺失的文件，不得仅因具备版本、格式、交付和治理规则而被认定为完整基线文件。

### B. 层级模块｜不同层级基线的专属模块

| 层级                | 文件类型     | 应配置模块                                                                           |
|:--------------------|:-------------|:-------------------------------------------------------------------------------------|
| L0 Master SSOT      | 主基线       | 公司定位、能力体系、认知框架、项目组合定位、系统架构、全域治理、视觉令牌、机器锚点。 |
| L1 Domain Baseline  | 全域基线     | CI / UI / UX / 字体 / 色彩 / 命名 / 文档类型 / 表格 / 模板 / 输出形态。              |
| L2 Global Standard  | 全局标准     | 具体标准定义、适用文件类型、字段规范、模板结构、示例、QA 规则。                      |
| L3 Project Baseline | 项目基线     | 项目定位、项目对象、联动关系、功能边界、视觉应用、模板清单、数据字段、交付路径。     |
| L4 Document Profile | 文档类型标准 | 文档用途、受众、固定模块、版式规则、命名规则、输出格式、检查标准。                   |
| L5 Output Instance  | 具体交付物   | 文件身份、版本、内容主体、输出格式、归档位置、引用来源。                             |

### C. 项目个性模块｜由项目特点决定

| 项目类型     | 可增加模块                                                       |
|:-------------|:-----------------------------------------------------------------|
| 官网项目     | 信息架构、页面结构、SEO、交互路径、视觉组件、内容转译规则。      |
| 系统项目     | 角色权限、对象模型、数据流、界面状态、异常提示、API / 字段映射。 |
| 供应链项目   | 供应节点、品类结构、采购规则、质量标准、替代策略、履约风险。     |
| 餐食履约项目 | 菜单结构、订单流、出品流、分餐流、核销规则、现场异常。           |
| 营养决策项目 | 用户画像、医学规则、营养规则、推荐逻辑、反馈信号、风险提示。     |
| 品牌传播项目 | 受众分层、话语体系、内容栏目、视觉母版、渠道矩阵、转化路径。     |

项目个性模块可以增长，但不得替代通用模块；个性是枝叶，通用模块是骨架。

## 26.9.11 Dictionary System｜全域字典体系

Synexa 必须逐步建立跨层级、跨项目、跨文档类型的字典体系。字典不是附属资料，而是组织认知、机器检索、字段统一和跨项目协同的基础设施。

### A. 字典层级

| 字典类型                                     | 作用                                                                    | 归属层级          |
|:---------------------------------------------|:------------------------------------------------------------------------|:------------------|
| Master Dictionary｜主字典                    | 定义 Synexa 全域最高级术语、概念、缩写、项目名称、能力层级。            | L0                |
| Domain Dictionary｜全域字典                  | 定义 CI、UI / UX、字体、色彩、文档类型、命名、版本、状态标签。          | L1                |
| Project Dictionary｜项目字典                 | 定义项目专属术语、对象、角色、字段、流程、页面、模块。                  | L3                |
| Document Dictionary｜文档字典                | 定义某类文档固定模块、字段名、表格列名、状态标签、输出格式。            | L4                |
| Machine Dictionary｜机器字典                 | 定义 Concept ID、Anchor ID、Field ID、Object ID、Project ID、状态枚举。 | L0 / L1 / L3 共用 |
| Vertical Integrated Dictionary｜垂直整合字典 | 将各项目、各层级、各业务线中的同类概念整合为统一全域字典。              | L1 / L2           |

### B. 字典标准字段

| 字段            | 说明                                         |
|:----------------|:---------------------------------------------|
| Term ID         | 术语编号。                                   |
| 中文名          | 中文正式名称。                               |
| 英文名          | 英文正式名称。                               |
| Short Name      | 简称或系统字段名。                           |
| Definition      | 定义。                                       |
| Layer           | 所属层级。                                   |
| Project         | 所属项目，如为全域通用则标记 Global。        |
| Category        | 术语类别。                                   |
| Related Terms   | 关联术语。                                   |
| Allowed Usage   | 允许使用场景。                               |
| Forbidden Usage | 禁止或不建议使用方式。                       |
| Version         | 版本。                                       |
| Status          | active / deprecated / archived / candidate。 |

### C. 字典建设触发条件

出现以下情况时，必须新增或更新字典：

1.  新增项目、模块、引擎、系统、场景或能力层；
2.  同一个概念在多个文件中出现不同叫法；
3.  某个字段需要跨表格、跨系统、跨项目复用；
4.  某个术语开始进入对外表达、客户方案或官网；
5.  某个概念需要进入机器索引、RAG、知识库或系统字段；
6.  发生命名冲突、理解歧义、翻译不一致或缩写混乱；
7.  某个项目由试验阶段进入正式项目基线阶段。

### D. 垂直整合原则

项目字典可以先局部生成，但成熟后必须向上汇总到全域字典。凡是跨两个以上项目复用的术语、字段、状态、对象或流程，都应进入 Domain Dictionary 或 Global Standard，不再停留在单一项目内。

局部先长，成熟上收；项目先试，全域再定。这样既不压死创新，也不纵容混乱。

------------------------------------------------------------------------

## 26.9.12 Common Modules & Custom Modules｜通用模块与个性化模块设计原则

Synexa 所有文件与模板采用“70% 通用模块 + 30% 个性化模块”的设计思路。比例不是机械限制，而是治理倾向：先保证稳定骨架，再允许项目生长。

### 通用模块原则

通用模块用于保证跨文件、跨项目、跨智能体协作时的可识别性、可复用性和可审计性。凡是涉及身份、版本、边界、术语、结构、治理、机器读取和输出检查的模块，都应尽可能通用化。

通用模块不得因项目审美、客户偏好或临时排版便利而删除。

### 个性化模块原则

个性化模块用于承载具体项目、业务场景、客户对象、输出媒介和传播语境的差异。个性化模块可以在 L3 / L4 / L5 中展开，但必须声明其上位来源、适用边界和复用条件。

个性化模块不得自行建立另一套命名系统、字体系统、状态系统或版本系统。

### 模块成熟转化

当某个项目个性模块被两个以上项目复用，或被三次以上正式输出验证，应评估是否上升为通用模块、全局标准或全域字典条目。

## 26.9.13 Baseline Development Trigger｜基线建设与升级触发机制

Synexa 基线文件不是一次性写作成果，而是随着项目、系统、场景、模板和经验资产增长而持续进化的治理结构。

出现以下情况时，应触发基线建设或升级：

| 触发类型       | 说明                                                       | 建议动作                                        |
|:---------------|:-----------------------------------------------------------|:------------------------------------------------|
| 新项目出现     | 出现新的业务项目、系统项目、品牌项目、供应项目或场景项目。 | 先在 L0 增加项目组合定位，再建立 L3 项目基线。  |
| 新文件类型出现 | 出现高频报告、表格、SOP、客户方案、复盘、合同附件等。      | 建立 L4 Document Profile。                      |
| 新术语高频出现 | 某概念跨文件反复出现，且有理解歧义。                       | 进入字典体系。                                  |
| 新视觉应用出现 | 官网、PPT、系统界面、客户材料出现新视觉需求。              | 更新 L1 Domain Baseline 或 Appendix E。         |
| 新数据字段出现 | 某字段需要跨系统、跨表格、跨项目复用。                     | 进入 Field Dictionary / Global Standard。       |
| 新模板被复用   | 某模板被多个项目使用。                                     | 从项目模板上升为全域模板。                      |
| 新风险出现     | 文件命名混乱、版本混乱、项目定位漂移、术语冲突。           | 触发治理补丁与 QA 规则更新。                    |
| 新输出对象出现 | 客户、投资人、合作伙伴、内部团队有不同阅读需求。           | 建立对应 Audience Edition 或 Document Profile。 |

### 升级逻辑

1.  先判断是否只是 L5 输出问题；
2.  如果多个输出反复出现同类问题，升级到 L4 文档类型标准；
3.  如果多个文档类型反复出现同类问题，升级到 L2 全局标准；
4.  如果影响全域视觉、命名、术语、版本或项目定位，升级到 L1 / L0；
5.  如果改变公司定位、核心架构、项目组合关系或治理原则，必须进入 L0 Master SSOT 审计。

局部问题不急着上升为制度，但重复三次的问题，就不是偶然，是系统在敲门。

# CH 26.10｜Synexa Professional Naming System <span class="subtitle">超智职业化命名系统</span>

命名是治理，不是修饰。Synexa 所有项目、文件、模板、表格、页面、系统模块、字段、版本、输出物和经验资产，必须采用可识别、可追踪、可检索、可协作、可审计的职业化命名系统。

命名的目标不是显得复杂，而是减少沟通成本、降低版本风险、提升组织可信度，并让人类与机器都能稳定识别同一个对象。

## 26.10.1 命名总原则

| 原则       | 说明                                                             |
|:-----------|:-----------------------------------------------------------------|
| 稳定性     | 名称一旦进入正式文件，应保持稳定，不随临时偏好频繁变化。         |
| 可识别性   | 名称应直接说明对象是什么，而不是只用序号、颜色、人员或模糊描述。 |
| 可检索性   | 文件名、项目名、模块名、字段名应便于搜索、排序、机器读取。       |
| 可追踪性   | 名称应能连接版本、日期、项目、类型、状态和责任记录。             |
| 可扩展性   | 命名应支持未来项目增长、模块扩展、跨系统使用。                   |
| 对外职业化 | 对外文件不得使用内部口语、颜色标识、临时状态或情绪化命名。       |
| 人机共读   | 命名应同时服务人类理解和机器索引。                               |

## 26.10.2 命名对象范围

| 对象       | 示例                                                               |
|:-----------|:-------------------------------------------------------------------|
| 公司与品牌 | Synexa、NexSply、NexChef。                                         |
| 项目       | Synexa Website、Nex2U、Domain Document System。                    |
| 文件       | Master SSOT、Project Baseline、Client Proposal、Strategic Report。 |
| 模板       | Meeting Notes Template、Report Template、SOP Template。            |
| 表格       | Project Portfolio Table、Asset Registry、Field Dictionary。        |
| 系统模块   | NexLens Dashboard、NexChef Order Flow。                            |
| 字段       | Project ID、Status、Version、Owner。                               |
| 版本       | v3.4.0、v3.4、v3.4.0-rc.1。                                        |
| 状态       | active、validated、archived、deprecated。                          |
| 经验资产   | Pattern Asset、Exception Asset、Rule Asset、Field Asset。          |

## 26.10.3 文件命名结构

正式文件推荐采用以下结构：

`[Brand]_[Project-or-Domain]_[Document-Type]_[Short-Description]_[Version]_[Date].[Extension]`

| 字段              | 说明                                 | 示例                                               |
|:------------------|:-------------------------------------|:---------------------------------------------------|
| Brand             | 品牌或体系名。                       | Synexa                                             |
| Project-or-Domain | 项目、业务域或全域名称。             | MasterSSOT / Nex2U / Website                       |
| Document-Type     | 文档类型。                           | ProjectBaseline / StrategicReport / ClientProposal |
| Short-Description | 简短说明，使用英文或拼音式稳定短语。 | CompanyIntro / ContentArchitecture                 |
| Version           | 版本号。                             | v3.4.0                                             |
| Date              | 输出日期，YYYYMMDD。                 | 20260621                                           |
| Extension         | 文件格式。                           | md / pdf / pptx / docx / xlsx / json               |

示例：

- `Synexa_MasterSSOT_CompanyIntro_v3.4.0_20260621.md`
- `Synexa_Nex2U_ProjectBaseline_v0.3.0_20260621.md`
- `Synexa_Website_ContentArchitecture_v0.2.0_20260621.pdf`
- `Synexa_ClientProposal_HospitalNutrition_v1.1.0_20260621.pptx`
- `Synexa_DomainDictionary_Terminology_v1.0.0_20260621.xlsx`
- `Synexa_DocumentProfile_WorkReport_v1.0.0_20260621.md`

## 26.10.4 项目命名规则

项目命名应同时具备战略识别、生态归属和长期可扩展性。

| 命名项      | 规则                                           |
|:------------|:-----------------------------------------------|
| Project ID  | 使用稳定编号，如 PRJ-001、PRJ-002。            |
| 中文名      | 用于内部理解和中文材料。                       |
| 英文名      | 用于文件名、系统、GitHub、机器索引。           |
| Short Code  | 用于表格、系统字段和跨文件引用。               |
| Public Name | 如对外名称不同，应单独记录，不替代内部正式名。 |
| Status      | 必须显性标注成熟度状态。                       |

项目名称不得只用“新官网”“医院项目”“供应链项目”“那个系统”“新版项目”等临时说法。临时讨论可以口语化，正式文件必须归一化。

## 26.10.5 模块命名规则

模块命名应遵循“功能对象 + 能力含义 + 层级归属”的原则。

| 类型     | 推荐命名                     | 不推荐命名   |
|:---------|:-----------------------------|:-------------|
| 系统模块 | NexChef_OrderFlow            | 点餐那个流程 |
| 数据模块 | NexLens_OperationDashboard   | 运营看板新版 |
| 文档模块 | DomainDictionary_Terminology | 术语表最新   |
| 视觉模块 | Synexa_DesignTokens          | 颜色更新版   |
| 经验模块 | Cortex_ExceptionLibrary      | 异常库最终   |

## 26.10.6 表格与字段命名规则

表格名称应说明对象和用途，字段名称应稳定、短名清晰、避免同义重复。

| 规则     | 说明                                                                          |
|:---------|:------------------------------------------------------------------------------|
| 首列命名 | 首列优先使用对象名称、项目名称、模块名称、文件名称或资产名称。                |
| 序号退位 | 序号可作为第二列或辅助列，不作为默认首列。                                    |
| 字段稳定 | 同一字段跨表格应保持一致，不得一处叫“负责人”，一处叫“责任人”，一处叫“Owner”。 |
| 中英映射 | 关键字段应建立中文名、英文名、机器字段名的映射。                              |
| 状态枚举 | 状态字段必须使用固定枚举，不得自由填写。                                      |
| 日期格式 | 日期统一使用 YYYYMMDD 或 YYYY-MM-DD。                                         |
| 版本字段 | 版本必须独立成字段，不得混入备注。                                            |

## 26.10.7 版本命名规则

版本号采用 `vMajor.Minor.Patch`。

| 类型      | 示例            | 适用情况                                               |
|:----------|:----------------|:-------------------------------------------------------|
| Major     | v4.0.0          | 公司定位、系统架构、项目归位、核心方法论发生重大变化。 |
| Minor     | v3.4.0          | 新增章节、模块、模板、项目定位、命名规则或治理规则。   |
| Patch     | v3.4.1          | 修正错别字、格式、页脚、表格排版、轻微表述。           |
| Working   | v3.4            | 工作稿，尚未完成审计或确认。                           |
| Candidate | v3.4.0-rc.1     | 候选正式版，等待最终审查。                             |
| Archived  | v3.3.0-archived | 已归档版本，不再作为主源。                             |

日期不是版本号；颜色不是版本号；人员确认不是版本号；“最终版”更不是版本号。

## 26.10.8 禁用命名清单

以下命名不得用于正式文件、正式表格、正式输出物或对外材料：

- 最新版
- 最终版
- 终稿
- 最终最终版
- 真的最终版
- 更新版
- 修改版
- 颜色更新版
- 红色版
- 蓝色版
- 老板确认版
- 客户确认版
- 先用这个
- 可用了
- 新版本
- New
- Final
- Final-final
- OK版
- 备份2
- 副本
- 复制件

如确需记录客户确认、内部确认、颜色方案或阶段状态，应写入文件元数据、版本记录或状态字段，而不是写入正式名称。

## 26.10.9 对外命名规则

对外文件必须优先体现专业、稳定、可信和可追踪。

对外文件命名应避免暴露内部过程、内部争议、临时状态、颜色调整、人员确认、反复修改痕迹。客户看到的文件名，应当像一个完成过治理的交付物，而不是一张厨房里的备菜单。

推荐：

- `Synexa_ClientProposal_HospitalNutrition_v1.1.0_20260621.pdf`
- `Synexa_InvestorBrief_CollaborativeIntelligence_v1.0.0_20260621.pdf`

不推荐：

- `医院方案最新版.pdf`
- `给客户看的最终版2.pdf`
- `红色调整版.pptx`
- `老板确认可发版.pdf`

## 26.10.10 命名变更治理

任何正式命名变更都必须说明：

| 项目           | 说明                                           |
|:---------------|:-----------------------------------------------|
| Old Name       | 原名称。                                       |
| New Name       | 新名称。                                       |
| Change Reason  | 变更原因。                                     |
| Scope          | 影响范围。                                     |
| Mapping        | 旧名称与新名称映射。                           |
| Status         | candidate / approved / deprecated / archived。 |
| Effective Date | 生效日期。                                     |

项目、模块、字段和文件类型一旦进入多个文件使用，命名变更必须进入 Change Log，并检查是否影响机器索引、历史归档、引用路径和对外材料。

# CH 26.11｜Synexa Baseline Layout & Presentation Standard <span class="subtitle">超智基线文件排版与呈现标准</span>

## 26.11.1 定义

超智基线文件排版与呈现标准，是 Synexa 生态下所有 Master SSOT、Domain Baseline、Global Standard、Project Baseline、Document Profile、System Baseline、Dictionary Baseline 和重要治理文件必须遵守的版式规则。

本标准明确：所有 Synexa 基线文件的排版形式，必须严格参照当前 Master SSOT 基线文件的排版体系完成。包括但不限于 CI 识别、页眉页脚、章节结构、标题层级、表格样式、Callout 样式、字体系统、字号行距、色彩令牌、信息密度、机器可读结构、内容形态和输出质检方式。

本标准不要求所有文件内容相同，但要求所有基线文件拥有同一套可识别、可复用、可审计、可机器解析的版式秩序。

------------------------------------------------------------------------

## 26.11.2 基本原则

### 1. 当前 Master SSOT 是基线文件排版母版

当前 Synexa Master SSOT 的排版形式，是所有后续基线类文件的默认母版。后续所有 L0-L4 层级的正式基线文件，应在该母版基础上进行场景适配，而不是重新设计一套风格。

基线文件可以因对象、篇幅、用途不同而调整信息密度，但不得偏离当前 Master SSOT 已形成的整体视觉气质、章节秩序、表格样式和人机共读结构。

### 2. 统一不等于复制，适配不等于漂移

所有基线文件应保持统一的视觉血缘。项目基线、系统基线、字典基线、文档类型基线可以有局部模块变化，但不得形成与 Master SSOT 完全不同的版式语言。

统一是根系，适配是枝叶。枝叶可以舒展，根系不能断。

### 3. 结构、逻辑、模块和形态同步标准化

基线文件不是只统一颜色和字体，而是同时统一：

- 结构：章节编号、目录、Appendix、版本记录、机器索引；
- 逻辑：从定位、边界、结构、方法、治理到输出质检的顺序；
- 模块：通用模块、层级模块、项目模块、机器模块；
- 形态：封面、摘要页、正文页、表格页、Callout、附录页、QA 页。

任何只做视觉统一、不做结构统一的文件，都不能称为正式基线文件。

------------------------------------------------------------------------

## 26.11.3 基线文件标准排版要素

所有 Synexa 基线文件应优先包含以下排版要素：

| 要素                         | 标准要求                                                                              |
|:-----------------------------|:--------------------------------------------------------------------------------------|
| Cover / 封面                 | 包含品牌识别、文件名称、版本号、文件性质、核心说明、关键数字或模块摘要。              |
| Header / 页眉                | 保留文件类别、章节类型或当前阅读位置，形成稳定导航。                                  |
| Footer / 页脚                | 保留文件名、版本号、页码或适用标识，便于归档和引用。                                  |
| Eyebrow / 眉题               | 使用英文或短标签标识章节性质，如 BASELINE PROTOCOL、POSITIONING、VERSION GOVERNANCE。 |
| Chapter Title / 章节标题     | 使用统一章节编号和中英文标题，支持人类阅读与机器分块。                                |
| Executive Summary / 执行摘要 | 用高密度方式说明文件核心判断和关键变化。                                              |
| Tables / 表格                | 使用统一表格线、表头深色底、字段稳定、首列命名优先、序号辅助。                        |
| Callout / 提示框             | 用于定义、边界、原则、风险、核心句，不与正文混排。                                    |
| Appendix / 附录              | 独立于正文编号，承接模板、版本、机器索引、QA 等模块。                                 |
| Machine Anchors / 机器锚点   | 保留 Concept ID、Anchor ID、字段、版本和机器读取建议。                                |
| QA Checklist / 输出质检      | 所有正式输出前必须保留或关联 QA 检查项。                                              |

------------------------------------------------------------------------

## 26.11.4 CI、UI / UX 与视觉排版要求

所有 Synexa 基线文件必须继承统一 CI 与视觉体系。

### CI 要求

- 使用 Synexa 统一品牌识别；
- 品牌红不得被年度色、项目色或客户色替代；
- 对外文件可适度降噪，但不得隐藏品牌归属；
- 项目品牌可作为子识别存在，不得压过 Synexa 主识别。

### UI / UX 要求

基线文件虽然不是系统界面，但也必须遵守信息体验原则：

- 让人一眼知道这是什么文件；
- 让人快速知道当前章节在讲什么；
- 让表格可以被扫描、检索和复用；
- 让关键判断以 Callout、表格或锚点形式被稳定识别；
- 让机器可以通过章节编号、字段和锚点稳定解析。

### 视觉排版要求

- 保持当前 Master SSOT 的高密度、低噪音、强结构风格；
- 使用统一字体系统、字号层级、行距、表格密度和边距；
- 不使用装饰性过强、传播海报式、杂志化过度或无法机器解析的排版；
- 视觉设计服务认知秩序，不服务短期炫技。

## 26.11.5 字体、字号与内容形态

所有基线文件应继承 Appendix E 的字体与设计令牌系统。

### 字体原则

- 英文与数字：保持机器感、系统感、终端感；
- 中文标题：保持战略判断感、认知基线感和可信度；
- 中文正文：保持清晰、克制、稳定、低摩擦；
- 表格与数据：优先保证可读、可扫描、可机器解析；
- 合同、报价、商务文件：可优先兼容性，但不得脱离整体气质。

### 内容形态原则

基线文件内容形态应优先使用：

- 高密度表格；
- 短段落；
- 明确编号；
- 定义框；
- 原则框；
- 边界框；
- 版本记录；
- 机器锚点；
- 输出 QA。

### 内容形态三级治理

#### A. 严禁使用

以下内容在正式基线文件中严禁作为主体表达方式：

1.  图片化文字替代可复制正文；
2.  无字段结构的长篇散文式主体内容；
3.  无版本依据的描述；
4.  无章节编号、无锚点、无字段的松散堆叙；
5.  只服务美观、不服务理解和机器解析的装饰性组件；
6.  直接在 PDF / PPT / DOCX 中修改事实内容而不回到主源；
7.  用颜色、人员确认、最终版等替代版本管理；
8.  删除页脚版本号、文件名、页码和机器锚点。

#### B. 限制使用

以下形式在正式基线文件中限制使用，只有在不影响主源、字段、机器解析和版本治理时，才可少量使用：

1.  长段落叙事；
2.  大面积视觉图形；
3.  复杂嵌套表格；
4.  合并单元格较多的表格；
5.  非必要装饰图标；
6.  传播感较强的视觉页；
7.  情绪化标题或口号式表达。

#### C. 例外允许

以下场景可以使用更强视觉化表达，但必须进入对应 Document Profile，不得替代基线文件主源：

1.  官网页面；
2.  PPT 演示；
3.  品牌传播图；
4.  授权展示材料；
5.  客户版轻量材料；
6.  信息图；
7.  系统架构图；
8.  展板或海报。

基线文件中的视觉表达可以辅助理解，但不得替代主源、字段、章节、版本和机器锚点。

## 26.11.5A 字体实现与渲染预检

VI 字体规则不得只停留在原则和 token 层，必须落实到 HTML / PDF / PPT / DOCX 的实际渲染文件。正式输出前，应检查渲染环境是否安装首选字体；必须优先检查 Space Grotesk 与思源宋体加粗 / Source Han Serif SC Bold 是否可用。近似字体池只作为参考，不得自动替代主字体锚点。

| 检查项       | 要求                                                                                                                           |
|--------------|--------------------------------------------------------------------------------------------------------------------------------|
| 主锚字体检查 | 优先检查 Space Grotesk、思源宋体加粗 / Source Han Serif SC Bold、中文正文用思源黑体 / Source Han Sans SC 是否可用。            |
| 替代字体记录 | 首选字体不可用时，允许使用 DejaVu Sans Mono、Noto Sans Condensed、Noto Serif CJK、Noto Sans CJK 等已列入矩阵或等价替代的字体。 |
| 禁止静默回退 | 不得在 Master SSOT 渲染中静默回退到普通 Inter 气质，除非该场景在 Document Profile 中明确允许。                                 |
| PDF 字体核验 | PDF 输出后应通过渲染抽样和字体列表检查确认字体已嵌入或被正确替代。                                                             |

## 26.11.6 表格与信息排序排版要求

基线文件中的表格应遵守以下规则：

| 规则         | 说明                                                         |
|:-------------|:-------------------------------------------------------------|
| 首列命名优先 | 首列优先放项目、模块、对象、文件、资产或规则名称。           |
| 序号辅助     | 序号只作为排序、引用、追踪字段，不默认作为首列。             |
| 字段稳定     | 同类表格字段应跨文件保持一致。                               |
| 表头明确     | 表头必须短、准、可机器理解。                                 |
| 状态显性     | 状态、版本、成熟度、责任主体应成为字段，不靠颜色或备注表达。 |
| 备注降噪     | 备注放在备注列、Callout 或附录，不干扰主判断。               |
| 机器可读     | 避免过度合并单元格、复杂嵌套表、图片化表格。                 |

## 26.11.7 基线文件与其他文档类型的关系

本标准优先约束“基线文件”。报告、PPT、客户方案、工作表格、会议纪要、SOP、合同报价、Dashboard、官网页面等其他文档类型，将逐步建立独立 Document Profile。

在独立标准建立前，其他文档类型应暂时参考以下原则：

| 文档类型   | 当前参考规则                                         | 后续方向                         |
|:-----------|:-----------------------------------------------------|:---------------------------------|
| 战略报告   | 参考 Master SSOT 的结构、字体、表格和 Callout 规则。 | 建立 Strategic Report Profile。  |
| 客户方案   | 参考基线文件的结构清晰原则，降低信息密度。           | 建立 Client Proposal Profile。   |
| 投资人材料 | 参考基线文件的判断结构，转化为 PPT 叙事。            | 建立 Investor Material Profile。 |
| 工作表格   | 参考首列命名、字段稳定、状态显性、版本独立原则。     | 建立 Data Table Profile。        |
| 会议纪要   | 参考对象、结论、责任人、截止时间、回流位置标准。     | 建立 Meeting Notes Profile。     |
| SOP        | 参考触发条件、步骤、责任、质量门、异常处理结构。     | 建立 SOP Profile。               |
| 官网页面   | 参考 Appendix E 视觉系统和 CH26.11 信息体验原则。    | 建立 Website Profile。           |
| Dashboard  | 参考 UI / UX、数据密度、状态反馈和机器字段规则。     | 建立 Dashboard Profile。         |

报告等各类模板将逐一建立统一标准。不同文档类型可以拥有不同结构、逻辑、模块和形态，但必须纳入 Synexa 全域统一治理。

## 26.11.8 基线文件排版生成规则

任何新建或升级基线文件时，必须遵守以下步骤：

1.  先确认该文件属于 L0、L1、L2、L3、L4 还是 L5；
2.  读取当前 Master SSOT 的排版母版；
3.  继承统一 CI、字体、字号、页眉页脚、表格、Callout、Appendix 和 QA 规则；
4.  根据文件层级选择对应标准模块；
5.  根据项目或文档类型增加个性化模块；
6.  输出 Markdown / YAML / JSON 主源；
7.  再生成 HTML / PDF / PPTX / DOCX 等输出形态；
8.  进行渲染抽样检查和 Output QA；
9.  更新 Version Register、Change Log 和 Machine-Readable Index。

不得直接从空白文件开始凭感觉排版。基线文件不是临时设计稿，而是体系资产。

## 26.11.9 禁止事项

以下行为不得出现在正式基线文件中：

1.  脱离当前 Master SSOT 自行设计另一套基线文件风格；
2.  只保留内容，不保留章节编号、版本号和机器锚点；
3.  直接在 PDF、PPT、DOCX 中修改事实内容而不回到主源；
4.  使用“最新版”“最终版”“颜色更新版”等非职业化命名；
5.  用图片化文字替代可复制、可检索的正文和表格；
6.  将序号作为所有表格默认首列；
7.  删除页脚版本号、文件名或页码；
8.  删除 Appendix G / H 等机器读取和输出质检模块；
9.  因客户偏好、项目偏好或设计偏好破坏全域基线气质；
10. 让不同项目基线形成彼此不兼容的版式体系。

## 26.11.10 底线

所有 Synexa 基线文件都必须长在同一棵树上。

可以因项目不同而分枝，可以因对象不同而开花，可以因媒介不同而换叶，但根系必须一致：统一 CI、统一结构、统一字体气质、统一内容秩序、统一命名、统一版本、统一机器锚点、统一输出质检。

当前 Master SSOT 是所有基线文件的排版母版。后续所有基线文件，必须以它为参照生成，而不是另起炉灶。

# CH 26.12｜Synexa Baseline Full Deliverable Standard <span class="subtitle">超智基线文件完整交付标准</span>

## 26.12.1 定义

超智基线文件完整交付标准，是 Synexa 生态下所有正式基线文件、候选版本、审计版本、项目基线、全域标准、字典基线与重要治理文件在交付时必须遵守的文件形态、主源关系、输出组合、质检与归档规则。

本标准用于明确：基线文件交付必须优先交付完整包，而不是只交付增补包。增补包只能作为临时审阅材料、差异说明材料或补丁说明材料，不得替代完整 Master Source、HTML 阅读版和 PDF 正式版。

## 26.12.2 完整包优先原则

任何正式基线文件更新，只要进入候选版本、对外评审、内部归档或团队执行阶段，必须交付完整包。完整包必须包含新版本的完整正文、完整目录、完整附录、完整版本记录、完整机器锚点和完整 QA 清单。

禁止只交付“新增章节”“更新包”“补丁段落”后即视为完成交付。增补内容可以用于过程讨论，但最终必须回写到完整文件中，形成可直接阅读、可直接归档、可直接生成 PDF / HTML、可直接进入知识库和 GitHub 的完整版本。

## 26.12.3 标准完整交付包

任何正式基线文件更新，原则上至少应交付以下文件：

| 交付项                  | 文件形态                  | 用途                                               | 是否必交     |
|:------------------------|:--------------------------|:---------------------------------------------------|:-------------|
| Master Source           | `.md` / `.yaml` / `.json` | 内容主源、结构主源、版本管理、机器喂养。           | 必交         |
| HTML Reading Version    | `.html`                   | 人机共读、网页预览、视觉检查、PDF 渲染中间层。     | 必交         |
| PDF Formal Version      | `.pdf`                    | 正式归档、展示、对外或内部流转。                   | 必交         |
| Machine Index           | `.json` / `.yaml`         | Concept ID、Anchor ID、字段、章节映射、版本索引。  | 建议必交     |
| Change Log / Audit Note | `.md` / `.pdf`            | Forward Audit、Reverse Audit、变更说明、风险提示。 | 重要更新必交 |
| Complete Package        | `.zip`                    | 多文件打包、归档、GitHub 入库或交付外部执行体。    | 建议必交     |

## 26.12.4 最小交付标准

当时间有限或任务仍处于 Working Draft 阶段时，最小交付也不得少于：

1.  Markdown 主源；
2.  HTML 阅读版；
3.  PDF 正式预览版。

如果只交付 Markdown、只交付 PDF、只交付 HTML 或只交付增补包，必须明确标注为 Partial Draft / Patch Draft，不能称为完整交付包，也不能称为新的 Master SSOT 候选版本。

## 26.12.5 增补包使用边界

增补包只允许用于以下场景：

| 场景              | 是否允许     | 说明                                       |
|:------------------|:-------------|:-------------------------------------------|
| 过程讨论          | 允许         | 用于快速审阅新增章节、补丁段落、差异说明。 |
| 局部人工确认      | 允许         | 用于确认高风险变更是否进入完整文件。       |
| Change Log 说明   | 允许         | 用于描述本次新增、删除、合并、改写内容。   |
| 最终交付          | 不允许       | 最终交付必须回写完整包。                   |
| GitHub 入库主文件 | 不允许       | 入库主文件必须是完整文件，不是增补包。     |
| 对外发送          | 原则上不允许 | 除非明确标注为补充说明，而非正式基线文件。 |

增补包是手术记录，不是完整身体。正式交付必须让身体完整站起来。

## 26.12.6 文件形态关系

| 文件形态               | 定位                 | 不得替代对象                   |
|:-----------------------|:---------------------|:-------------------------------|
| Markdown / YAML / JSON | 主源与结构源。       | 不得被 PDF / PPT / DOCX 替代。 |
| HTML                   | 阅读版与渲染中间层。 | 不得成为事实修改源。           |
| PDF                    | 正式归档与展示版。   | 不得作为内容编辑主源。         |
| DOCX                   | 协作批注版。         | 不得成为长期唯一版本。         |
| PPTX                   | 演示叙事版。         | 不得承载完整主源。             |
| ZIP                    | 交付包与归档包。     | 不得掩盖包内文件版本差异。     |

## 26.12.7 文件命名规则

基线文件命名应参考当前正式主基线文件命名方式，采用简洁、稳定、职业化结构：

`Synexa_Company_Intro_VX.Y[.Z].[extension]`

正式版本示例：

- `Synexa_Company_Intro_V3.3.html`
- `Synexa_Company_Intro_V3.3.pdf`

候选草稿示例：

- `Synexa_Company_Intro_V3.5.md`
- `Synexa_Company_Intro_V3.5.html`
- `Synexa_Company_Intro_V3.5.pdf`

同一轮交付中的文件必须共享同一版本号。不得在正式基线文件名中使用 `Update_Package` 替代完整文件身份。`Update_Package` 只能用于过程补丁，不得用于完整主文件。

禁止同一交付包中出现：

- Markdown 是 v3.4，PDF 是最新版；
- HTML 叫更新版，PDF 叫最终版；
- 文件名使用颜色、人员、临时状态替代版本号；
- 包内文件版本号、日期、状态不一致；
- 完整文件仍使用 Update Package 命名。

## 26.12.8 交付前质检

每次交付前必须检查：

| 检查项                | 检查标准                                                                      |
|:----------------------|:------------------------------------------------------------------------------|
| Full Package Check    | 是否交付完整正文、完整目录、完整附录和完整版本记录，而非仅交付增补包。        |
| Version Match         | MD / HTML / PDF 文件名、封面、页脚、版本记录一致。                            |
| Source Match          | HTML / PDF 是否由当前 Markdown / YAML / JSON 主源生成。                       |
| Layout Match          | HTML / PDF 是否继承当前 Master SSOT 的排版体系。                              |
| Rendering QA          | PDF 是否完成抽样渲染检查，无黑块、乱码、溢出、遮挡、断表。                    |
| Link / Anchor Check   | 目录、章节、锚点、内部引用是否可追踪。                                        |
| Machine Readability   | Concept ID、Anchor ID、表格字段、版本号是否保留。                             |
| Delivery Completeness | 是否至少包含 MD、HTML、PDF 三项最小交付。                                     |
| Naming Compliance     | 是否参考正式主基线命名方式，避免 Update Package、最新版、最终版等非正式命名。 |

## 26.12.9 交付底线

基线文件交付不是“发一个能看的文件”，而是交付一组可阅读、可归档、可追踪、可机器解析、可再次生成的完整文件系统。

PDF 是花，HTML 是枝，Markdown / YAML / JSON 是根。交付时可以先给花，但根必须在；可以给补丁，但最终必须回到完整树上。

# CH 26.13｜Human-Machine Decision Governance <span class="subtitle">人机协同决策治理机制</span>

## 26.13.1 定义

人机协同决策治理机制，用于规定 Synexa iS 中哪些事项可以由系统自动建议或执行，哪些事项必须进入人工审核、Judgment Holder 裁决或 Core 级别确认。

## 26.13.2 治理原则

1. AI 可以扩展选项，不替代人的价值判断；
2. 系统可以推演、调度和执行，但方向、边界、价值判断与关键责任必须由人智承担；
3. 高风险行动必须保留人工确认、拒绝、退回和升级路径；
4. 所有关键决策必须形成 Decision Record，并可进入 Judgment Asset；
5. 系统越自动化，治理锚点、日志和人工控制权越要明确。

## 26.13.3 人机权限分级

| 等级 | 决策类型 | 系统权限 | 人智权限 | 必须记录 |
|------|----------|----------|----------|----------|
| D1 | 低风险、可逆、日常执行 | 可建议并自动执行。 | 抽查。 | 自动日志。 |
| D2 | 中风险、可修正、影响局部 | 可生成方案和执行建议。 | 责任人审核。 | 审核记录。 |
| D3 | 高风险、影响客户 / 合作方 / 成本 / 品牌 | 只可推演和建议。 | Judgment Holder 裁决。 | 风险、依据、权衡、裁决。 |
| D4 | 红线事项、外部承诺、重大资源、战略方向 | 不得自动执行。 | Core / 指定负责人确认。 | 完整决策记录与复盘。 |

## 26.13.4 Reject / Revise Governance｜拒绝与修正治理

当人智决策层拒绝系统方案时，不得只记录为“未通过”。必须记录：

| 字段 | 内容 |
|------|------|
| Rejection Reason | 拒绝原因。 |
| Boundary Violated | 触碰了哪类边界：战略、合规、成本、品牌、伦理、客户承诺。 |
| Required Revision | 需要系统重新推演的方向。 |
| Human Judgment Note | 人类判断依据与责任人。 |
| Asset Destination | 是否进入 Judgment Asset / Exception Asset / Rule Asset。 |

## 26.13.5 底线

没有人工拒绝路径的人机协同系统，不是真正可控的协同智能系统。Synexa iS 必须在图、文档、流程、系统界面和执行协议中保留人智定向、人智决策、退回修正和责任记录。

## E.1 Visual Personality｜视觉气质

<div class="callout core">

<div class="call-label">

TYPOGRAPHY PRINCIPLE V3.3

</div>

<div>

英文像机器，中文像人；数字像系统，标题像判断。Synexa 的英文主题表达锚定 Space Grotesk，体现清晰、现代、系统化与轻技术气质；中文主题标题锚定思源宋体加粗 / Source Han Serif SC Bold，保持认知基线文件的判断力、可信度与阅读温度。

</div>

</div>

| 对象               | 气质关键词                                | 设计判断                                                                 |

| 英文 / 数字        | Raw Machine / Terminal / System / Precise | 使用 Mono、Condensed、工程感无衬线字体；控制情绪，增强系统感。           |
| 中文大标题         | 判断力 / 认知基线 / 战略感 / 可信         | 使用思源宋体 / Noto Serif CJK 加粗，形成正式、沉稳、带判断力的标题气质。 |

| 数据 / 标签 / 编号 | 机器可读 / 代码感 / 低情绪 / 强秩序       | 使用 Mono 字体，并通过 letter-spacing、字号和灰度建立系统秩序。          |

FONT ANCHOR LOCK
