## 一、工作空间分类体系

Synexa iS 体系下共设六类 AI 工作空间，各有明确的职责边界与触发条件。

| # | 中文名 | 英文代号 | 职能一句话 | SSADS 层级 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | **智核中枢** | `iS-Core` | 基线治理 · 项目孵化与裁决 | L1 · 治理与认知中枢层 |
| 2 | **智权枢纽** | `iS-Hub` | 任务中台 · 跨项目资源与进度协调 | L1 延伸 · 协调调度层 |
| 3 | **枢机经纬** | `iS-SCO` | 推演辅助 · 战略推演与决策支持（N·Grid / EKB） | L2 · 知算善衡层 |
| 4 | **智核矩阵** | `iS-Matrix` | AI 劳动力 · 批量执行与内容生产 | L4 · Digital Employee 层 |
| 5 | **各 PCS 项目** | `iS-[代号]` | 具体项目全生命周期推进 | L5 · 项目落地层 |
| 6 | **智核实验场** | `iS-Lab` | 灵感容器 · 未成熟想法的最小验证场 | L1 前置缓冲层 |

> **注**：超智（Synexa）在业务上是集团总基底，在 PCS 维度以建设项目形式存在（`iS-Synexa`），与其他 PCS 实例平级管理，但战略优先级高于其他实例。

## 二、各工作空间职责边界

### 2.1 智核中枢（iS-Core）· 基线系统

**职责（只做这四件事）**：
1. 识别是否需要新项目（判断触发条件）
2. 完成最小定义（Step 0A 级别：项目名称、一句话定义、层级归位、优先级）
3. 做项目归位（L1 / L2 / L3）
4. 确认优先级（与现有活跃项目的关系与排序）

**停止边界**：
> 一旦完成最小定义，iS-Core 必须立即停止深入讨论，不得在中枢层继续推进该项目的业务细节、执行方案或内容设计。

**触发动作**：
> 最小定义完成 → 立即创建该项目的 PCS → 后续所有推进转移至该项目专属对话组进行。

---

### 2.2 智权枢纽（iS-Hub）· 任务中台

**职责**：
- 识别跨项目的资源重叠、任务冲突或依赖关系
- 做出协调决策（指定由哪个项目统一产出共享资源）
- 管理跨项目的进度节奏与优先级排序

**使用场景示例**：多个 PCS 项目同时需要同一批供应链数据时，由 iS-Hub 裁决由哪个项目统一产出，其他项目引用，避免重复劳动。

> **注**：当前项目数量较少时，iS-Hub 职责可由 iS-Core 兼任，待项目规模扩大后独立启用。

---

### 2.3 枢机经纬（iS-SCO）· 推演辅助

**职责**：
- 战略推演与期望值计算（N·Grid 框架）
- 重大决策的风险揭示与反向验证（RVM）
- 成本对冲量化（CCM）
- 内含 EKB（知算善衡）等具体推演工具

**使用场景**：需要做重大决策、评估新业务可行性、推演竞争格局时调用。

---

### 2.4 智核矩阵（iS-Matrix）· AI 劳动力系统

**职责**：
- 承接批量执行任务（内容生产、数据处理、标准化输出）
- 数字员工矩阵的调度与管理
- 具体任务的高效执行与交付

**使用场景**：需要批量生产内容、执行标准化重复任务、调用具体数字员工时使用。

---

### 2.5 各 PCS 项目（iS-[代号]）· 项目推进

**职责**：
- 单一项目的全生命周期推进（Step 1 → Step 6）
- 项目内所有任务的执行与状态管理
- 项目产出的回写与归档

**当前已立项的 PCS 实例**：

| 项目名称 | 代号 | 当前状态 |
| :--- | :--- | :--- |
| 超智建设 | `iS-Synexa` | 待立项 |
| 智食引擎 | `iS-Nex2U` | Step 3 推进中 |
| 意臻供应链 | `iS-Nexsply` | 待立项 |
| Bella Giornata | `iS-BG` | 持续运营 |

---

### 2.6 智核实验场（iS-Lab）· 灵感容器

**职责**：
- 接住未成熟的想法与业务苗头
- 做最小可行性验证（不超过 Step 0A）
- 判断是否值得提交 iS-Core 正式立项

**停止边界**：
> iS-Lab 不得自行推进任何项目超过最小验证阶段。一旦判断值得立项，必须提交至 iS-Core 完成正式孵化流程。

## 三、越界提示机制

当用户在某个工作空间提出的请求超出该空间的职责边界时，AI 必须暂停执行，输出标准提示：

```
⚠️ 越界提示
你当前的请求「[请求摘要]」超出了本工作空间（iS-[代号]）的职责范围。
建议转移至：iS-[目标代号]（[目标空间名称]）处理。
是否确认在此继续？若确认，本次执行标注为 [非标执行·已越界]。
```

**坚持继续的处理**：AI 执行，但在输出末尾标注 `[非标执行·已越界]`，并在下一次状态回写时记录该事件，供后续流程优化参考。

## 四、工作空间使用决策树

```
我有一个想法 / 任务 / 问题，应该去哪里？

├── 是新想法或新业务苗头，还不确定要不要做
│   └── → iS-Lab（智核实验场）做最小验证
│           └── 验证后值得推进 → 提交 iS-Core 正式立项

├── 需要判断是否立项 / 完成项目最小定义
│   └── → iS-Core（智核中枢）

├── 有具体项目任务要推进
│   └── → 对应的 iS-[项目代号]（PCS 项目组）

├── 多个项目之间有资源冲突或需要协调
│   └── → iS-Hub（智权枢纽）

├── 需要做重大决策 / 战略推演 / 风险评估
│   └── → iS-SCO（枢机经纬）

└── 需要批量执行 / 内容生产 / 调用数字员工
    └── → iS-Matrix（智核矩阵）
```

## 五、跨工作空间协作规则（三条铁律）

1. **iS-Core 是唯一的项目孵化入口**：任何新项目不得绕过 iS-Core 直接在执行层启动。
2. **GitHub 是唯一的状态真实源（SSOT）**：任何工作空间的关键产出必须回写至仓库，不得停留在对话记录。
3. **PCS 是项目的唯一上下文载体**：任何 AI 接入项目前必须先读该项目的 PCS，不得依赖口头交代。

## 六、跨平台指令同步机制

### 6.1 指令文件结构（GitHub SSOT）

```
00-overview/
├── AI_Workspace_Architecture_v1.0.md   ← 本文件（工作空间架构总说明）
├── iS-Core_Instructions.md             ← 智核中枢指令母本
├── iS-Hub_Instructions.md              ← 智权枢纽指令母本
├── iS-SCO_Instructions.md              ← 枢机经纬指令母本
├── iS-Matrix_Instructions.md           ← 智核矩阵指令母本
├── iS-Lab_Instructions.md              ← 智核实验场指令母本
└── iS-[项目代号]_Instructions.md       ← 各 PCS 项目指令母本
```

### 6.2 Manus 侧同步机制

Manus 具备 GitHub 直连能力，Project 指令框只需引用 GitHub 对应文件路径。每次对话自动拉取最新版本，**无需手动更新 Project 指令**。

### 6.3 GPT 侧同步机制

GPT 无法直连 GitHub，采用以下最小人工操作流程：

1. GitHub 每次更新指令文件后，Manus 自动生成"GPT 同步包"（包含需要重新上传的文件清单 + 文件内容）
2. 用户在 GPT 对应 Project 知识库中替换上传对应文件（每次操作约 1-2 分钟）
3. 所有指令文件带版本号，AI 接入时必须报告当前读取的版本号
4. 若 GPT 侧版本低于 GitHub 最新版本，AI 必须提示"当前指令版本滞后，请更新知识库文件"

### 6.4 版本漂移防护

- 所有指令文件均有版本号（格式：`V.年份后两位.月.序号`）
- AI 每次接入必须在"当前状态确认"中报告所读取的指令版本号
- 版本不一致时，AI 不得静默执行，必须明确提示
