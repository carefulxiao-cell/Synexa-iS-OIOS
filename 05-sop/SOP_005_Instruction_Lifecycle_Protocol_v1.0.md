# SOP_005：指令生命周期管理协议 (Instruction Lifecycle Protocol)

**版本**：v1.0
**适用范围**：Synexa iS 全局（含 Core、各 PCS 项目组、超智等所有子系统）
**执行主体**：策略室（iS-SCO）、用户（User）、执行框（V2/V3等）

---

## 1. 协议背景与目的

在多智能体协同开发中，指令的下发、执行、验收与废弃如果缺乏标准流程，极易导致：
- **状态混乱**：执行框不知道以哪个版本的指令为准。
- **沟通断层**：策略室与执行框无法直接对话，导致指令悬停。
- **历史包袱**：被推翻的旧指令残留在代码库中，干扰后续开发。

**目的**：建立一个从「需求对齐」到「执行归档」的标准化闭环流程，确保指令流转清晰、状态透明、废弃果断。

---

## 2. 指令生命周期全景图

指令的完整生命周期包含 9 个标准动作：

`对齐 → 生成 → 审核 → 入仓 → 下发 → 执行 → 反查 → 完成 → 整理`

### 2.1 详细流转步骤

| 阶段 | 动作说明 | 执行方 | 产出物 / 状态变更 |
|------|----------|--------|-------------------|
| **1. 对齐** | 用户与策略室在对话中明确任务目标、边界、设计共识。 | 用户 + 策略室 | 对话共识记录 |
| **2. 生成** | 策略室按 `SOP_003` 格式生成指令包文档。 | 策略室 | `xxx_Instruction_V1.0.md` |
| **3. 审核** | 用户确认指令包内容无误。 | 用户 | 确认信号 |
| **4. 入仓** | 策略室将指令包推送至 GitHub，并更新 `INSTRUCTION_TRACKER.md`。 | 策略室 | 状态变更为「⏳ 待执行」 |
| **5. 下发** | 用户将指令包转发给执行框，附标准触发话术。 | 用户 | 执行框收到任务 |
| **6. 执行** | 执行框拉取代码、实施开发、提交报告（按 `SOP_003` 格式）。 | 执行框 | 代码 commit + 提交报告 |
| **7. 反查** | 用户将报告转给策略室，策略室验收代码与报告。 | 用户 + 策略室 | 验收结论 |
| **8. 完成** | 策略室更新 `INSTRUCTION_TRACKER.md`，附上 commit hash。 | 策略室 | 状态变更为「✅ 已完成」 |
| **9. 整理** | 策略室定期审查汇总表：废弃冲突项、合并重复项、通报全局状态。 | 策略室 | 更新后的汇总表 |

---

## 3. 标准触发话术（下发约定）

由于策略室与执行框无法直接通信，**第 5 步（下发）** 必须由用户手动触发。

**用户发给执行框的标准话术**：
> 请拉取 `[仓库地址]` 最新代码，执行以下指令包：`docs/[指令包文件名]`，完成后按 SOP_003 格式提交报告。

---

## 4. 指令废弃与替代协议 (Supersede Protocol)

当新的设计共识推翻了尚未执行的旧指令时，**必须**执行废弃流程，严禁在 GitHub 上保留相互冲突的指令文档。

**废弃标准流程**：
1. **识别冲突**：策略室在汇总表中标注旧指令为「⚠️ 待废弃」。
2. **确认废弃**：用户确认后，正式启动废弃。
3. **物理删除**：策略室从 GitHub 仓库的 `docs/` 目录中**彻底删除**旧指令包文档。
4. **状态标记**：策略室在 `INSTRUCTION_TRACKER.md` 中将旧条目移至「⏸️ 已驳回 / 暂缓」区块，并标记为「🚫 已废弃（被 XXX 替代）」。
5. **生成新指令**：策略室生成包含最新共识的替代指令包，并推送入仓。

**核心原则**：GitHub 上不留废弃文档，汇总表保留废弃记录（可追溯），执行框只看到有效指令。
