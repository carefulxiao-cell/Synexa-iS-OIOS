## 2. 图01｜总体生态与系统能力架构：锁定内容

### 核心定位

以“真实经营事实 + 菜单与产品组织 + 采购生产服务执行 + 经营反馈”为主闭环；由两个数智引擎、共用对象与规则体系、人机受控进化机制共同构成。

### 双数智引擎

| 引擎 | 责任边界 | 关键产出 |
|---|---|---|
| 经营数据数智引擎 | 原始事实采集、标准化、对账、计算、追溯、经营分析；不覆盖原始值 | 标准化事实、对账差异、计算结果、数据血缘、经营洞察 |
| 菜单与运营数智引擎 | 场景菜单、产品组合、预测、采购、库存、生产、排工、配送、反馈的业务编排；不以分析结果替代事实 | 菜单版本、需求计划、生产计划、MRP、执行任务、履约反馈 |

### 四大业务域

1. 需求与产品；
2. 采购与生产；
3. 履约与服务；
4. 财务与经营。

### 六层系统能力

1. 数据接入；
2. 主数据与规则；
3. 事实与计划；
4. 业务执行；
5. 智能分析；
6. 人机交互。

### 三项横贯能力

1. 数据治理与血缘；
2. 权限、版本与审计；
3. AI 协同与受控学习。

### 责任分工（候选）

| 角色 | 本轮定义 |
|---|---|
| Kimi | 事实整理、母表/对象核验、差异标注；不批准业务规则 |
| ChatGPT | 策略、业务架构、分析、任务指令；不替代专业审核 |
| Manus | 系统工程、技术架构、MVP 实现；不自行确认业务事实或专业参数 |
| 专业人员 | 专业审核、业务事实确认、授权、例外裁决与正式生效 |
| 项目主基线 / 专项总控 | 版本、资产、责任与决策记录的上位接口 |
| 未来 04 系统专项 | 技术架构、数据模型、接口、权限和 MVP 的承接接口；本轮仅预留 |

## 3. 图02｜核心对象与 SKU 关系架构：锁定内容

### 对象与关系规则

| 关系 | 基数 / 约束 |
|---|---|
| `Scene` ↔ `Menu Slot` | 多对多，经“场景化档位配置”承载排序、必选性、容量、适用期等范围规则 |
| `Menu Version` → `Menu Slot` → `可售项` | 菜单是范围和有效期下的编排；产品本体不等于菜单项 |
| `Product` → `Variant` | 一对多；变体承接口味、份量、适配人群、工艺或营养差异 |
| `Variant` → `Sales SKU` | 一对多候选；包装、规格、渠道、定价、履约可不同 |
| `Set Meal` ↔ `Sales SKU` | 多对多，经套餐组成保存数量、必选/可选、替换组、加价、生效期 |
| `Variant` ↔ `Recipe Version` | 多对多，经适用关系保存范围、优先级、生效期 |
| `Recipe Version` → `BOM Line` → `Ingredient` | 配方版本有多条 BOM 行；BOM 为投入/用量/损耗/替代关系 |
| `Recipe Version` ↔ `SOP / Quality Standard` | 引用已批准版本；工序与质量标准不可默认一对一 |
| `Ingredient` ↔ `Procurement SKU` | 多对多，经转换规则保存净含量、计量、出成率/可食率、等级、替代条件 |
| `Supplier` ↔ `Procurement SKU` | 多对多，经供应商供货项/报价合同保存价格、最小订购量、交期、有效期 |
| `Procurement Channel` ↔ `Supplier Offer` | 多对多候选；渠道不等同供应商 |
| `Meal Order` ↔ `Demand Plan` | 多对多，经需求归集/分摊承载；预测、确认需求和订单事实必须区分 |
| `Demand Plan` ↔ `Production Batch` | 多对多，经生产分配承载计划量、批次量、优先级、调整原因 |
| `Production Batch` ↔ `Inventory Batch` | 多对多，经领料/产出/退料/报损事件承载；批次保留配方、BOM、SOP、质量标准版本快照 |
| `Supplier PO` → `PO Line` → `Procurement SKU` | 下 PO、收货、验收、入库、对账是不同事实和状态 |

### 共享、范围与继承

- 共享产品能力池、食材、基础配方与基础标准可复用；
- 场景、院区、厨房、服务点、渠道等范围配置应表达“继承—覆盖—禁用”；
- 控糖餐、月子餐、专家餐、围餐等应继承适用的通用产品能力和专业/场景规则，不预设独立产品库；
- 已发生订单、需求、生产、采购、收货、配送须保留当时受控版本快照，不可被后续改版静默覆盖。

## 4. 图03｜业务工作链与受控进化流程：锁定内容

### 主工作链

`每周全部启用场景的菜单计划包` → 菜单生成 → 专业审核 → 发布 → 餐食需求合并与预测 → 生产计划 → 物料需求 → 供应商采购下单 → 验收入库 → 出库领料 → 排产排工 → 生产检查 → 配送销售 → 结算成本 → 复盘优化。

### 四类受控版本

1. 菜单版本：草稿 / 待专业审核 / 已批准 / 已发布或待生效 / 生效中 / 已替代；
2. 需求版本：预测中 / 待确认 / 已确认 / 已冻结 / 执行中 / 已完成；
3. 生产版本：草拟 / 审核 / 已批准 / 已冻结 / 生产中 / 待质检 / 已放行或返工/报废；
4. 采购与库存执行版本：请购 / 审批 / PO 已下达 / 供应商确认 / 收货验收 / 入库或退货 / 领料或退料 / 对账关闭。

### 核心门禁

- 已发布的菜单是“可供选择/备选菜单池”，不等于生产指令；
- 只有“已确认需求 + 已批准/冻结生产计划”可驱动 MRP、采购与生产；
- 单场景修改须回到需求汇总层重算总餐数、共享/专用食材、产能、工时、路线、预算和成本差异；
- 共享采购与专项采购必须分别标识、授权与归集；
- 系统规则验证和专业主源/经营指标验证任何一项不通过，都不得自动放行；
- 实际结果只能形成优化候选，经人工审核后才形成下一版本草稿；
- 异常须经过受控通道：编号、影响评估、临时授权、补救动作、事后复盘。

## 5. 关联矩阵：锁定维度

列：业务能力 × 数据对象 × 工作节点 × 系统能力 × 责任角色 × 权威主源。  
行以“需求与菜单、产品与对象、采购与库存、生产与质量、履约与服务、财务与经营、治理与进化”七个能力域组织。

---

## 6. 结构冲突、缺口与审核重点

1. `场景 / 菜单 / 档位 / 餐次`语义边界需专项核定；
2. `产品 / 变体 / 售卖 SKU / 套餐`不可继续以“菜品”单一对象混用；
3. `预测 / 需求计划 / 订单`与`生产计划 / 生产批次`须分别建模；
4. `食材 / 采购 SKU / 库存`须分开；库存应体现地点、批次、效期、质量状态与可用量；
5. 菜单、需求、生产、采购库存须建立版本谱系、冻结点、审批记录与历史快照；
6. 地址/路线主数据、点餐系统/代码入口、营收损益细表、采购换算/出成率与真实岗位/授权仍是关键待核接口；
7. 104 个结构点 / 141 个产品 SKU 仅由 Kimi 对照实际母表后再定义与编码；
8. 首批不得承诺自动发布、自动采购、自动替代、自动放行或自动写回专业规则。

---

## 7. 审核顺序

1. 业务架构主责方：核对语义、关系、边界与责任；
2. Kimi：核对数据对象、实际母表、数量、名称与口径；
3. Manus：将经确认的版本转化为技术架构、MVP 范围与接口设计。
