# Synexa iS · 全局指令同步协议 (ISYNC Protocol)

> **版本**：v1.1 (新增 TBF 三态核查与执行框门禁机制)
> **更新时间**：2026-04-17
> **定位**：Synexa iS 体系内所有工作空间（对话组）的指令归集与审查标准协议。
> **核心原则**：一处定义，全局生效。各工作空间仅需配置触发词，无需理解协议细节。

---

## 1. 协议目标

解决多工作空间并行运作时的“指令散落”、“版本遗忘”与“代码/指令脱节”问题。通过建立**分级指令汇总机制**，实现：
1. **指令可追溯**：所有对话组的历史指令按时间线完整留存。
2. **完成度可核查**：通过指令与代码的交叉比对，防止 AI 幻觉与功能遗漏。
3. **状态全局可视**：在中央仓形成全体系的指令健康度视图。
4. **执行门禁控制**：通过 TBF 三态核查机制，确保代码提交与生产环境验证的强制一致性。

---

## 2. 分级指令汇总机制 (Hierarchical Instruction Sync)

为彻底解决指令悬空与丢失问题，ISYNC 协议确立三级汇总架构：

| 层级 | 汇总载体 | 触发时机 | 责任方 |
| :--- | :--- | :--- | :--- |
| **L1 项目/任务级** | 各项目 `docs/` 下的指令包文件 | **立即归档**：每次下发指令包时，必须同步推送至 GitHub | 各 PCS 工作空间 |
| **L2 工作空间级** | `06-isync/iS-[工作空间]_ISYNC.md` | **被动触发**：收到 `汇总指令` 时，读取 L1 文件聚合写入 | 各工作空间 |
| **L3 全局体系级** | `CONTEXT_OS.md` 决策日志 | **事件触发**：Core 做出重大裁决后立即回写 | iS-Core |

**核心基线规则（L1 强制归档）**：
任何工作空间在下发新的指令包、达成新的开发共识时，**必须在产生的那一刻立即将其保存为 Markdown 文件并推送至 GitHub 对应项目目录**。未推送到 GitHub 的指令视为"未生效"，严禁仅停留在聊天记录中。

## 3. 目录结构与文件规范

L2 级指令同步文件统一存放在 `carefulxiao-cell/Synexa-iS-OIOS/06-isync/` 目录下。

### 2.1 总索引文件 (`_ISYNC_INDEX.md`)
记录所有已接入 ISYNC 协议的对话组清单、对应文件路径及最后同步时间。

### 2.2 项目指令文件 (`[项目代号]_ISYNC.md`)
每个独立立项的对话组拥有一个专属文件，包含：
*   **基础信息**：项目代号、名称、当前生效指令版本。
*   **指令记录区**：按时间倒序排列的历史指令记录（包含系统提示词、执行指令、补丁指令）。
*   **审查记录区**：历次“全面审查”的结论摘要。

## 4. 触发词与标准执行序列 (SOP)

各工作空间 Agent 在收到以下触发词时，必须严格执行对应的标准序列。

### 触发词一：`汇总指令`

**适用场景**：任意对话组，在完成一轮重要对话、修改了系统提示词或下发了关键指令后触发。

**执行序列**：
1.  **收集**：将本次对话中所有已使用的指令（系统提示词、执行指令、补丁指令）按时间顺序整理。
2.  **格式化**：附上版本号（如适用）、触发时间、执行结果摘要。
3.  **写入**：追加写入中央仓 `06-isync/[项目代号]_ISYNC.md` 的「指令记录区」。
4.  **更新索引**：更新 `06-isync/_ISYNC_INDEX.md` 中本项目的最后同步时间。
5.  **提醒**：在回复末尾附加标准 GPT 同步提醒。

### 触发词二：`全面审查 [项目代号]`

**适用场景**：任意对话组，建议在版本交付前、TBF 核查前或定期维护时触发。

**执行序列**：
1.  **读取基线**：读取 `06-isync/[项目代号]_ISYNC.md`，获取全量历史指令清单。
2.  **读取现状**：读取该项目代码仓库（如 `carefulxiao-cell/nexflow`）中的实际文件结构与功能现状。
3.  **交叉比对**：逐条比对“指令要求了什么” vs. “代码实际实现了什么”。
4.  **输出报告**：输出三栏审查报告：
    *   ✅ **已完成**（指令与代码一致）
    *   🟡 **部分完成**（代码存在但不完整）
    *   ❌ **未落地**（指令有记录，代码中找不到对应实现）
5.  **回写结论**：将审查结论回写至 `[项目代号]_ISYNC.md` 的「审查记录区」。

## 5. TBF 三态核查机制（核心门禁）

为解决执行框“表面通过、实际失败”的问题，所有接入 ISYNC 协议的项目，其 TBF（任务目标基线文件）必须强制执行三态核查机制。

### 4.1 三态定义与处理逻辑

| 状态 | 定义 | 处理逻辑 |
|------|------|------|
| ✅ **TBF 通过** | 代码已提交至主分支，且**生产环境端到端验证通过**。 | 解锁下一阶段指令包。 |
| ⚠️ **TBF 待验证** | 代码已提交，但生产环境尚未验证或验证不完整。 | **强制阻断**：不允许执行下一指令包，必须优先完成生产验证。 |
| ❌ **TBF 未通过** | 代码已提交，但生产环境验证失败（如数据库结构不一致、功能报错）。 | **强制打回**：返回执行框修复，不计入完成进度。 |

### 4.2 强制验证标准

TBF 的核查不能仅停留在代码层（如“测试用例通过”），必须包含**生产环境的实际状态感知**：
1. **数据库实际状态**：必须在生产数据库执行 `SHOW COLUMNS` 等命令，确认实际表结构与代码 Schema 完全一致。
2. **端到端功能**：必须在生产环境实际操作核心链路，并提供截图或明确的验证说明。

## 6. 工作空间接入指南

任何新立项的对话组，只需在其系统提示词（System Prompt）或项目指令（Project Instructions）中加入以下段落，即可完成接入：

```markdown
【ISYNC 协议】
本工作空间已接入 Synexa iS 全局指令同步协议（ISYNC）。
- 收到「汇总指令」时：执行指令归集序列，推送至中央仓。
- 收到「全面审查 [本项目代号]」时：执行指令与代码完成度比对审查序列。
- **L1 强制归档**：每次下发新指令包或达成新共识，必须立即保存为文件并推送至 GitHub 项目目录，否则指令不生效。
- 严格执行 TBF 三态核查门禁，未达「✅ TBF 通过」状态前，禁止推进下一阶段。
协议定义详见：carefulxiao-cell/Synexa-iS-OIOS/00-master/ISYNC_PROTOCOL.md
```
