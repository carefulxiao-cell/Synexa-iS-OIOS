# Synexa Collaboration Router Execution Principles

> Version: v0.1.2  
> Effective Date: 2026-06-10  
> Maintainer: iS-Matrix  
> Use: Operating principles for cross-workspace collaboration

## 1. 不因越界而停摆

越界不是停止工作的唯一理由。

当任务跨空间时，当前空间应先完成自己最擅长、最有价值、最符合职责的部分，再生成交接任务包。

## 2. 不冒充全能

任何工作空间都不得假装自己可以同时完成战略、裁决、生产、执行、代码、仓库和回流。

协同的前提是承认边界。

边界清楚，协同才有力量。

## 3. 当前空间先完成最有价值部分

当前空间必须问：

- 我能合法完成什么？
- 我完成什么能让下游少走弯路？
- 我不能完成的部分应该交给谁？

例如：

- iS-Matrix 应先完成模板、SOP、Skill 源文件草案。
- iS-SCO 应先完成策略判断与风险推演。
- PCS 应先完成项目任务拆解与执行状态。
- iS-Core 应先完成基线与主责判断。

## 4. 每次协同必须有主责

协同不是多人围观。

每次协同必须指定一个 main owner。

可以有多个 collaborators，但只能有一个 main owner。

## 5. 交接必须带上下文

不能只说“交给 Manus”。

必须说明：

- 用户原始意图
- 当前空间已完成内容
- 下游要做什么
- 输出格式
- 文件路径
- 校验要求
- 回流要求

没有上下文的交接，是把问题转嫁给下游。

## 6. 协同结果必须回流

下游完成后，必须回流：

- 完成了什么
- 哪些地方卡住
- 哪些上游判断不清
- 哪些模板需要修补
- 是否需要 iS-Core 裁决
- 是否需要 GitHub 更新

没有回流，系统不会进化。

## 7. 实战案例必须可补丁化

每次实战中暴露的问题，都应形成轻量 patch opportunity。

不要追求一次完美。

要追求每次更准一点。

## 8. 保持轻量，避免流程怪兽

协同路由器的价值是减少混乱，不是制造表格迷宫。

原则：

- 小任务少字段
- 标准任务完整字段
- 系统级任务才写 case log 和 patch note
- 不为一次性琐事制造重流程

## 9. 先路由，再生产

当任务明显跨空间时，先判断路由，再进入生产。

否则容易出现：

- iS-Matrix 偷做战略
- iS-SCO 偷做 SOP
- PCS 偷做基线裁决
- iS-Core 陷入项目细节

## 10. 产物必须可交给下游直接执行

所有 handoff package 和 agent prompt 都应满足：

- 下游不用重新猜目标
- 下游不用重新问背景
- 下游知道完成标准
- 下游知道回流格式

## 11. Core 不承接执行细节

iS-Core 是基线治理与裁决入口，不是所有协同任务的总执行办公室。

除非涉及以下事项，否则不应提交 iS-Core：

- 基线变更
- 全局协议
- 项目立项
- 职责重构
- 优先级冲突
- 跨空间冲突裁决

能由主责空间解决的协同执行问题，应在主责空间完成。
