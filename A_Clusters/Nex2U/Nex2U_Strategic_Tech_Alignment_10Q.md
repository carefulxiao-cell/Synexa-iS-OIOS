# Nex₂U 战略与技术深度对齐文档（十问十答）

> **文档定位**：针对当前系统现状、架构重构、引擎接入、开发规划等核心问题的深度对齐与解答。
> **目标**：在正式启动代码开发前，彻底理清“为什么做”、“做什么”、“怎么做”、“怎么评估”，确保全线全栈认知一致。

## 1. 现有后端数据结构为何未对齐六大数据库？

**现状说明**：
现有的后端（`hospitalapp-edldi6mw.manus.space`）是一个“点餐系统”的壳。它的底层数据表是围绕“商品（菜品）”、“订单”、“用户”来设计的，这是典型的电商逻辑。

**未对齐的原因**：
它没有建立“营养结构点（P·C·V·E·PR）”、“餐型母型”、“主题场景”等维度的表结构。在现有系统中，一道菜只是一个带有价格和图片的商品，而不是由“蛋白质+碳水+烹饪工艺”动态组合而成的结构化产物。因此，它无法支撑“结构驱动生成”的业务目标。

## 2. 核心引擎（Nex₂U）为何完全缺失？

**现状说明**：
现有系统只有前端展示（Nufō³ 的雏形）和后端管理（NuBō 的雏形），中间缺少了负责计算和规则匹配的“大脑”。

**缺失的原因**：
之前的开发重点在于“跑通点餐和支付流程”，即解决“怎么卖”的问题。而 Nex₂U 引擎解决的是“怎么配”、“怎么算”的问题。没有引擎，系统就只能人工录入固定菜单，无法实现基于 28 个场景和 90 个营养点的动态智能生成。

## 4. 从零搭建 vs 原有架构：差异与评估标准

### 4.1 核心差异对比

| 维度 | 原有架构（点餐系统） | 新架构（Nex₂U 引擎系统） |
| :--- | :--- | :--- |
| **驱动方式** | 商品驱动（人工录入菜品） | 结构驱动（规则+营养点动态生成） |
| **数据模型** | 扁平化（菜品-订单） | 立体化（场景-母型-营养点-食材-工艺） |
| **扩展性** | 仅限点餐，难以扩展 | 预留具身智能接口，可扩展至多场景 |
| **核心价值** | 交易工具 | 知识资产与规则资产的沉淀平台 |

### 4.2 架构评估与查验维度（5个维度）

1.  **数据解耦度**：菜品是否被拆解为可独立计算的营养点和工艺？
2.  **规则可配置性**：新增一个主题场景，是否只需配置规则而无需改代码？
3.  **接口标准化**：引擎层是否提供标准 API，允许任何前端（H5、小程序、甚至机器人）调用？
4.  **性能与并发**：在大量规则计算时，引擎的响应时间是否达标？
5.  **数据闭环**：履约数据是否能回流至引擎，优化下一次的生成规则？

### 4.3 阶段性扫描与校正标准

*   **设计期**：ER 图是否完整覆盖六大数据库？API 契约是否清晰？
*   **开发期**：每周 Review 核心接口的输入输出是否符合 Master Doc 定义。
*   **测试期**：输入特定场景和约束，引擎生成的餐食方案是否符合营养逻辑。

## 5. 平台核心构成与工作原理

一个完整的 Nex₂U 平台包含以下核心层级：

1.  **UI 层（Nufō³）**：用户交互界面（H5/PC）。负责展示场景、收集用户约束（如忌口）、呈现生成的餐食方案。
2.  **API 层（网关）**：前后端通信的桥梁。负责鉴权、请求路由、数据格式转换。
3.  **引擎层（Nex₂U）**：核心大脑。包含规则解析器、营养计算器、方案组合器。
4.  **数据层（Schema）**：底层存储。包含六大核心数据库（主题、母型、营养点、工艺、食材、菜单）。
5.  **执行层（NuBō）**：运营与履约后台。负责供应链调度、厨房生产指令下发。

**工作原理（数据流）**：
用户在 UI 层选择“高蛋白早餐（T04）” -> API 层将请求发给引擎层 -> 引擎层查询数据层，获取 T04 的规则和可用营养点 -> 引擎层动态组合出符合规则的餐食方案 -> 返回给 UI 层展示 -> 用户确认后，指令下发至执行层进行生产。

## 6. 核心引擎的接入方式与风险

**接入方式**：
引擎应作为一个**独立的微服务（Microservice）**存在，通过 RESTful API 或 gRPC 与前端和运营后台通信。

**工作原理**：
输入（场景ID、用户约束） -> 引擎内部黑盒计算（匹配母型、筛选营养点、组合食材） -> 输出（结构化的餐食方案 JSON）。

**风险点**：
*   **规则冲突**：当多个约束条件叠加时，可能导致无解（算不出符合条件的餐食）。
*   **性能瓶颈**：复杂的组合计算可能导致接口响应过慢。

**最佳接入时机与步骤**：
1.  **先定义契约**：在写引擎代码前，先定好 API 的输入输出格式。
2.  **Mock 接入**：前端先用假数据（Mock）对接，不依赖引擎的实际开发进度。
3.  **核心逻辑跑通**：引擎先实现最基础的 1-2 个场景的计算逻辑。
4.  **联调与灰度**：前后端真实对接，先在内部测试环境跑通，再逐步放开场景。

## 7. 数据结构对齐的优势与风险

**优势**：
*   **降维打击**：将复杂的餐饮经验转化为机器可读的结构，实现真正的数字化。
*   **高度复用**：一个营养点可以在无数个场景中被复用，极大降低边际成本。

**风险**：
*   **前期设计成本高**：需要花费大量时间梳理和定义表结构，短期内看不到“界面”。
*   **过度设计**：如果把结构拆得太细，会导致数据库查询极其复杂，影响性能。

**可行性影响因素**：
取决于我们对“营养结构点”和“工艺规则”的定义是否足够清晰、互斥且穷尽（MECE 原则）。

## 8. 部署环境：后端管理转为前端类似？

**解答**：
是的，完全可以。
目前的后端管理（`hospitalapp-edldi6mw.manus.space`）部署在 Manus 的临时沙盒中。为了保证稳定性和安全性，后端管理平台（NuBō）的**前端页面**应该和 C 端点餐页面（Nufō³）一样，部署在正式的云服务器或对象存储（如阿里云 OSS + CDN）上，绑定正式域名。
而**后端 API 服务和数据库**，则部署在云服务器（ECS）上。这是标准的生产级前后端分离部署方案。

## 10. 核心任务提炼与推进规划总结

### 10.1 核心任务（The Core Mission）
**构建 Nex₂U 结构驱动引擎，并以此为核心重构现有点餐系统，落地“新一代优质饭堂”MVP。**

### 10.2 核心要点提炼（The Key Principles）
1.  **结构先行**：无 Schema 不写代码，无 API 契约不对接。
2.  **引擎独立**：Nex₂U 必须是独立的计算服务，不与 UI 逻辑耦合。
3.  **数据闭环**：从场景到营养点，再到履约，数据必须结构化流转。
