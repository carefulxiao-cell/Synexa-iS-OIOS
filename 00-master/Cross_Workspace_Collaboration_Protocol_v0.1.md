## 一、协议目的

本协议用于解决 Synexa iS 体系在跨工作空间任务执行中出现的以下五类问题：

1. **职责边界模糊**：单一工作空间被要求同时承担战略推演、SOP 生产、项目执行、基线裁决等多类任务，导致越界执行或职责混淆。
2. **协同编排缺失**：多个工作空间参与同一任务时，缺乏统一的触发判断、主责认定和协作顺序规范，导致重复劳动或关键环节遗漏。
3. **交接任务包不规范**：工作空间之间的任务移交依赖对话记录或口头描述，缺乏结构化的交接载体，导致下游接收方无法准确还原上游意图。
4. **回流反馈机制缺失**：下游完成任务后，校准意见、补丁建议和执行偏差无法系统性回流至上游，导致体系无法从实战中持续迭代。
5. **版本补丁无法追踪**：协议本身缺乏版本管理机制，每次实战经验无法沉淀为可复用的协议修订依据。

> **核心原则：越界不是职责错误，而是跨工作空间协同的触发信号。**

---

## 二、适用范围

本协议适用于以下所有工作空间、智能体与项目组：

### 2.1 Synexa iS 内部工作空间

- **iS-Core**：全局基线治理中枢，负责项目立项、基线裁决与协议维护
- **iS-Hub**：外部工具、Agent 案例研究与技术情报中心
- **iS-SCO**：战略推演、竞争分析与决策支持中心
- **iS-Matrix**：SOP、模板、提示词与数字员工指令生产中心
- **iS-Lab**：新想法最小验证与实验性探索空间
- **各 PCS 项目组**：具体项目的执行与推进空间（如 iS-Synexa PCS、iS-Nex2U PCS 等）

### 2.2 智能体执行体

- **Manus**：代码执行、文件生成、仓库操作、网页构建
- **GPT**：深度推演、长文档生产、知识整合
- **Kimi**：长文档处理、中文内容生产
- **Kimi Claw / Claude Code 类执行体**：代码生成、技术实现、自动化脚本
- **后续所有内部或外部智能体**：凡接入 Synexa iS 体系的智能体，均受本协议约束

## 三、触发条件

当用户在单一工作空间提出的任务，同时包含以下**两类或两类以上**内容时，本协议自动触发：

1. 战略判断（方向选择、优先级排序、竞争分析）
2. 决策推演（情景模拟、路径比较、风险评估）
3. 外部案例研究（竞品分析、行业对标、工具调研）
4. SOP / 模板 / 提示词生产（可复用资产的创建与固化）
5. 具体项目执行（某 PCS 项目的推进动作）
6. 基线裁决（影响全局认知基线的判断与决策）
7. 工具开发 / 代码执行（技术实现、自动化、系统搭建）
8. 资产归档 / GitHub 更新（文件写入、版本管理、仓库操作）

**触发后的第一动作**：当前工作空间不得直接拒绝，也不得冒充全能独立完成全部任务，而应执行「协同分级判断」。

---

## 四、协同分级

根据越界程度，将跨空间协同需求分为四个等级：

### A 类：轻微越界

- **判断标准**：任务主体属于当前空间，仅有少量内容属于其他空间职责，且不影响当前空间的核心输出质量。
- **处理方式**：当前空间先完成全部内容，并在输出中明确标注「本部分归属 [目标空间]，建议同步至该空间存档」。
- **是否需要交接任务包**：不强制，但建议附注。

### B 类：结构越界

- **判断标准**：任务涉及两个或两个以上空间的核心职责，当前空间无法独立完成，或独立完成会导致质量严重下降。
- **处理方式**：当前空间完成本空间最有价值的部分，并生成**跨空间交接任务包**，明确移交目标空间和协作顺序。
- **是否需要交接任务包**：必须生成。

### C 类：执行越界

- **判断标准**：任务的核心执行动作（代码运行、文件生成、仓库操作、系统部署）超出当前空间能力边界，必须由执行型智能体（Manus / Claude Code / Kimi Claw 等）承接。
- **处理方式**：当前空间完成策略层、指令层或规范层的输出，生成**执行交接任务包**，移交执行体。
- **是否需要交接任务包**：必须生成。

### D 类：基线越界

- **判断标准**：任务涉及对全局认知基线、体系架构定义、命名规范、协议条款或核心原则的修改或裁决。
- **处理方式**：当前空间可提供分析建议，但**不得自行裁决**，必须生成**基线裁决提交包**，提交 iS-Core 处理。
- **是否需要交接任务包**：必须生成，且必须等待 iS-Core 回复后方可继续。

---

## 五、主责空间判断规则

当任务触发跨空间协同后，按以下规则判断主责空间：

- **战略推演、方向判断、竞争分析** → 主责：**iS-SCO**
- **SOP / 模板 / 数字员工指令 / 提示词生产** → 主责：**iS-Matrix**
- **具体项目推进、里程碑执行** → 主责：**对应 PCS 项目组**
- **外部工具调研、Agent 案例研究、技术情报** → 主责：**iS-Hub**
- **新想法最小验证、实验性探索** → 主责：**iS-Lab**
- **基线裁决、新项目立项、协议修订** → 主责：**iS-Core**
- **代码执行、文件生成、仓库操作、系统部署** → 主责：**Manus / Claude Code / Kimi Claw 等执行体**

**判断优先级**：当任务涉及多个空间时，以「最终产出物的归属」作为主责判断依据，而非任务的起点。

## 六、当前空间处理原则

当前工作空间在识别到跨空间协同需求后，须遵循以下六条处理原则：

1. **不直接拒绝**：不以「超出职责范围」为由拒绝响应，而是明确说明当前空间可完成的部分。
2. **不冒充全能**：不在未获授权的情况下独立完成全部任务，尤其不得替代 iS-Core 做基线裁决，不得替代执行体做代码部署。
3. **先完成当前空间最有价值的部分**：识别任务中属于当前空间核心职责的内容，优先完成，确保用户在本轮对话中获得实质性产出。
4. **明确标注需移交部分**：在输出中以「⚡ 移交建议」标注需要其他空间处理的内容，说明移交目标和原因。
5. **生成交接任务包**：按本协议第七节模板，生成结构化的跨空间交接任务包，确保下游空间能够准确还原上游意图。
6. **要求下游生成回流反馈包**：在交接任务包中明确要求下游空间在完成任务后，按本协议第八节模板生成回流反馈包，并返回当前空间或 iS-Core。

## 七、跨工作空间交接任务包模板

以下为标准交接任务包格式，生成后可直接在对话中传递或存入 GitHub。

---

```
# 跨工作空间交接任务包

## 基本信息
- 任务名称：[简洁描述本次任务]
- 生成时间：[YYYY-MM-DD]
- 生成空间：[当前工作空间名称，如 iS-SCO]
- 目标空间：[接收方工作空间名称，如 iS-Matrix]

## 用户原始意图
[用一到三句话还原用户在本轮对话中的真实需求，不加解读，不加判断]

## 当前空间判断
[说明当前空间对本任务的理解：任务性质、涉及的职责类型、识别到的跨空间需求]

## 协同触发原因
[说明为何触发本协议：属于哪一分级（A/B/C/D），越界的具体内容是什么]

## 主责空间
[目标空间名称及判断依据]

## 协作空间
[如涉及多个空间，列出所有协作空间及其分工]

## 已完成内容
[列出当前空间在本轮已完成的具体产出，可附文件路径或内容摘要]

## 请下一空间完成
[明确列出需要目标空间完成的具体任务，条目化，可执行]

## 输出要求
[说明目标空间的输出形式：文件格式、存储路径、命名规范、质量标准]

## 回流要求
[说明目标空间完成后，需要按第八节模板生成回流反馈包，并返回至何处（当前空间 / iS-Core / GitHub）]
```

## 八、回流反馈包模板

以下为标准回流反馈包格式，由下游空间在完成任务后生成并返回。

---

```
# 跨工作空间回流反馈包

## 基本信息
- 对应任务名称：[与交接任务包中的任务名称一致]
- 生成时间：[YYYY-MM-DD]
- 生成空间：[本空间名称]
- 回流目标：[上游空间名称 / iS-Core]

## 本次接收任务
[简述从交接任务包中接收到的任务内容]

## 实际完成内容
[列出本空间实际完成的产出，含文件路径、内容摘要或关键结论]

## 发现的问题
[列出执行过程中发现的问题：信息缺失、逻辑矛盾、执行障碍、预期偏差等]

## 对上游判断的校准意见
[对上游空间在交接任务包中的判断提出校准建议：哪些判断准确，哪些需要修正，原因是什么]

## 对模板 / SOP 的补丁建议
[如本次执行中发现现有模板或 SOP 存在不足，提出具体补丁建议，说明修改位置和修改内容]

## 是否建议提交 iS-Core 裁决
- [ ] 否，本次任务已在空间内闭环
- [ ] 是，建议提交 iS-Core，原因：[说明原因]

## 是否建议更新 GitHub 文件
- [ ] 否
- [ ] 是，建议更新以下文件：
  - 文件路径：[路径]
  - 更新内容：[简述]
```

## 九、实战案例：超智官网全球顶级视觉系统提示词

本案例为本协议的首个实战触发案例，完整还原跨工作空间协同流程。

### 9.1 任务背景

用户在 iS-SCO 工作空间提出：为超智（Synexa）官网构建「全球顶级视觉系统提示词」。该任务同时涉及视觉战略推演（iS-SCO 职责）、提示词与 SOP 生产（iS-Matrix 职责）、官网设计落地执行（iS-Synexa PCS 职责），以及可能的品牌基线裁决（iS-Core 职责）。

协同分级判断：**B 类（结构越界）**，需生成跨空间交接任务包。

---

### 9.2 完整协同流程

**Step 1 · iS-SCO：完成视觉战略推演**

- 完成内容：全球顶级科技品牌视觉系统对标分析、Synexa 视觉定位判断、核心视觉原则提炼（空间感 / 精密感 / 未来感 / 可信感）、色彩系统方向、字体方向、构图逻辑
- 移交内容：视觉战略推演结论 → iS-Matrix（固化为提示词与 SOP）
- 协同触发原因：提示词生产属于 iS-Matrix 核心职责，iS-SCO 不直接生产提示词资产

**Step 2 · iS-Matrix：固化为设计 Agent 提示词与 SOP**

- 接收内容：iS-SCO 视觉战略推演结论
- 完成内容：
  - 视觉系统设计 Agent 主提示词（含角色定义、风格约束、输出规范）
  - 各模块子提示词（首页 Hero / 产品页 / 关于页 / 全局导航）
  - 视觉设计 SOP（设计师 / AI 执行体通用）
  - 提示词资产存入 iS-Matrix 资产库
- 移交内容：提示词包 + SOP → iS-Synexa PCS（用于官网设计落地）
- 回流反馈：对 iS-SCO 视觉原则的可执行性校准意见

**Step 3 · iS-Synexa PCS：官网设计落地执行**

- 接收内容：iS-Matrix 提示词包 + SOP
- 完成内容：
  - 使用提示词驱动 AI 生成官网视觉稿
  - 执行 SOP 完成视觉审查与迭代
  - 记录执行过程中的提示词偏差与 SOP 不足
- 回流反馈：执行偏差记录 + 补丁建议 → iS-SCO（复盘校准）+ iS-Matrix（更新提示词资产）

**Step 4 · iS-SCO：复盘校准**

- 接收内容：iS-Synexa PCS 回流反馈包
- 完成内容：
  - 对视觉战略推演结论进行校准
  - 判断偏差来源（战略层 / 提示词层 / 执行层）
  - 输出校准报告 → iS-Matrix

**Step 5 · iS-Matrix：更新提示词资产**

- 接收内容：iS-SCO 校准报告 + iS-Synexa PCS 补丁建议
- 完成内容：
  - 更新视觉系统设计 Agent 提示词（版本升级）
  - 更新视觉设计 SOP
  - 记录本次 Patch Note
- 判断：是否需要提交 iS-Core 裁决

**Step 6 · iS-Core：必要时纳入品牌基线**

- 触发条件：视觉系统定义涉及 Synexa 品牌核心识别系统（色彩 / 字体 / 构图原则），属于 D 类基线越界
- 完成内容：
  - 审查 iS-Matrix 提交的视觉系统定义
  - 裁决是否纳入 Synexa 品牌基线
  - 若纳入，更新 CONTEXT_OS.md 品牌基线字段，推送 GitHub
  - 触发 GPT 同步提醒

---

### 9.3 案例总结

本案例验证了以下协议设计的有效性：

- 「越界即触发」机制有效防止了单一空间独立承担全链路任务的风险
- 交接任务包确保了跨空间意图传递的准确性
- 回流反馈机制使视觉战略与执行结果之间形成了校准闭环
- iS-Core 的基线裁决节点确保了品牌一致性不被分散执行所侵蚀

## 十、版本管理与补丁机制

### 10.1 版本规则

- **v0.x**：协议草案阶段，可频繁修订，无需 iS-Core 裁决
- **v1.0**：协议正式版，须经 iS-Core 裁决后发布
- **v1.x**：小版本迭代，由实战 Case Log 和 Patch Note 驱动，经 iS-Core 确认后更新
- **vX.0**：重大版本升级，须经 iS-Core 正式裁决，并更新 CONTEXT_OS.md

### 10.2 Case Log 机制

每次实战触发本协议后，应生成 Case Log，记录以下内容：

- 案例名称与触发时间
- 触发空间与协同分级
- 参与空间列表
- 协同流程摘要
- 发现的协议不足
- 是否触发补丁

Case Log 存入：`00-master/case-logs/CWCP_CaseLog_[案例名]_[日期].md`

### 10.3 Patch Note 机制

每次对本协议进行修改时，须在文件末尾「版本记录」节追加 Patch Note，记录：

- 修改版本号
- 修改日期
- 修改内容摘要
- 触发修改的 Case Log 引用（如有）
- 是否经 iS-Core 裁决

### 10.4 基线级变更提交规则

以下情形属于基线级变更，必须提交 iS-Core 裁决，不得自行修改：

- 修改「主责空间判断规则」（第五节）
- 修改「协同分级」定义（第四节）
- 新增或删除适用范围中的工作空间（第二节）
- 将协议版本从 v0.x 升级至 v1.0
