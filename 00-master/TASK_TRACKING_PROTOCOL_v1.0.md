## 零、触发词机制（各专项工作空间必读）

**任何工作空间（对话组）在需要建立或维护任务追踪表时，只需使用以下触发词，无需重新沟通标准：**

| 触发词 | 适用场景 | 执行动作 |
|---|---|---|
| `读取任务协议` | 首次接入或需要校准标准时 | 读取本文件全文，按本协议规范建立或校验当前工作空间的任务追踪表 |
| `初始化任务表 [工作空间代号]` | 新工作空间首次建立任务追踪表 | 按第二章字段规范，创建该工作空间的标准任务追踪表，文件命名为 `TASK_BOARD_[代号].md` |
| `更新任务表` | 每次有新任务、状态变更或阻塞项时 | 按本协议字段规范追加或更新任务行，并在回复末尾附推进汇总表 |
| `输出推进汇总` | 每次回复末尾需要附汇总表时 | 按第三章模板输出标准推进汇总表（Markdown 表格格式） |
| `全局任务审查` | 跨工作空间任务状态对齐时 | 读取所有活跃工作空间的 `TASK_BOARD_*.md`，输出全局任务健康度报告 |

> **核心原则**：触发词一经使用，Agent 必须先读取本文件，再执行任何任务追踪操作。禁止在未读取本协议的情况下自行定义字段或格式。

## 一、协议目标

本协议解决以下问题：

**问题一：标准不统一。** 不同工作空间各自设计任务追踪表，字段、状态标签、优先级定义各不相同，导致跨工作空间对齐困难。

**问题二：重复沟通成本高。** 每次新建工作空间或新接入专项 Agent，都需要重新沟通追踪格式，浪费大量对齐成本。

**问题三：状态不可见。** 任务状态停留在聊天记录中，无法被其他 Agent 或工作空间读取，形成信息孤岛。

本协议通过「一处定义，全局生效」的机制，确保：
- 所有工作空间使用同一套字段规范和状态标签；
- 任何 Agent 通过触发词即可激活标准，无需重新协商；
- 任务状态以结构化 Markdown 文件形式持久化至 GitHub，可被任意工作空间读取。

## 二、标准字段规范

### 2.1 核心字段（必填）

| 字段名 | 类型 | 说明 | 示例 |
|---|---|---|---|
| **任务ID** | 字符串 | 格式：`[工作空间代号]-[序号]`，序号三位补零 | `W01-001`、`NF-012` |
| **任务名称** | 字符串 | 简洁描述任务目标，不超过20字 | `架构图底图替换为 v1.3` |
| **优先级** | 枚举 | P0 / P1 / P2 / P3（见 2.3 定义） | `P1` |
| **状态** | 枚举 | 使用标准状态标签（见 2.2 定义） | `🔵 进行中` |
| **负责方** | 字符串 | 执行该任务的工作空间代号或角色 | `执行-iS-Core` |
| **创建日期** | 日期 | `YYYY-MM-DD` 格式 | `2026-05-03` |

### 2.2 扩展字段（按需填写）

| 字段名 | 类型 | 说明 | 示例 |
|---|---|---|---|
| **更新日期** | 日期 | 最后一次状态变更的日期 | `2026-05-03` |
| **依赖项** | 字符串 | 前置任务 ID，多个用逗号分隔 | `W01-003, W01-004` |
| **阻塞原因** | 字符串 | 当状态为「已阻塞」时必填 | `等待用户确认 GitHub Token` |
| **交付物** | 字符串 | 任务完成后的可验证产出 | `checkpoint f2ebd202` |
| **检查点/版本** | 字符串 | 关联的代码 checkpoint 或文件版本号 | `f2ebd202` |
| **备注** | 字符串 | 补充说明，不超过50字 | `依赖 #02 全量同步完成后验证` |

### 2.3 状态标签定义

| 状态标签 | 含义 | 触发条件 | 责任方 |
|---|---|---|---|
| `⬜ 待启动` | 已登记，尚未开始 | 任务创建时默认状态 | iS-Core |
| `🔵 进行中` | 已下发，正在执行 | 指令已下发至执行框 | 执行框 |
| `🟡 待确认` | 执行完成，等待人工或上游确认 | 执行框完成后，等待验收 | 人工 / iS-Core |
| `🟣 审查中` | 提交至审查框，等待审查结论 | 进入 FBR 审查流程 | 审查框 |
| `✅ 已完成` | 验收通过，任务关闭 | 人工确认或自动验证通过 | iS-Core |
| `❌ 已取消` | 任务终止，不再推进 | 需求变更或决策撤销 | iS-Core |
| `🔴 已阻塞` | 因依赖项或外部原因暂停 | 阻塞原因字段必填 | 全局 |

### 2.4 优先级定义

| 优先级 | 含义 | 处理时限 | 典型场景 |
|---|---|---|---|
| **P0** | 紧急阻塞 | 立即处理，当前对话内完成 | 系统无法访问、核心功能崩溃 |
| **P1** | 高优先级 | 本次工作周期内完成 | 关键功能缺失、用户明确要求 |
| **P2** | 中优先级 | 下一工作周期完成 | 体验优化、非核心功能 |
| **P3** | 低优先级 | 有空时推进 | 探索性功能、长期规划 |

## 三、标准推进汇总表模板

**每次回复末尾必须附此表（触发词 `输出推进汇总` 时输出，或每次有任务变更时自动附加）。**

```markdown
### 推进汇总 · [工作空间代号] · [日期]

| 任务ID | 任务名称 | 优先级 | 状态 | 负责方 | 备注 |
|---|---|---|---|---|---|
| W01-001 | 示例任务A | P0 | ✅ 已完成 | 执行-iS-Core | checkpoint abc123 |
| W01-002 | 示例任务B | P1 | 🔵 进行中 | 执行-iS-Core | — |
| W01-003 | 示例任务C | P1 | 🟡 待确认 | 人工 | 等待用户点击确认 |
| W01-004 | 示例任务D | P2 | ⬜ 待启动 | — | 依赖 W01-003 |
```

> **规则**：表格按优先级降序排列，同优先级内按状态排列（进行中 > 待确认 > 已阻塞 > 待启动 > 已完成）。已完成任务可折叠至表格底部或单独归档区。

## 五、接入指南（各专项工作空间）

### 5.1 首次接入流程

1. **触发**：在工作空间对话中输入 `读取任务协议`
2. **读取**：Agent 读取本文件全文（`00-master/TASK_TRACKING_PROTOCOL_v1.0.md`）
3. **初始化**：输入 `初始化任务表 [工作空间代号]`，Agent 按规范创建 `TASK_BOARD_[代号].md`
4. **推送**：Agent 将文件推送至 GitHub `06-isync/` 目录
5. **确认**：在回复末尾输出首次推进汇总表

### 5.2 日常使用流程

```
用户下发新任务
    ↓
Agent 在 TASK_BOARD 中新增任务行（状态：⬜ 待启动）
    ↓
任务开始执行（状态变更：🔵 进行中）
    ↓
执行完成，等待验收（状态变更：🟡 待确认）
    ↓
验收通过（状态变更：✅ 已完成，填写交付物字段）
    ↓
每次回复末尾自动附推进汇总表
```

### 5.3 强制规则

1. **任何状态变更必须同步更新 TASK_BOARD 文件并推送至 GitHub**，禁止仅停留在聊天记录中。
2. **每次回复末尾必须附推进汇总表**，格式严格按第三章模板执行。
3. **新任务必须先登记，再执行**，禁止未登记直接开始执行。
4. **阻塞状态必须填写阻塞原因**，不得留空。
5. **已完成任务不得删除**，只能移至「已完成任务」区归档。

## 六、与现有机制的关系

| 现有机制 | 关系说明 |
|---|---|
| `ISYNC_PROTOCOL.md` | ISYNC 负责指令归集与代码审查，本协议负责任务状态追踪；两者互补，ISYNC 是「指令层」，本协议是「任务层」 |
| `EXECUTION_TRACKER.md` | EXECUTION_TRACKER 是 iS-Core 自身的任务看板（编撰线/执行线/治理线），本协议是其底层标准规范；EXECUTION_TRACKER 应按本协议字段规范维护 |
| `FBR 机制` | FBR 是功能基线审查机制，本协议中「审查中」状态对应 FBR 审查阶段 |
| `TBF 机制` | TBF 是任务目标基线文件，本协议任务表是 TBF 的执行追踪层 |
