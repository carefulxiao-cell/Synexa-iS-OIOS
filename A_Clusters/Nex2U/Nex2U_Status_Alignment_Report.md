# Nex₂U 现状对齐与推进路径报告

## 1. 核心判断：现有网站是“模型”还是“可用系统”？

经过对前端点餐平台（`sitechnology.com.cn`）和后端运营平台（`hospitalapp-edldi6mw.manus.space/admin/pin`）的实际检查，结论如下：

**这两个网站是高保真的“功能原型（Prototype）”，而非可正式商用的“生产系统（Production）”。**

### 1.1 已落地的可用点（高价值资产）
*   **前端交互逻辑已跑通**：前端 H5 页面已经实现了“堂食点餐”和“周期预订（7日餐预订）”的完整交互流。
*   **UI/UX 设计已成型**：界面设计（如颜色、排版、组件样式）已经非常成熟，符合医疗/健康餐饮的专业调性。
*   **场景分类已体现**：前端已经展示了“早餐·启动代谢”、“正餐·特护膳食”、“正餐·慢病管理”等分类逻辑，与 28 个主题场景的思路是一致的。

### 1.2 为什么还不能正式使用（目标差距）
*   **缺乏核心引擎支撑**：目前的系统更像是一个“静态菜单展示+购物车”的传统点餐系统。它没有接入真正的“营养结构点（P·C·V·E·PR）”计算逻辑，也没有实现“结构驱动的餐食生成”。
*   **数据结构未对齐**：后端的数据库结构（Schema）大概率是基于传统电商逻辑（商品、订单、用户）设计的，而不是基于 Nex₂U 的六大核心数据库（主题系统、母型系统、营养点系统等）设计的。
*   **部署环境非生产级**：后端管理平台目前部署在 Manus 的临时沙盒域名（`*.manus.space`）下，这种环境不具备生产级别的稳定性、安全性和持久化能力。

## 2. 整体情况与计划目标对齐

为了确保不跑偏，我们需要把“我们要做什么”和“我们现在有什么”彻底对齐。

### 2.1 我们的终极目标（The North Star）
构建一个**结构驱动的健康稳态餐食生成引擎（Nex₂U）**。
它不是一个简单的点餐工具，而是一个能够将非结构化的健康餐饮、营养逻辑与供应链经验，转化为可计算、可执行、可复用的结构化规则系统。它的首发落地场景是**新一代优质饭堂**，并预留了连接具身智能工具的接口。

### 2.2 我们的系统架构（The Blueprint）
整个系统分为三层，这也是我们后续开发必须严格遵循的边界：
1.  **Nufō³（交互层）**：用户触点，即前端 H5 点餐平台。负责收集用户需求、展示餐食方案、完成交易。
2.  **Nex₂U（引擎层）**：核心大脑。负责接收 Nufō³ 的指令，调用六大数据库，基于营养结构点和工艺规则，动态生成餐食方案。
3.  **NuBō（执行层）**：即后端运营平台。负责接收 Nex₂U 生成的方案，进行供应链调度、厨房生产管理、履约交付。

### 2.3 我们当前的现状（The Reality）
*   **理论体系**：已非常完备（28个主题场景、90个营养点、餐型母型等），并已收拢至 `Nex2U_Master_Doc_v2.1.md`。
*   **前端（Nufō³）**：已有高保真原型（`sitechnology.com.cn`），UI 和基础交互可直接复用，但需要重构数据对接逻辑。
*   **后端（NuBō）**：已有基础框架，但需要按照六大数据库的结构进行彻底重构。
*   **引擎（Nex₂U）**：**完全缺失**，这是接下来开发的最核心任务。

## 3. 后续推进路径与步骤（The Roadmap）

为了避免“一上来就干网站”导致的混乱和资源浪费，后续的开发必须遵循**“文字描述 -> 流程图 -> 编码打包”**的结构化流程。

### 阶段一：数据结构与接口契约设计（本周）
**目标**：在写任何一行代码之前，先把底层数据结构和前后端交互接口定死。
1.  **数据库 Schema 设计**：基于 Master Doc v2.1，设计六大核心数据库的表结构（如 `NutritionPoint` 表、`MealTemplate` 表、`Scenario` 表等）。
2.  **API 契约定义**：定义 Nufō³ 与 Nex₂U、Nex₂U 与 NuBō 之间的核心 API 接口（如 `generateMealPlan` 接口）。
3.  **交付物**：数据库 ER 图、API 接口文档。

### 阶段二：核心引擎（Nex₂U）开发（第 1-2 周）
**目标**：实现“结构驱动生成”的核心逻辑。
1.  **规则引擎开发**：实现基于 P·C·V·E·PR 编码的餐食组合算法。
2.  **数据录入**：将 28 个场景、90 个营养点等基础数据录入系统。
3.  **交付物**：可独立运行并输出计算结果的后端服务。

### 阶段三：前后端重构与对接（第 3-4 周）
**目标**：将现有的高保真原型接入真正的引擎。
1.  **后端（NuBō）重构**：基于新的数据库 Schema 重构管理后台，提供运营人员工作台。
2.  **前端（Nufō³）对接**：保留现有 UI，将静态数据替换为调用 Nex₂U 引擎的动态数据。
3.  **交付物**：完整跑通的 MVP 系统（新一代优质饭堂版本）。

## 4. 定期复核机制建议

为了确保全线全栈的描述随时最新，随时可以交付传递，建议建立以下机制：

1.  **单一事实来源（SSOT）**：`Nex2U_Master_Doc_v2.1.md` 及配套的架构图是唯一的权威文档。任何开发决策必须先更新文档，再写代码。
2.  **双周对齐会**：每两周进行一次系统状态 Review，对照 Master Doc 检查开发进度是否偏离航向。
3.  **跨平台同步**：每次 Master Doc 更新后，必须同步至 GitHub 仓库，并手动更新至 GPT 的 Project 知识库中，确保 Manus 和 GPT 的认知始终一致。
