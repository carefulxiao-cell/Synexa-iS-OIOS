# 系统审查标准 (IS_VERIFY_STANDARD)

**版本**: v1.1
**适用范围**: Synexa iS 体系下所有项目通用
**定位**: 规范系统审查的前置条件、维度、深度与输出格式，确保审查质量的一致性与结论的可信度。本标准为动态演进文件，随项目经验积累持续迭代。

---

## 1. 前置检查：审查启动条件

**审查必须在满足以下条件后方可启动，任何一项不满足，必须中止并要求补充，不得继续执行审查。**

| 检查项 | 要求 | 不满足时的处理 |
|---|---|---|
| 系统交付包文档 | 包含功能清单/接口清单/部署信息/已知问题 | 中止，要求开发方补充 |
| 完整代码包 | 包含前端/后端源码/schema.sql/环境配置 | 中止，要求开发方补充 |
| 测试记录 | 包含已测/未测/已知异常/边界场景 | 中止，要求开发方补充 |
| 当前变更记录 | 包含进行中修改/半完成模块/不稳定模块 | 中止，要求开发方补充 |
| 数据一致性说明 | 包含同步机制/双轨数据/持久化边界 | 中止，要求开发方补充 |

---

## 2. 审查级别定义

根据项目所处阶段选择对应的审查级别，不同级别的审查侧重点和深度不同。

| 级别 | 适用阶段 | 审查侧重 | 输出要求 |
|---|---|---|---|
| **L1 快速扫描** | 早期原型/概念验证 | 架构方向是否正确，核心数据模型是否合理 | 问题汇总表 + 整体评估结论 |
| **L2 标准审查** | 功能开发完成/准测试 | 六大维度全覆盖，重点关注业务逻辑和数据一致性 | 问题汇总表 + 优先处理清单 + 整体评估结论 |
| **L3 深度审查** | 准上线/重大版本迭代 | 六大维度全覆盖，深入代码细节，安全与性能专项检查 | 问题汇总表 + 优先处理清单 + 整体评估结论 + 上线建议 |

---

## 3. 审查六大维度

审查必须严格覆盖以下六个维度，不得遗漏。

### 3.1 架构风险 (Architecture Risks)
模块划分是否职责单一清晰，是否存在某个模块宕机导致整体崩溃的单点故障，模块间耦合度是否过重（修改一处引发多处连锁反应），以及系统在外部依赖失效或高并发时是否具备基本的降级能力。

### 3.2 数据风险 (Data Risks)
数据表设计是否存在不合理的冗余或缺失关键字段，关键字段是否缺少数据库层面的非空、唯一、外键约束，本地状态（前端 state/内存）与数据库之间的同步机制是否可靠，是否存在本地生成 ID 与数据库 ID 格式不一致或冲突的问题，以及数据持久化边界是否清晰合理。

### 3.3 接口风险 (API Risks)
所有敏感接口是否均有严格的身份验证与权限控制，是否对所有外部输入进行了类型、必填项及边界值的严格校验，是否存在未捕获的异常直接抛出给前端，以及接口之间的调用链路是否清晰、是否存在死循环或过度嵌套。

### 3.4 安全风险 (Security Risks)
代码中是否明文硬编码了密钥、密码、IP 地址或 Token，是否存在 SQL 注入、XSS 等常见 Web 漏洞风险点，用户提交的任何内容是否都经过了转义和安全过滤，以及用户信息、支付数据等是否进行了加密存储或脱敏展示。

### 3.5 业务逻辑风险 (Business Logic Risks)
核心业务流程是否有未覆盖的异常分支（如支付失败、网络中断），在多步操作中若某一步失败是否具备完整的状态回滚机制，关键业务字段在整个链路中是否能正确完整地传递，正在修改或重构的模块是否存在新旧逻辑并存导致的冲突，以及未登录用户、并发操作等特殊场景下的业务处理是否完整。

### 3.6 可维护性风险 (Maintainability Risks)
关键复杂逻辑是否有清晰的注释说明，是否存在大量复制粘贴的重复代码，是否存在未定义常量的魔法数字或魔法字符串，以及系统是否具备基本的日志记录能力以便故障时快速定位。

## 4. 严重程度定义

| 等级 | 标记 | 定义 | 上线影响 |
|---|---|---|---|
| 致命 | 🔴 | 系统无法正常运行、存在严重安全漏洞或核心业务阻断 | **必须修复后方可上线，无例外** |
| 需关注 | 🟡 | 影响系统稳定性、数据准确性或可维护性 | 需在近期版本修复，可带条件上线 |
| 建议优化 | 🟢 | 不影响当前核心运行，但影响长期代码质量或扩展性 | 可纳入后续迭代计划 |

---

## 5. 审查结论标准

审查结论必须明确给出以下三种判定之一，不得模糊表述：

| 结论 | 触发条件 | 含义 |
|---|---|---|
| **不建议上线** | 存在任何🔴致命项 | 必须完成所有致命项修复并重新审查后，方可重新评估 |
| **有条件上线** | 无🔴致命项，但存在🟡需关注项 | 需制定明确的修复计划和时间节点，并由负责人确认后方可上线 |
| **建议上线** | 无🔴致命项，无🟡需关注项 | 可正常推进上线流程 |

---

## 6. 审查输出规范

审查完成后，必须输出名为 `系统审查报告_VERIFY_REPORT_[项目代号]_v[版本号].md` 的文件，结构如下：

**第一部分：整体评估结论**
给出三种判定之一（不建议上线 / 有条件上线 / 建议上线），并用一到两句话说明判定依据。

**第二部分：优先处理清单**
仅列出🔴致命项，按处理的逻辑顺序排序，作为开发团队的最高优先级任务。若无致命项，此部分标注「无」。

**第三部分：问题汇总表**
以表格形式列出所有发现的问题，包含：维度 / 问题描述 / 严重程度 / 建议处理方式。
