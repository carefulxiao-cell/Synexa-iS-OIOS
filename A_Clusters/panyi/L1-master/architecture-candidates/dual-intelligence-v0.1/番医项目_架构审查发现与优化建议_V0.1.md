# 番医项目｜首批架构审查发现与优化建议

> **性质**：架构表达审查记录  
> **状态**：候选建议，待业务审核  
> **边界**：不替代专业计算、系统需求书或实施批准。

## 一、核心判断

本轮最重要的架构收益，不是新增更多模块，而是把原先容易混在一张“菜单/采购/生产表”里的对象，拆成可追溯、可审核、可版本化的四组受控对象：

1. **菜单版本**：什么可以被选择和展示；
2. **需求版本**：什么需求已被确认、何时冻结；
3. **生产版本**：什么计划可以被生产、由哪个批次执行；
4. **采购与库存执行事实**：什么被下单、收货、验收、入库、领用和结算。

只有这样，才能避免“按 A 菜单采购、按 B 菜单生产、按 C 口径结算”的经营与食品安全风险。

## 二、结构冲突与重复

| 优先级 | 发现 | 风险 | 建议裁决 |
|---|---|---|---|
| P0 | 场景、菜单、档位、餐次在日常叙述中容易混用 | 系统模型、菜单审核和需求聚合会失真 | 建立四者术语定义及关系表；Scene 不等于 Menu / Slot / 餐次 |
| P0 | 产品、变体、售卖 SKU、套餐容易统称“菜品” | 价格、工艺、结算、套餐组成和履约规则无法独立演化 | 固化四层对象边界；套餐用组成关系表而非文本字段 |
| P0 | 预测、确认需求、订单、生产计划、生产批次可能被同一张表承载 | 备选菜单可能误驱动采购和生产 | 建立四类受控版本及冻结规则；只有确认需求与批准生产计划驱动执行 |
| P0 | 食材、采购 SKU 与库存数量可能被混用 | 营养 / 配方语义、交易规格与批次效期不可追溯 | 分开建模；库存以地点、批次、效期、质量状态、可用量和事件管理 |
| P1 | 共享采购与专项采购未明确拆分 | 专膳、应急或专用食材可能混账、越权或无法核算 | 在需求、物料、PO 行和成本归集层同时标识采购属性 |
| P1 | 既有采购换算、出成率和应用口径仍有大量待确认项 | BOM 和成本模型如果过早固化会放大错误 | 采购换算、出成率和单价只作为待验证输入；不得直接进入正式配方 / 自动 MRP |
| P1 | 地址主数据、点餐 / 打单系统与代码入口未找回 | 场景线无法稳定绑定履约单元、路线和交付时效 | 先找回地址主数据和系统责任源，再定义配送 / 标签接口 |
| P1 | 营收与损益细表、退款 / 折扣 / 补贴口径待确认 | 成本、毛利和经营洞察可能与销售事实错配 | 先做字段字典与对账关系，不先做经营自动结论 |
| P1 | 人力管理台已建立岗位框架，但真实岗位、授权与财务责任仍待确认 | 排工和异常升级可能无最终责任人 | 先完成岗位 × 审批点 × 每日必交付物的 RACI；不得由 AI 替代最终责任 |

## 三、必须补齐的系统接口

1. **患者 / 医嘱与膳食管理**：最小化处理身份、饮食约束、过敏原、禁忌、餐次、病区 / 床位和生效时间；专业人员负责主源确认。
2. **菜单 / 营养 / 配方主数据**：菜单、配方、BOM、营养、过敏原、替代规则、份量、损耗、专业来源和有效期须版本化。
3. **订餐 / 需求 / 餐卡**：预测、预约、确认、取消、加餐、实发必须区分。
4. **采购 / 供应商 / ERP**：供应商资格、合同价、MOQ、交期、PO、到货、退货、对账与接口失败告警。
5. **库存 / 追溯**：可用量、预留量、批次、效期、温区、质检状态、领退料、报废与正反向追溯。
6. **生产 / 质量 / 排班**：工单、实际投料、产出、损耗、温控、留样、质检、设备状态、岗位资质和工时。
7. **配送 / POS / 结算**：路线、交接、签收、销量、退餐、退款、餐补、成本中心与总账口径。
8. **主数据、身份与消息机制**：统一编码、组织权限、接口幂等、事件时间、重试、失败告警和审计日志。

## 四、快速见效路径

1. 用图02建立 **对象边界审查表**：先对 Scene、Slot、Product、Variant、Sales SKU、Set Meal、Ingredient、采购 SKU 的现有母表列逐项归类，所有不确定项标 `TO VERIFY`。
2. 用图03建立 **菜单计划包审批清单**：菜单版本、需求版本、生产版本、采购 / 库存执行版本各有责任人、状态、冻结点和变更入口。
3. 用关联矩阵建立 **接口责任表**：每个对象只指定一个权威主源，其他表只作为校验或派生来源。
4. 优先完成 **批次级最小追溯闭环**：收货批次 → 领料 → 生产批次 → 交付 / 销售 → 异常 / 反馈；先小范围试验，后扩展。

## 五、长期根本路径

1. 形成“共用对象 + 范围配置 + 版本谱系 + 事实血缘”四层业务本体；
2. 将 AI 的产出统一进入“候选池”，以证据、影响分析和人工审核决定是否生成新版本；
3. 把场景、菜单、产品、供应、生产、履约、经营事实形成可计算的协同网络；
4. 在语义与主源稳定后，再由 Manus 把已确认对象转为数据模型、接口契约、权限模型和 MVP 迭代范围。
