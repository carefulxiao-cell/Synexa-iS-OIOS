# IS_CODE_PACKAGE_GOVERNANCE_v1.1 · 全局代码包治理与交付接入原则

版本：v1.1

最后更新：2026-06-10
文件性质：全局管理原则文件，适用于 Synexa iS 体系内所有在流转的代码包资产。

**适用对象：** 所有开发窗口交付的代码包、源码压缩包、技术交接包、AI 接力代码资料、新方向实验代码与应急恢复代码资产。

**核心目标：** 确保代码资产在接收、备份、审查、实验、恢复和后续交接过程中始终具备**可追溯、可隔离、可复用、可回滚、可安全流动**的治理能力。

**体系定位：** 本文件是 Synexa iS 体系代码资产治理的全局原则，适用于所有在 iS 体系内流转的代码包。代码包的状态信息应在对应项目的 PBS（M1 资产库）中登记，状态标签与本文件五状态定义保持一致。

---

## 1. 总原则

代码包不是普通文件，而是项目真实运行能力、开发历史、业务逻辑、技术依赖和未来演进可能性的集合。任何代码包一旦进入组织资产体系，都不应被简单视为「一个压缩包」或「一个可随意修改的源码目录」，而应被纳入明确的状态管理、版本管理和风险隔离机制。

本原则强调：**开发方只交付一个原始代码包，但组织内部不应只保留一个代码包。** 正确方式是将同一个原始代码包转化为多个治理状态，使其分别承担原始留证、安全储备、预审交接、实验开发和应急恢复等不同功能。

> **核心判断：原始包负责真实性，安全储备包负责可追溯，审查包负责可交接，实验包负责创新，恢复包负责应急。**

---

## 2. 五状态治理模型

同一个原始代码包进入后，应形成五种管理状态。它们不是简单重复复制，而是分别承担不同职责，避免原始资产被污染、实验代码误入生产、敏感信息误入仓库，以及应急时无法快速接入。

| 状态编号 | 状态名称 | 核心作用 | 是否可修改 | 使用边界 |
|----------|----------|----------|-----------|----------|
| 00 | `original` 原始包 | 保留开发方交付的原始状态，作为事实源和追溯依据 | 否 | 不直接开发、不直接覆盖、不直接改动 |
| 01 | `safe-reserve` 安全储备包 | 形成只读安全备份，用于兜底、比对和未来追溯 | 否 | 内容应与原始包一致，或仅做规范命名 |
| 02 | `reviewed` 预审包 | 经目录核验、敏感信息检查和必要脱敏后，形成可交接版本 | 可做审查性修正 | 用于阅读、交接、入库和 AI 接力 |
| 03 | `sandbox` 实验包 | 从预审包派生，用于新方向、新功能、新架构测试 | 是 | 所有试错、重构和探索均在此发生 |
| 04 | `recovery-ready` 应急接入包 | 从预审包整理，保留可运行、可接入、可恢复能力 | 原则上少改 | 用于系统异常、迁移、回滚或快速接管 |

五状态模型的关键不是文件数量，而是**职责隔离**。任何修改都不能回写到 `original` 和 `safe-reserve`；任何实验都不能污染 `recovery-ready`；任何未审查内容都不能直接作为正式交接依据。

---

## 3. 原始包不可动原则

开发方交付的第一个完整代码包应被视为原始事实源。该包的价值不在于立即可用，而在于它记录了交付时点的真实状态。无论后续发现结构混乱、说明不足、存在敏感信息，还是运行方式不完整，都不应直接修改原始包。

| 原则 | 说明 |
|------|------|
| 不改内容 | 不在原始包内增删文件、不修复代码、不替换配置 |
| 不直接开发 | 不以原始包作为实验开发目录 |
| 不直接覆盖 | 不用后续版本覆盖原始交付文件 |
| 不直接扩散 | 未经审查前，不作为正式交接包传播 |
| 保留来源 | 应记录交付时间、交付方、版本说明和对应业务状态 |

原始包的作用是**留证**，不是开发。只有保留原始状态，后续才有能力判断哪些变化来自开发方，哪些变化来自内部审查，哪些变化来自实验改造。

---

## 4. 安全储备包只读封存原则

安全储备包是原始包的兜底副本，作用是防止原始包损坏、丢失或在后续操作中被误动。安全储备包应尽量保持与原始包一致，允许的变化仅限于外部文件命名规范化、校验记录和存放方式调整。

安全储备包不承担日常开发任务，也不承担测试任务。它的存在价值是：当后续 `reviewed`、`sandbox` 或 `recovery-ready` 出现争议时，能够回到最初状态重新核验。

| 项目 | 要求 |
|------|------|
| 内容状态 | 与原始包保持一致 |
| 修改权限 | 只读，不修改 |
| 核验方式 | 建议生成校验值（如 SHA-256），确认文件未被篡改 |
| 使用场景 | 追溯、比对、重新预审、灾备兜底 |

---

## 5. 预审包用于交接与入库原则

`reviewed` 不是简单复制包，而是经过预审后形成的可交接版本。预审的目标不是过度删减代码资产，而是确认该代码包能被安全阅读、接力、归档和必要时纳入版本管理。

预审包应尽量保留项目知识、业务逻辑、模块结构、接口关系和运行说明；但应剥离或占位处理密钥、真实连接串、生产账号、真实用户数据和不可扩散的生产配置。

| 应保留内容 | 应处理内容 |
|-----------|-----------|
| 业务逻辑、模块结构、普通接口路径、技术依赖、运行说明 | 密钥、Token、Secret、真实数据库连接串、生产服务器账号、真实用户数据 |
| 表结构说明、测试数据样例、配置模板、部署说明 | 真实支付参数、短信接口密钥、云服务 AccessKey、生产 `.env` |
| 代码目录、依赖清单、版本说明、已知问题 | 可直接操作生产环境的敏感脚本或命令 |

预审包是后续 AI 接力、团队交接、GitHub 私有仓库入库和开发协作的主要依据。它应成为「可读、可审、可传递」的标准代码资产版本。

---

## 6. 实验包与恢复包必须分离

新方向测试与应急恢复是两类完全不同的任务。实验包追求可试错、可重构、可废弃；恢复包追求稳定、少改、可复现。二者如果混在一起，会导致实验代码污染恢复路径，也会让应急接入时无法判断哪个版本可靠。

| 类型 | 目标 | 来源 | 允许行为 | 禁止行为 |
|------|------|------|----------|----------|
| `sandbox` 实验包 | 新功能、新方向、新架构验证 | 从 `reviewed` 派生 | 可修改、可重构、可废弃 | 禁止覆盖原始包和储备包 |
| `recovery-ready` 恢复包 | 快速接入、应急恢复、回滚兜底 | 从 `reviewed` 整理 | 仅做必要运行适配 | 禁止混入未经验证的实验代码 |

任何新开发都应进入 `sandbox`；任何应急接管都应依赖 `recovery-ready`。这条分离原则是防止版本污染的关键。

## 7. 代码包接收后的标准动作

开发窗口交付代码包后，应按顺序完成以下动作。该流程的目标是让代码包从「一个文件」转化为「可治理资产」。

| 步骤 | 动作 | 产出 |
|------|------|------|
| 1 | 接收开发方原始代码包，记录交付时间、来源和版本说明 | `original` 原始包记录 |
| 2 | 复制安全储备包，保持只读封存 | `safe-reserve` 安全储备包 |
| 3 | 解压并进行目录结构、依赖、配置、敏感信息和运行方式预审，输出预审记录 | 目录树、`REVIEW_RECORD_YYYYMMDD.md`、敏感扫描记录 |
| 4 | 形成预审后的可交接版本 | `reviewed` 预审包 |
| 5 | 从预审包复制实验包 | `sandbox` 实验包 |
| 6 | 从预审包整理恢复包 | `recovery-ready` 应急接入包 |

这个顺序不能倒置。尤其不能在未形成原始留证和安全储备之前直接进入开发测试，也不能在未完成预审之前直接将源码作为正式交接依据。

**预审记录要求**：`REVIEW_RECORD_YYYYMMDD.md` 应至少包含以下内容：目录结构树形文本、敏感信息扫描结论（发现项及处理方式）、运行方式验证结论（是否可本地启动）、预审负责人与日期。该文件应与预审包存放于同一目录。

## 8. 命名原则

代码包命名应统一、可读、可追溯，避免不同成员、不同 AI 或不同阶段对同一文件产生误判。采用以下命名结构：

```text
{project}_source_{YYYYMMDD}_{status}_vX.Y.zip
```

其中 `{status}` 应使用受控状态名，避免随意命名。

| 状态名 | 含义 |
|--------|------|
| `original` | 开发方原始交付，未改动 |
| `safe-reserve` | 安全储备，只读封存 |
| `reviewed` | 已完成预审和必要脱敏，可交接 |
| `sandbox-[描述性短名]` | 实验方向，可修改（如 `sandbox-ai-rewrite`、`sandbox-new-auth`） |
| `recovery-ready` | 应急接入或恢复使用 |

当实验方向超过两个时，以 `sandbox-[描述性短名]` 格式命名，避免仅用字母序列（如 `sandbox-a`、`sandbox-b`）导致含义模糊。

命名应遵循**状态明确、日期明确、版本明确、项目明确**四项要求。文件名中的版本号应与文件内容说明保持一致，避免出现命名版本与实际内容版本不一致。

**示例：**

```text
hospital-canteen_source_20260610_original_v1.0.zip
hospital-canteen_source_20260610_safe-reserve_v1.0.zip
hospital-canteen_source_20260610_reviewed_v1.0.zip
hospital-canteen_source_20260610_sandbox-ai-rewrite_v1.0.zip
hospital-canteen_source_20260610_recovery-ready_v1.0.zip
```

## 9. 私有仓库不等于免门禁原则

私有仓库能够降低公开可见性风险，但不能替代代码包治理。代码资产一旦进入版本系统，后续可能被成员复制、AI 读取、外包接力、权限扩散、迁移导出或误设公开。因此，私有权限不是免审查理由。

本原则强调：**可以保留项目知识，但不能保留生产危险信息；可以让代码可交接，但不能让密钥和真实生产凭证随代码流动。**

| 信息类型 | 处理原则 |
|----------|----------|
| 项目业务逻辑、代码结构、模块关系、普通接口路径 | 尽量保留 |
| 运行说明、依赖说明、配置模板 | 保留，并使用示例值 |
| `.env.example` | 可保留 |
| 真实 `.env` | 不应进入正式交接包 |
| 密钥、Token、Secret、AccessKey | 删除或占位 |
| 真实数据库连接串、服务器账号、生产 IP | 删除或占位 |
| 真实用户数据、订单数据、手机号、身份信息 | 删除、抽象或样例化 |
| 可直接操作生产环境的命令或脚本 | 审查后再决定是否保留摘要 |

精准脱敏的目标不是让资料变少，而是让资料能够安全流动。业务知识和技术结构应尽量保留，生产凭证和真实身份信息必须剥离。

## 10. 存储位置与访问权限

五个状态的代码包应存放于不同位置，并设置对应的访问权限，防止越权读写和状态污染。

| 状态 | 建议存储位置 | 读权限 | 写权限 |
|------|------------|--------|--------|
| `original` | 本地加密存储 / 私有 S3 | 项目负责人 | 仅接收时写入一次，此后锁定 |
| `safe-reserve` | 独立备份路径 / 异地备份 | 项目负责人 | 锁定，不再写入 |
| `reviewed` | GitHub 私有仓库 / 共享工作区 | 团队成员 + AI 工作空间 | 预审负责人 |
| `sandbox` | GitHub 私有仓库（独立分支或目录） | 开发成员 + AI 工作空间 | 开发成员 |
| `recovery-ready` | 私有仓库 + 本地备份（双存） | 项目负责人 + 运维 | 运维负责人 |

`original` 和 `safe-reserve` 一旦写入，应通过文件系统权限或存储策略设为只读，防止任何人（含 AI）在后续操作中误改。

## 11. AI 接力专项规则

AI 工作空间（含 Manus、GPT、Kimi 等）是代码包的重要消费方，须遵循以下专项规则：

| 规则 | 说明 |
|------|------|
| 只读 `reviewed` | AI 工作空间只允许读取 `reviewed` 预审包，不得直接接触 `original` 和 `safe-reserve` |
| 同步提供清单 | 向 AI 传递代码包时，应同步提供 `CODE_PACKAGE_MANIFEST`，使 AI 能够理解包的边界、版本和已知问题，避免基于不完整信息产生误判 |
| 产出落入 sandbox | AI 产出的修改建议、重构代码、新增功能，应由人工确认后落入 `sandbox`，不得直接写回 `reviewed` |
| 不传递敏感信息 | 即使是 `reviewed` 包，传递给 AI 前仍须确认敏感信息已完成脱敏处理 |
| 接力说明随包走 | AI 接力时，前一个 AI 工作空间应输出接力说明（当前状态、已做工作、待解决问题），随代码包一并传递，不依赖对话记录续接 |

## 12. 版本迭代后的状态刷新规则

当开发方交付新版本代码包时，五个状态的处理规则如下：

| 状态 | 处理方式 |
|------|----------|
| 旧版 `original` | 以日期+版本号归档保留，不覆盖 |
| 旧版 `safe-reserve` | 以日期+版本号归档保留，不覆盖 |
| 旧版 `reviewed` | 归档，新版本重新走预审流程 |
| 旧版 `sandbox` | 由负责人判断是否需要迁移合并至新版本，不得自动继承 |
| 旧版 `recovery-ready` | 归档，基于新版 `reviewed` 重新整理 |

**核心原则**：新版本到来不等于旧版本消失。旧版本的 `original` 和 `safe-reserve` 是历史追溯的基础，必须完整保留。版本迭代时，应在对应项目的 PBS（M1 资产库）中更新状态标签，并记录版本变更时间。

## 13. 开发方交付要求

开发方交付代码包时，不应只提供一个压缩文件，还应提供必要说明。没有说明书的代码包很难被接管，也很难在后续发生问题时快速判断责任边界和运行条件。

开发方交付时应至少说明以下内容：

| 交付项 | 说明 |
|--------|------|
| 代码包生成时间 | 明确该包对应的时间点 |
| 对应版本 | 说明该包对应哪个开发版本或生产状态 |
| 包含范围 | 说明包含前端、后端、数据库脚本、部署脚本、配置模板等哪些内容 |
| 排除范围 | 说明哪些内容未包含，例如生产密钥、服务器文件、数据库备份等 |
| 运行环境 | 说明语言版本、框架、依赖、数据库、中间件等 |
| 启动方式 | 说明本地运行、测试运行或部署运行方式 |
| 数据库变更 | 说明表结构、迁移脚本、初始化数据情况 |
| 已知问题 | 说明当前未解决问题和潜在风险 |
| 敏感信息声明 | 说明是否包含 `.env`、密钥、连接串、真实用户数据或生产配置 |

建议开发方同步提供以下辅助文件：

```text
CODE_PACKAGE_MANIFEST_YYYYMMDD.md
DIRECTORY_TREE_YYYYMMDD.txt
ENV_EXAMPLE_YYYYMMDD.env
RUNBOOK_YYYYMMDD.md
CHANGELOG_YYYYMMDD.md
KNOWN_ISSUES_YYYYMMDD.md
```

这些文件的意义在于让代码包从「可下载文件」变成「可接管资产」。

## 14. 最小可执行版本

在资源或时间有限时，代码包治理至少应保留三种状态：`original`、`safe-reserve` 和 `sandbox`。其中 `original` 保证事实源，`safe-reserve` 保证兜底，`sandbox` 保证新开发不会污染原始资产。

| 最小状态 | 用途 | 是否必需 |
|----------|------|----------|
| `original` | 原始留证 | 必需 |
| `safe-reserve` | 安全备份 | 必需 |
| `sandbox` | 新开发测试 | 必需 |

**最小版本适用条件**：个人实验项目、内部工具原型、生命周期预期短于 3 个月的临时项目。凡涉及生产数据、外部开发方、多人协作或 AI 接力的项目，必须执行完整五状态模型，不得仅做最小版本。

---

## 15. 一句话执行口径

**开发方交付 `original`；内部复制 `safe-reserve`；预审后形成 `reviewed`；新方向从 `reviewed` 派生 `sandbox`；应急接入从 `reviewed` 整理 `recovery-ready`。**

这套机制的本质，是把代码包从一次性交付文件，升级为可持续治理、可安全接力、可稳定回滚、可独立实验的组织级技术资产。
