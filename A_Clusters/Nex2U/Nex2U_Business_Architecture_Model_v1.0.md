## 二、系统边界定义（System Boundary Definition）

Nex₂U 整体系统由三个层级构成，各层边界如下。边界划分的核心原则是：**规则在中枢生成，执行在两端落地，数据向中枢回流**。

### 2.1 Nex₂U 系统中枢层（System Nexus Layer）

**做什么**：负责决策逻辑生成、多端协同、数据流转、规则演进与系统目标锚定。具体包括：菜单逻辑生成（P1 引擎）、用户画像与场景状态识别、口味聚合与爆品系统、标签系统与推荐逻辑、数据结构与结构化结果生成机制、规则迭代机制。

**不做什么**：不直接面向 C 端用户展示界面；不直接操作 B 端厨房排期；不承担医疗诊断与处方职责。

### 2.2 NuBō 执行层（Execution Layer / B端优食运维）

**做什么**：将系统中枢生成的菜单逻辑转化为真实供给与生产行为。具体包括：菜单管理与调整、爆品管理、规则配置入口、数据看板与报表系统、厨房执行体系协同、运营协同流程、异常处理。

**不做什么**：不制定核心营养规则（由 Nex₂U/NuStā 负责）；不生成 C 端个性化推荐逻辑；不替代团餐公司的出品职责。

### 2.3 Nufō³ 交互层（Interaction Layer / C端食全食美）

**做什么**：为 C 端用户提供个性化饮食决策与体验。具体包括：点餐界面、推荐展示与标签展示、轻量状态输入、反馈入口、个人饮食洞察面板（趋势/行为/结构/建议）。

**不做什么**：不展示复杂营养分析；不提供医疗判断；不生成底层菜单逻辑；不承担 B 端运营管理职能。

## 三、核心业务链条（Core Business Chain）

```
用户需求识别 → 场景状态解析 → 营养目标锚定 → 九维约束计算
→ 菜单结构生成（P1引擎）→ 标签系统匹配 → 前端推荐呈现（Nufō³）
→ 用户选择/点餐 → 订单传递至执行层（NuBō）
→ 食材原料映射 → 供应链匹配与备货 → 厨房生产排期 → 出品履约
→ 用户反馈采集 → 运营结果数据回流 → 规则迭代更新 → 循环演进
```

## 四、核心模块拆解（Core Module Decomposition）

### 模块 A：需求识别与场景解析模块

**模块职责**：识别用户当前的用餐需求与所处场景状态，生成结构化的需求描述，作为下游营养目标锚定的输入。

| 字段 | 内容 |
| :--- | :--- |
| **输入数据 (Input)** | 用户角色类型、年龄段、典型用餐节律；当前场景状态（普通工作日/值班/恢复期/陪护期）；用餐时段（早/午/晚/加餐）；目标与需求偏好（轻负担/控糖/高蛋白等） |
| **处理规则 (Logic)** | IF 场景状态 = "恢复期" AND 角色 = "术后患者" THEN 激活"恢复支持"功能标签；IF 时段 = "早餐" AND 偏好 = "高蛋白" THEN 推荐权重向蛋白质类菜品倾斜 |
| **输出数据 (Output)** | 结构化需求描述对象（用户ID + 场景标签 + 目标标签 + 时段标签） |
| **当前状态** | 待建立：用户画像数据结构、场景状态枚举表 |

### 模块 B：营养目标锚定模块（NuStā 知识引擎驱动）

**模块职责**：基于结构化需求描述，从 NuStā 健康稳态知识体系中检索匹配的营养规则，输出当次用餐的营养目标参数。

| 字段 | 内容 |
| :--- | :--- |
| **输入数据 (Input)** | 模块 A 输出的结构化需求描述对象；NuStā 营养规则库（热量范围、三大宏量营养素比例、功能性营养素建议） |
| **处理规则 (Logic)** | 基于用户目标标签，从规则库中检索对应的营养参数范围；若存在多个目标标签冲突（如"高蛋白"与"低热量"），按优先级规则取交集 |
| **输出数据 (Output)** | 营养目标参数对象（热量范围 kcal、蛋白质克数范围、碳水范围、脂肪范围、特殊营养素标记） |
| **当前状态** | 待建立：NuStā 营养规则库（第一阶段最小集合：控糖友好、高蛋白、轻负担、稳能量四类规则） |

### 模块 C：P1 菜单生成引擎模块（九维约束计算）

**模块职责**：基于营养目标参数，综合九维约束条件，从菜品库中筛选并组合生成符合条件的菜单结构。这是整个系统的核心计算模块。

| 字段 | 内容 |
| :--- | :--- |
| **输入数据 (Input)** | 模块 B 输出的营养目标参数；菜品库（含各菜品的营养数据、口味标签、成本数据、出品难度标记）；场景配置参数（当前场景的九维权重配置） |
| **处理规则 (Logic)** | 九维约束引擎并行计算：① 用户接受度维度（好吃/好选/低心理阻力）② 口味聚合维度（高频偏好/区域习惯）③ 爆品潜力维度（点选率/复购率/可复制性）④ 场景适配维度（医院/企业/外送）⑤ 运营协同维度（前后端衔接/排产逻辑）⑥ 实施落地维度（操作复杂度/培训成本）⑦ 成本效率维度（食材成本/损耗率/出餐效率）⑧ 健康友好维度（结构均衡/功能适配）⑨ 反馈迭代维度（历史反馈数据权重）；综合评分排序，输出 Top-N 菜单组合 |
| **输出数据 (Output)** | 菜单组合列表（菜品ID + 营养数据 + 标签 + 组合评分 + 推荐理由） |
| **当前状态** | 待建立：菜品库基础数据结构、九维权重配置表（第一阶段先实现简化版：营养友好 + 口味接受度 + 成本效率三维） |

### 模块 D：标签系统模块

**模块职责**：为菜品、用户、场景打标签，支撑推荐逻辑与数据分析。标签是连接用户需求与菜品供给的语义桥梁。

| 字段 | 内容 |
| :--- | :--- |
| **输入数据 (Input)** | 菜品营养数据、用户行为数据、场景配置数据 |
| **处理规则 (Logic)** | 菜品标签：基于营养数据自动打标（如热量 < 400kcal → "轻负担"）+ 人工审核；用户标签：基于历史行为数据动态生成；场景标签：基于场景配置静态定义 |
| **输出数据 (Output)** | 结构化标签对象（标签ID + 标签类型 + 标签值 + 置信度） |
| **当前状态** | 待建立：标签体系定义文档（第一阶段最小集合：10-15个核心菜品标签） |

### 模块 E：前端推荐呈现模块（Nufō³）

**模块职责**：将菜单组合列表以低认知成本的方式呈现给 C 端用户，降低选择摩擦，引导有效点餐行为。

| 字段 | 内容 |
| :--- | :--- |
| **输入数据 (Input)** | 模块 C 输出的菜单组合列表；用户历史偏好数据；当前场景标签 |
| **处理规则 (Logic)** | 首屏展示高评分组合；标签以简洁图标形式展示（不展示复杂营养数值）；提供"今日推荐"与"自由选择"两种模式 |
| **输出数据 (Output)** | 用户界面渲染数据（菜品展示列表 + 推荐标签 + 组合建议） |
| **当前状态** | 待升级：现有雏形界面需重构以支持标签展示与洞察面板 |

### 模块 F：订单与执行传递模块（NuBō）

**模块职责**：将用户点餐行为转化为可执行的生产订单，传递至厨房执行体系，并协同运营流程。

| 字段 | 内容 |
| :--- | :--- |
| **输入数据 (Input)** | 用户点餐数据（菜品ID + 数量 + 时段）；菜品原料清单；当日备货数据 |
| **处理规则 (Logic)** | 订单聚合：按时段汇总同类菜品订单，生成生产排期；库存预警：IF 某菜品累计订单 > 备货量 × 0.8 THEN 触发备货预警；替换规则：IF 某原料缺货 THEN 按预设替换规则自动推荐替代菜品 |
| **输出数据 (Output)** | 生产排期单（菜品 + 数量 + 出餐时间）；库存预警通知；替换建议列表 |
| **当前状态** | 待升级：现有订单模块需增加与菜品库的原料映射关联 |

### 模块 G：供应链匹配模块（Nexsply 接口）

**模块职责**：基于菜单生成结果与生产排期，向供应链（Nexsply）发出精准的原料需求，实现需求预测与供给匹配。

| 字段 | 内容 |
| :--- | :--- |
| **输入数据 (Input)** | 菜单组合列表（含各菜品原料清单）；历史消耗数据；备货周期参数 |
| **处理规则 (Logic)** | 原料需求汇总：基于菜单生成结果，计算未来 N 天的原料需求量；供应商匹配：优先从 Nexsply 认证供应商列表中匹配；约束校验：IF 某原料无法稳定供应 THEN 触发菜单替换建议，反馈至模块 C |
| **输出数据 (Output)** | 原料采购需求单（原料ID + 数量 + 交货时间）；供应链约束反馈（不可用原料列表） |
| **当前状态** | 待建立：Nexsply 数据接口规范、原料库基础数据结构 |

### 模块 H：反馈采集与规则迭代模块

**模块职责**：采集用户行为数据与运营结果数据，生成结构化结果，驱动规则迭代。这是系统长期护城河的来源。

| 字段 | 内容 |
| :--- | :--- |
| **输入数据 (Input)** | 用户点选行为、复购行为、满意度反馈、放弃原因；运营数据（出餐量、损耗率、投诉率、爆品表现） |
| **处理规则 (Logic)** | 数据路径：原始数据 → 指标 → 趋势 → 报告 → 决策 → 规则迭代；爆品识别：IF 某菜品复购率 > 阈值 AND 满意度 > 阈值 THEN 标记为"爆品候选"；规则更新触发：IF 某标签菜品持续低点选 THEN 触发标签规则复审 |
| **输出数据 (Output)** | 结构化运营报告；爆品候选列表；规则更新建议（待人工审核后生效） |
| **当前状态** | 待重构：现有数据看板需从"纯交易数据展示"升级为"结构化结果生成机制" |

## 五、多场景可配置架构逻辑（Multi-Scene Configuration）

系统通过"后端统一、前端分化"的原则支持多场景部署，核心差异体现在**场景配置参数**上。

| 配置维度 | 医院场景 | 企业团餐场景 | 外部送餐场景 |
| :--- | :--- | :--- | :--- |
| **九维权重重点** | 健康友好维度↑、运营协同维度↑ | 爆品潜力维度↑、成本效率维度↑ | 用户接受度维度↑、实施落地维度↑ |
| **前端界面重点** | 功能标签、恢复支持提示、管理秩序 | 爆品推荐、性价比标签、高频组合 | 标准化组合、快速选择、配送时效 |
| **订单组织方式** | 病区/楼层集中订单 | 部门集中订单 | 个人独立订单 |
| **结算逻辑** | 机构统一结算 | 企业补贴+个人自付 | 个人支付 |
| **菜单更新频率** | 按周更新（稳定性优先） | 按日更新（新鲜感优先） | 按日更新（爆品优先） |

**配置接口**：运营人员可在 NuBō 的"场景配置"模块中，通过可视化界面调整上述参数，无需修改底层代码。

## 六、升级 vs 重构模块识别（Upgrade vs Refactor）

基于对现有雏形系统（NuBō/Nufō³）的分析，识别各模块的改造策略。

| 模块 | 所属系统 | 改造策略 | 核心原因 |
| :--- | :--- | :--- | :--- |
| 用户注册/登录/基础信息管理 | Nufō³ | **升级（Upgrade）** | 基础逻辑可复用，需扩展用户画像字段 |
| 基础订单与支付链路 | NuBō/Nufō³ | **升级（Upgrade）** | 交易链路可复用，需增加场景状态关联字段 |
| 菜品库基础数据（名称/图片/描述） | NuBō | **升级（Upgrade）** | 基础数据可复用，需扩展营养数据字段与标签字段 |
| 基础数据看板（交易数据） | NuBō | **升级（Upgrade）** | 基础框架可复用，需扩展为结构化结果生成机制 |
| **菜单生成逻辑** | NuBō | **重构（Refactor）** | 现有"人工排菜"逻辑无法支撑九维约束引擎，必须重构 |
| **推荐系统** | Nufō³ | **重构（Refactor）** | 现有"热销推荐"无法支撑用户画像+场景状态驱动的动态推荐 |
| **前端交互界面** | Nufō³ | **重构（Refactor）** | 需支持标签展示、个人饮食洞察面板、轻量状态输入 |
| **标签系统** | 全系统 | **新建（New Build）** | 现有系统无标签体系，需从零建立 |
| **供应链匹配接口** | NuBō | **新建（New Build）** | 现有系统无 Nexsply 数据接口，需从零建立 |
| **营养规则库（NuStā）** | Nex₂U中枢 | **新建（New Build）** | 现有系统无结构化营养规则库，需从零建立 |

## 七、关键依赖与假设（Dependencies & Assumptions）

本模型成立的前提条件如下：

1. **营养规则库假设**：假设 NuStā 健康稳态知识体系的第一阶段最小集合（控糖友好、高蛋白、轻负担、稳能量四类规则）可在 Step 4 前完成结构化定义。
2. **菜品库假设**：假设现有菜品的营养数据（热量、蛋白质、碳水、脂肪）可通过人工录入或第三方数据库补全。
3. **供应链接口假设**：假设 Nexsply 可提供结构化的原料库数据（原料ID、供应商、价格、可用性），支持接口对接。
4. **场景配置假设**：第一阶段以医院场景为唯一验证场景，其他场景配置参数在 MVP 跑通后再扩展。

## 八、潜在阻塞点与风险（Blockers & Risks）

| 阻塞点 | 风险等级 | 应对策略 |
| :--- | :--- | :--- |
| 营养规则库缺失，无法驱动模块 B | **高** | Step 4 优先建立最小集合（4类规则），人工审核后上线 |

| 营养规则与供应链现实脱节（SAP 已识别） | **中** | 每周进行一次"规则-供给"对齐会议，及时更新约束条件 |

## 九、第一阶段最小闭环（MVP Definition）

基于以上分析，第一阶段 MVP 的最小系统实现集合如下：

1. **菜单引擎（简化版）**：实现三维约束（营养友好 + 口味接受度 + 成本效率），支持医院场景。
2. **标签系统（基础版）**：10-15 个核心菜品标签，支持前端展示与基础推荐。
3. **用户点餐系统（简版）**：支持点餐、查看推荐标签、提交反馈。
4. **运营管理后台（NuBō）**：支持菜单管理、菜品库维护、基础数据看板。
5. **数据采集与基础报表**：采集点选行为、满意度反馈，生成周报。
6. **爆品识别（初级）**：基于点选率和复购率，人工标记爆品候选。
7. **反馈机制**：用户端简单评分 + 运营端异常记录。
8. **用户洞察面板（简版）**：展示本周常选菜品、口味倾向、轻提示。

**MVP 成功标准**：用户愿意选、前线愿意做、管理方愿意推、数据能沉淀、规则能迭代、能向更多场景复制外溢。
