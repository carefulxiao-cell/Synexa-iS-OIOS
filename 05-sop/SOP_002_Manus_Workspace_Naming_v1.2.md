# SOP_002_Manus_Workspace_Naming_v1.2

> **版本**：v1.2
> **生效日期**：2026-04-16
> **维护主体**：iS-Core（智核中枢）
> **定位**：定义超智体系在 Manus 平台上的工作空间（Workspace）与对话框（Session）的命名规范与管理机制。
> **核心消歧规则**：主题对话组前缀使用**英文缩写**，项目内部功能角色前缀使用**全中文**，两者在视觉上天然区分，杜绝歧义。

---

## 1. 机制概述

Synexa iS 体系在 Manus 平台上采用两层命名结构管理所有对话框。两层逻辑相互独立，分别服务于不同的查看场景：

- **第一层（主题组视角）**：让「所有任务」列表按主题板块一目了然，快速定位属于哪个大的治理板块。
- **第二层（项目内部视角）**：进入具体项目/系统后，清晰区分不同的工作分工职责。

---

## 2. 消歧核心规则

> **主题对话组前缀 → 英文缩写（如 Core、SCO、PCS）**
> **项目内部功能角色前缀 → 全中文（如 中枢、策略、执行框、审查框）**

这条规则是命名体系的基础。`SCO` 出现时，必然指主题组；`策略` 出现时，必然指项目内部的策略角色。两者不再混淆。

---

## 3. 命名规范 (Naming Convention)

### 3.1 第一层：主题对话组 (Theme Group)

标识该对话框属于哪个大的治理主题板块。

**命名公式**：`[英文主题前缀] - [具体内容描述]`

| 英文主题前缀 | 对应治理层级 | 含义 |
| :--- | :--- | :--- |
| `Core` | 智核中枢 | 全局基线治理、跨项目裁决、状态同步 |
| `SCO` | 策略中心 | 战略推演、需求定义、架构设计 |
| `PCS` | 项目控制系统 | 具体项目的执行、开发、交付管理 |
| `Matrix` | 智核矩阵 | 知识沉淀、SOP 制定、培训 |

**示例**：
- `Core - 超级项管·NexFlow`：在 Core 主题组中，关于 NexFlow 项目的全局裁决对话框。
- `Core - 动态功能基线·FBR`：在 Core 主题组中，关于 FBR 机制的专项治理对话框。
- `SCO - 超级项管·NexFlow`：在 SCO 主题组中，关于 NexFlow 项目的战略推演对话框。

### 3.2 第二层：项目/系统内部分工 (Project/System Sub-Session)

在某个具体项目/系统的内部，区分不同的工作职责分工。

**命名公式**：`[中文功能角色] - [项目/系统代号]`

| 中文功能角色 | 对应英文概念 | 含义 |
| :--- | :--- | :--- |
| `中枢` | Core | 该项目/系统内部的总控管理对话框 |
| `策略` | SCO | 该项目/系统内部的策略推演对话框 |
| `执行框` | Execution | 该项目/系统内部的具体开发执行对话框 |
| `审查框` | Review | 该项目/系统内部的 FBR 审查核验对话框 |

**示例**：
- `中枢 - 超级项管·NexFlow`：NexFlow 项目内部，负责总控管理的对话框。
- `策略 - 超级项管·NexFlow`：NexFlow 项目内部，负责策略推演的对话框。
- `执行框 - 超级项管·NexFlow`：NexFlow 项目内部，负责具体执行的对话框。
- `审查框 - 超级项管·iS-NexFlow`：NexFlow 项目内部，负责 FBR 审查的对话框。

## 5. 管理机制与跨平台对齐

### 5.1 目录映射（三平台 SSOT）

```
Manus 文件夹（Folder）
  ↕ 映射
GitHub 03-projects/[ProjectCode]/
  ↕ 映射
GPT Project
```

### 5.2 列表视图优化

通过「英文主题前缀 vs 中文功能角色」的视觉区分，在 Manus「所有任务」列表中：
- 看到英文前缀（`Core`、`SCO`、`PCS`）→ 立即识别为主题组归属。
- 看到中文前缀（`中枢`、`策略`、`执行框`、`审查框`）→ 立即识别为某项目内部的分工角色。
