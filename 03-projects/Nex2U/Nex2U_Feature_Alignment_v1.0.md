## 一、前端（Nufō³）功能对齐

### F-01｜场景分类逻辑

**当前状态**：六大类分组是视觉分类，场景选择触发静态菜品列表展示，不是引擎计算。

**用户反馈**：无法根据每个用户的身体状态、当日目标做完全个性化定制——那样生产和服务跟不上，过于理想。

**对齐结论**：采用"场景驱动的规则筛选"模式，而非"用户驱动的个性化生成"模式。

**具体方案**：

场景选择触发的不是"为你定制"，而是"为这个场景筛选符合规则的菜品组合"。逻辑如下：

1. 用户选择主题场景（如 T07 日常均衡）
2. 系统从菜品库中，按照该场景的营养结构点规则（蛋白/碳水/脂肪/蔬菜纤维比例范围）筛选符合条件的菜品
3. 在符合条件的菜品中，按照母型结构（主食+蛋白+蔬菜+汤）组合推荐套餐
4. 用户可以在推荐结果内自由替换单品，但替换时系统会提示"替换后营养结构偏离程度"

这个方案的核心优势：**规则是固定的，内容是灵活的**。生产端不需要为每个用户单独备餐，因为推荐的是同一个场景下符合规则的菜品池，厨房按菜品备餐即可。

**风险控制**：
- 短期（MVP阶段）：场景筛选规则由运营人员在后台手动配置，系统执行筛选逻辑
- 中期：引入引擎自动计算，运营人员只需审核结果
- 长期：引擎主导，人工审核异常情况

### F-02｜用户身份体系

**当前状态**：只有姓名和余额，用户对系统匿名。

**用户反馈**：可以积累用户数据，给概况提醒。但不能走到细致的、完全针对化的个性化推荐。有些数据可以前端显示，但更多应在后台沉淀。

**对齐结论**：建立"轻量级用户档案 + 数据后台沉淀"的两层结构。

**前端显示（用户可见）**：
- 基础信息：姓名、用餐身份（员工/患者/访客）
- 饮食禁忌：过敏原标注（花生/海鲜/乳制品/麸质等，多选）
- 餐食偏好：口味偏好（清淡/均衡/重口）、忌口（无猪肉/无牛肉等）
- 消费记录：本月消费金额、本周用餐次数

**后台沉淀（运营可见，用户不可见）**：
- 用餐频次与时段分布
- 最常选择的主题场景
- 营养摄入趋势（按周/月汇总）
- 复购率与偏好菜品排行
- 过敏原与禁忌的统计分布（用于菜品结构优化）

**实现优先级**：
- P0（MVP必须）：饮食禁忌标注（影响菜品筛选安全性）
- P1（第二阶段）：餐食偏好、消费记录前端展示
- P2（第三阶段）：后台数据看板的用户维度分析

### F-03｜营养汇总与目标对比

**当前状态**：购物车显示热量/蛋白质/碳水/脂肪/膳食纤维/GI指数，是计算后展示，但没有目标对比。

**用户反馈**：应该有目标对比，怎么样的方案有较高的可执行性。

**对齐结论**：采用"当餐目标对比"而非"全天目标追踪"，可执行性最高。

**具体方案**：

"全天目标追踪"需要用户记录一天所有饮食，依赖度高、用户负担重，不适合饭堂场景。

"当餐目标对比"的逻辑更简单：每个主题场景本身就定义了该餐的营养目标范围（如 T07 日常均衡：热量 500-650kcal，蛋白质 25-35g）。用户在购物车里看到的不只是"这餐有多少营养"，而是"这餐的营养是否在这个场景的合理范围内"。

**前端展示形式**：
- 购物车底部显示当前场景的营养目标区间
- 用进度条或颜色标注当前选择是否在目标区间内（绿色=达标，黄色=偏低，红色=超标）
- 不强制，只提示，用户自主决策

**实现优先级**：P1（第二阶段，依赖场景营养目标数据的建立）

### F-04｜搜索功能

**当前状态**：/search 路由 404，搜索功能缺失。

**用户反馈**：搜索可以增加，但怎么搜索会比较科学？

**对齐结论**：三层搜索逻辑，从简单到智能逐步实现。

**第一层（MVP，文本匹配）**：
- 按菜品名称搜索
- 按食材搜索（如"鸡肉""豆腐"）
- 搜索结果显示菜品卡片，可直接加入购物车

**第二层（第二阶段，标签筛选）**：
- 按营养标签筛选（高蛋白/低脂/低GI/高纤维）
- 按适用场景筛选（28个主题场景）
- 按饮食禁忌过滤（自动排除用户标注的过敏原）

**第三层（第三阶段，语义搜索）**：
- 用户输入"想吃清淡一点的"，系统理解意图并推荐
- 依赖 AI 接入，暂不在 MVP 范围内

**实现优先级**：P0（MVP必须，第一层）

### F-05｜周期预订的营养规划

**当前状态**：预订功能只是"提前选菜"，没有营养均衡规划逻辑。

**用户反馈**：这个功能怎么可以风险最低实现？

**对齐结论**：采用"被动展示"而非"主动规划"，风险最低。

**具体方案**：

主动规划（系统帮你安排一周饮食）需要复杂的算法和用户高度配合，风险高。

被动展示的逻辑：用户自己选好7天的预订后，系统在预订确认页面展示"本周营养汇总"——7天的热量/蛋白质/碳水/脂肪分布图，让用户自己判断是否均衡，自主调整。

**前端展示形式**：
- 预订确认页底部增加"本周营养概览"折叠面板
- 用柱状图展示7天的热量和三大营养素分布
- 标注哪天偏高/偏低，但不强制修改
- 可选：显示"本周场景分布"（早餐选了几次均衡早餐、几次高蛋白早餐）

**实现优先级**：P2（第三阶段，依赖营养数据的完整性）

## 二、后台（NuBō）功能对齐

### B-01｜营养结构点管理模块

**当前状态**：完全缺失。营养数据附属在菜品上，不是从结构点出发组合菜品。

**用户反馈**：看看怎么尽快完善，并且反向测试推演验证完对应的结构文件，然后应该怎么融合到一起？

**对齐结论**：这是整个系统的核心模块，必须优先建立，其他所有模块都依赖它。

**完整思路与路径**：

**第一步：定义营养结构点数据模型（Day 1-2）**

营养结构点的数据结构如下：

```
营养结构点（NutritionPoint）
├── 编码（如 P01、C03、V02）
├── 分类（蛋白/碳水/脂肪/蔬菜纤维/控制约束/质构）
├── 名称（如"优质动物蛋白"）
├── 功能描述（如"提供完整氨基酸，支持组织修复"）
├── 目标摄入量范围（每餐，如蛋白质 25-35g）
├── 适用场景（推荐主题场景列表）
├── 禁用场景（禁止出现的主题场景列表）
├── 硬性约束（必须满足的条件，如"肾病患者禁用高蛋白点"）
└── 关联食材标签（哪些食材可以提供这个营养点）
```

**第二步：在后台建立营养结构点管理界面（Day 3-5）**

后台新增"营养结构点库"模块，支持：
- 查看全部90个营养点的列表（按六大分类分组）
- 编辑每个营养点的参数（目标量范围、约束规则、适用场景）
- 为每个营养点关联对应的食材标签

**第三步：将菜品与营养结构点关联（Day 5-7）**

在菜品管理界面，为每道菜品增加"营养结构点标注"字段：
- 该菜品主要提供哪个营养点（主标注，单选）
- 该菜品辅助提供哪些营养点（辅标注，多选）
- 该菜品有哪些约束标签（如"高嘌呤""高钾""高磷"）

**第四步：反向验证（Day 7-8）**

用已有的75+道菜品，对照营养结构点体系进行全量标注，验证：
- 每个营养点是否有足够的菜品覆盖（避免某个营养点只有1道菜）
- 28个主题场景是否都能从菜品库中找到符合规则的组合
- 约束规则是否存在冲突（如某道菜同时被多个场景推荐和禁用）

**第五步：融合进场景生成逻辑（Day 8-10）**

建立场景→营养结构点→菜品的三层映射关系：
- 每个主题场景定义所需的营养结构点组合（如 T07 日常均衡需要 P01+C02+V01+F01）
- 系统根据场景的营养点需求，从菜品库中筛选符合条件的菜品
- 这就是引擎的核心逻辑

### B-02｜AI补全升级为结构化标注

**用户反馈**：这个和上一点是关联的是吗？

**对齐结论**：是的，完全关联。B-01 建立了营养结构点体系后，B-02 就是让 AI 自动完成菜品的结构化标注。

**升级逻辑**：

当前的 AI 补全：输入菜品名称 → AI 返回热量/蛋白质/碳水/脂肪数值

升级后的 AI 结构化标注：输入菜品名称 + 配料 → AI 返回：
1. 营养数值（热量/蛋白质/碳水/脂肪/膳食纤维/GI指数）
2. 主营养结构点标注（从90个营养点中匹配最符合的1个）
3. 辅助营养结构点标注（最多3个）
4. 约束标签（高嘌呤/高钾/高磷/高钠/高糖等，自动识别）
5. 适用场景推荐（从28个主题场景中推荐最适合的3-5个）

这个升级完全依赖 B-01 的营养结构点体系建立完成后才能实现。实现顺序：B-01 → B-02。

### B-03｜健康套餐管理的逻辑倒转

**用户反馈**：完整的思路、路径和重要节点要明晰列出，有序一一实现。

**对齐结论**：三阶段演进，每个阶段有明确的交付物和验证标准。

**第一阶段：人工配置（当前 → MVP）**

运营人员在后台手动为28个主题场景配置推荐菜品组合。系统执行展示逻辑。

验证标准：28个场景都有至少3个推荐套餐，每个套餐包含主食+蛋白+蔬菜+汤的完整结构。

**第二阶段：规则筛选（MVP后 1-2个月）**

建立营养结构点体系后，后台增加"场景规则配置"功能：
- 运营人员为每个场景配置营养结构点规则（而不是直接配置菜品）
- 系统根据规则自动从菜品库筛选符合条件的菜品
- 运营人员审核筛选结果，可手动调整

验证标准：修改一道菜品的营养结构点标注后，相关场景的推荐菜品自动更新。

**第三阶段：引擎生成（第二阶段稳定后）**

引擎根据场景规则、菜品库、当日库存、用户禁忌，动态生成最优套餐推荐。运营人员只需审核异常情况。

验证标准：在不修改任何配置的情况下，新上架的菜品能够自动出现在符合其营养结构点的场景推荐中。

### B-04｜运营看板数据维度扩展

**用户反馈**：整理出周全、细致的明晰描述，以便开发推进。

**对齐结论**：将看板从"财务视角"扩展为"健康餐食运营视角"，增加三个维度。

**现有维度（保留）**：
- 今日营收、本周/月营收趋势
- 菜品销量排行榜
- 数据导出（营收/销量）

**新增维度一：场景维度**
- 今日/本周最受欢迎的主题场景 Top5
- 各场景的订单量分布（饼图）
- 场景覆盖率：28个场景中有多少个在本周被用户选择过
- 场景与时段的交叉分析（哪个时段哪个场景最热门）

**新增维度二：营养维度**
- 今日/本周用户平均营养摄入概况（热量/蛋白质/碳水/脂肪的均值）
- 各营养指标的分布区间（多少用户在合理范围内）
- 最常被选择的营养结构点组合
- 营养结构点覆盖率（哪些营养点的菜品被频繁选择，哪些被忽略）

**新增维度三：用户维度**
- 活跃用户数（今日/本周/本月）
- 复购率（本周用餐2次以上的用户占比）
- 新用户 vs 老用户占比
- 用餐身份分布（员工/患者/访客）

**实现优先级**：
- P1（第二阶段）：场景维度
- P2（第三阶段）：营养维度、用户维度

### B-05｜身份码管理的泛化

**用户反馈**：这个怎么理解？明晰说说。

**对齐结论**：这是一个"配置驱动"的功能泛化，让同一套代码支持不同场景的身份标识需求。

**详细说明**：

当前系统的"床位码管理"是为医院场景设计的：一张床对应一个二维码，患者扫码后系统知道这是几号床/哪个科室的患者，可以送餐到床。

但系统定位已经调整为"新一代优质饭堂"，饭堂场景的身份标识逻辑不同：

| 场景 | 身份标识 | 对应字段 |
| :--- | :--- | :--- |
| 医院 | 床位号 + 科室 | bed_no + department |
| 企业饭堂 | 工号 + 部门 + 楼层 | employee_id + dept + floor |
| 学校食堂 | 学号 + 班级 | student_id + class |
| 社区食堂 | 桌号 + 区域 | table_no + zone |

**泛化方案**：

将"床位码管理"改为"身份码管理"，在后台系统设置中增加"场景类型"配置：
- 管理员选择当前场景类型（医院/企业/学校/社区）
- 系统根据场景类型自动切换身份码的字段名称和生成规则
- 二维码的生成逻辑、批量导出、扫码绑定功能保持不变，只是字段标签不同

这样做的好处：一套代码，通过配置支持多种场景，未来扩展到新场景时不需要重新开发。

**实现优先级**：P1（第二阶段，MVP阶段先保留医院场景的床位码逻辑，第二阶段泛化）

## 四、三阶段推进路径

### MVP 阶段（第 1-14 天）

**目标**：系统可以真实运营，支付闭环跑通，营养结构点体系建立，场景筛选逻辑上线。

**核心交付物**：
- 营养结构点管理模块（后台）
- 菜品结构化标注（75+道菜品全量标注）
- 场景驱动规则筛选（前端）
- 搜索功能第一层
- 饮食禁忌标注（用户端）
- 支付闭环验证

### 第二阶段（第 15-30 天）

**目标**：系统从"可用"升级为"好用"，数据开始有意义。

**核心交付物**：
- 当餐营养目标对比（前端）
