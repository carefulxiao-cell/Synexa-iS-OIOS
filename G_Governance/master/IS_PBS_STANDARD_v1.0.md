# IS_PBS_STANDARD_v1.0 · 项目基线表标准

版本：v1.0
状态：🟢 活跃
归属：全局治理 · iS-Core 维护
最后更新：2026-06-09
文件性质：本文件为 Synexa iS 体系通用治理标准，定义项目基线表（PBS）的结构规范与填写规则，适用于体系内所有项目类型。

---

## 一、定义与定位

**项目基线表（Project Baseline Sheet，PBS）** 是 Synexa iS 体系中每个项目的最小完整状态描述文件，是项目在体系内存在的「身份证」与「状态快照」。

PBS 不是项目计划书，不是执行方案，也不是进度报告。它的唯一职责是：**在任意时刻，让任何工作空间（含 AI 智能体）能够以最低成本读懂该项目的当前状态、核心资产与关键约束。**

PBS 的设计原则：
- **最小完整**：只包含跨工作空间协同必须知道的内容，不包含执行细节
- **可机读**：结构化字段优先，便于 AI 智能体解析与引用
- **状态驱动**：每次关键决策或状态变化后必须更新，不允许停留在过时状态
- **版本可追溯**：每次更新须更新版本号与更新日期

## 二、PBS 五模块结构（M0–M4）

### M0 · 项目身份（Project Identity）

项目的最小定义层。完成 M0 即完成「项目孵化」动作，可在体系内正式注册。

| 字段 | 说明 | 示例 |
|------|------|------|
| **项目代号** | 英文缩写或 iS-前缀代号，全局唯一 | `iS-NexFlow` |
| **项目全称** | 中文全称，含品牌名（如有） | `NexFlow · 数智协同引擎` |
| **一句话定义** | ≤30 字，说清「这是什么 / 解决什么问题」 | `面向复杂场景的多智能体协同调度引擎` |
| **层级归位** | 体系层级定位（核心引擎 / 场景项目 / 工具 / 实验） | `核心引擎` |
| **优先级** | P0（战略核心）/ P1（活跃推进）/ P2（储备）/ P3（观察） | `P1` |
| **项目状态** | 孵化中 / 推进中 / 暂停 / 封存 | `推进中` |
| **归属工作空间** | 对应的 Manus 对话组代号 | `W03-NexFlow` |
| **创建日期** | YYYY-MM-DD | `2026-03-15` |
| **最后更新** | YYYY-MM-DD | `2026-06-09` |

---

### M1 · 资产库（Asset Repository）

项目当前所有关键文件与资产的索引，含状态标签。

**状态标签体系（三态）**

| 标签 | 含义 | 使用场景 |
|------|------|----------|
| `🟢 活跃` | 当前有效，可直接引用 | 最新版本文件、已验证的方案 |
| `🟡 待更新` | 内容已过时或待修订，引用需注意版本差异 | 架构图待更新、文档待同步 |
| `🔴 封存` | 已废弃，仅作历史参考，不得直接引用 | 旧版本、已推翻的方案 |

**资产库填写格式**

```
| 文件名 | 版本 | 类型 | 状态 | 路径 | 说明 |
```

**填写规则**：
- 每个项目至少包含 PCS（项目宪章）文件
- 架构图、主文档、指令包等关键文件必须登记
- 状态标签必须与实际内容同步更新
- 路径使用相对于仓库根目录的路径

---

### M2 · 项目原则（Project Principles）

3–5 条该项目的核心约束与设计原则，用于在执行层出现分歧时提供裁决依据。

**填写规则**：
- 数量严格限定在 3–5 条，不得超出
- 每条原则须有明确的行为指向，避免空泛表述
- 原则之间不得相互矛盾
- 原则应能回答「当 A 与 B 冲突时，优先 A」这类问题

**示例（iS-NexFlow）**：
1. 先打通核心场景，再考虑通用化扩展
2. 智能体调度逻辑必须可解释，不接受黑盒决策
3. 与 iS-Cortex 的知识接口优先于与外部系统的集成
4. 边缘部署优先于云端集中处理

---

### M3 · 经验积累（Experience Accumulation）

轻量版项目经验记录（轻量 PER），沉淀项目推进过程中的关键判断与教训。

**定位说明**：M3 是 iS-Cortex 异常案例库（E 库）在项目层的前端入口。项目层的经验积累在 M3 沉淀，定期由 iS-Core 提炼后推送至 iS-Cortex 全局库。

**填写格式**

```markdown
### [日期] [事件简述]
- **背景**：触发场景与上下文
- **判断**：当时做出的关键决策
- **结果**：实际结果（含正向与负向）
- **沉淀**：可复用的经验或需要规避的模式
- **置信度**：高 / 中 / 低（基于验证次数与场景覆盖度）
```

**置信度分类**

| 置信度 | 标准 | 引用建议 |
|--------|------|----------|
| **高** | 在 2 个以上场景中验证，结果一致 | 可直接引用，作为默认策略 |
| **中** | 在 1 个场景中验证，或结果有条件依赖 | 引用时需注明适用条件 |
| **低** | 尚未验证，基于推断或单次观察 | 作为假设，需持续验证 |

**方法论锚点**：每个项目可在 M3 末尾标注该项目所依赖的核心方法论来源（如：番医项目经验 / SSADS 框架 / 外部案例），便于跨项目经验迁移时追溯来源。

---

### M4 · 当前状态（Current Status）

项目当前推进状态的快照，是 PBS 中更新最频繁的模块。

| 字段 | 说明 |
|------|------|
| **当前阶段** | 项目所处的推进阶段（对应 Step 编号） |
| **当前 Step** | 具体推进步骤，如 `Step 2A: 核心功能原型` |
| **阻塞项** | 当前阻塞推进的问题（若无则填「无」） |
| **待决策项** | 需要 iS-Core 裁决的事项（若无则填「无」） |
| **下一步行动** | 最近一个可执行动作，含负责方 |
| **目标完成时间** | 当前阶段预计完成时间（若无确定时间则填「待定」） |

**阻塞项分类**

| 类型 | 说明 | 处理路径 |
|------|------|----------|
| `资源阻塞` | 缺少人力、资金或工具 | 上报 iS-Core 资源调度 |
| `决策阻塞` | 需要跨项目裁决或优先级确认 | 触发 iS-Core 裁决流程 |
| `信息阻塞` | 缺少关键信息或外部输入 | 标注信息来源，等待获取 |
| `技术阻塞` | 技术方案未确定或工具限制 | 转至对应技术工作空间 |

## 三、PBS 文件命名规范

```
IS_PBS_[项目代号]_v[版本号].md
```

示例：
- `IS_PBS_NexFlow_v0.1.md`
- `IS_PBS_Nex2U_v1.2.md`
- `IS_PBS_CapabilityAtom_v0.1.md`

**版本号规则**：
- 主版本（x.0）：M0 完成（项目孵化）或重大结构调整
- 次版本（x.y）：M1–M4 任意模块有实质性更新
- 初始版本从 v0.1 开始，M0 完整填写后升至 v1.0

---

## 四、PBS 生命周期与更新触发条件

| 触发事件 | 必须更新的模块 | 更新时限 |
|----------|---------------|----------|
| 项目孵化完成 | M0（完整填写） | 即时 |
| 新文件产出或状态变更 | M1 | 当次对话结束前 |
| 原则发生调整 | M2 | 当次对话结束前 |
| 关键判断或异常事件发生 | M3 | 48 小时内 |
| 阶段推进或阻塞状态变化 | M4 | 即时 |
| 项目暂停或封存 | M0（状态字段）+ M4 | 即时 |

## 五、PBS 与体系其他文件的关系

```
CONTEXT_OS.md（全局状态）
    └── 引用各项目的 M0（项目代号 + 状态 + 优先级）

03-projects/_INDEX.md（项目索引）
    └── 引用各项目的 M0 + M4（状态快照）

IS_PBS_[项目代号].md（项目基线表）
    └── M1 资产库 → 指向各具体文件
    └── M3 经验积累 → 定期推送至 iS-Cortex E 库

PCS（项目宪章）
    └── 与 PBS 互补：PCS 是项目启动时的完整定义，PBS 是持续更新的状态快照
    └── 两者均为 SSOT，不得相互矛盾
```

## 六、Base Token 索引（跨工作空间引用锚点）

每个 PBS 文件在 M0 完成后，自动生成以下 Base Token，供其他工作空间引用：

```
[项目代号]-M0    → 项目身份摘要（代号+定义+状态+优先级）
[项目代号]-M1    → 资产库索引
[项目代号]-M4    → 当前状态快照
```

引用格式：`@PBS:[项目代号]-M[模块编号]`

示例：`@PBS:NexFlow-M4` 表示引用 NexFlow 项目的当前状态快照。
