## 0. 文档定位说明

本文档用于定义 Synexa iS（智核中枢）的整体结构、核心逻辑、项目建构方法与工具配置原则，作为后续所有项目、业务、项目中枢系统与数字员工体系建设的统一基础说明。

本文档目标不是介绍若干 AI 工具，而是建立一套能够长期运转、持续更新、支持多智能体与人类协作者共同调用的组织级认知与执行基础设施。

它承担四个作用：
1. 作为 Synexa iS（智核中枢）的总说明书
2. 作为各 Project Context System（PCS）的上位母架
3. 作为后续项目建构的标准路径依据
4. 作为多智能体、数字员工与知识中枢协同的统一参照

**权威性说明**
本总纲及其所指向的 Context OS，作为 Synexa iS 的唯一真实信息源与必读前置协议，构成所有项目、智能体与协作者接入体系时的统一参照。
> **冲突裁决最高原则**：当多方信息出现冲突时，必须严格遵循第九章 9.7 节的“信息权威裁决顺序（五顺位）”进行判定。

**机器可读优先**
本总纲及所有下属的 PCS、SOP、Skills，必须采用高信息密度的结构化格式（如 Markdown 多级列表、JSON 映射），摒弃人类习惯的冗长叙述，确保 AI 能够瞬间、无歧义地解析。

**项目分层标准**
* G·集团级：集团级基础中枢与战略层项目
* B·业务线级：核心能力引擎 / 核心业务系统
* F·功能模块级：具体项目实例 / 试验场 / 派生模块
该分层用于项目归位与职责划分，不直接等同于业务重要性排序。

**Context OS 定义**
Context OS 在本体系中并非指工程语境中的上下文管理机制，而是指集团级的全局认知操作系统，用于统一承载项目、规则、状态、决策与协同关系的运行基底。

## 第一章：体系总定义

本章用于回答这套体系是什么、为什么存在、要解决什么问题，以及它的整体逻辑是什么。

### 1.1 体系名称

**Synexa iS（智核中枢）**
* 正式结构名：SSADS｜五层协同架构
* 方法总线：7步建构路径
* 执行支持：4组工具集合

SSADS 释义：
* S = SOP
* S = Skills
* A = Agent Matrix
* D = Digital Employee
* S = System Layer

### 1.2 一句话定义

Synexa iS（智核中枢），是一套组织级智能操作系统（OIOS）。它以治理与认知中枢为总控，以 SOP 为方法规则，以 Skills 为能力资产，以 Agent Matrix 为协同编排，以 Digital Employee 为持续执行，并通过 PCS（项目中枢系统）完成项目实例化落地的组织级智能操作架构。

### 1.3 现实问题背景

随着项目增多、信息沉淀加剧、多智能体并行，组织面临的核心瓶颈不再只是效率不足，而是认知基线衰减、对齐成本爆炸、认知漂移与局部最优陷阱。Synexa iS 正是为解决这些问题而建立。

### 1.4 中枢形态定义

该体系的治理与认知中枢并非静态说明文档，而是一个动态、结构化、可持续更新的全局状态机，用于承载组织当前有效的架构、项目、决策与协同状态。这里的“全局状态机”并非技术实现层概念，而是指一个能够持续记录、更新并调度组织当前有效架构、项目状态、关键决策与协同关系的动态认知中枢。

### 1.5 中枢运作边界（治理与认知中枢的职责边界定义）

治理与认知中枢不是执行层，而是**孵化层与裁决层**。其运作边界由以下三条规则严格约束：

**【中枢职责】——中枢只做这四件事**
1. 识别是否需要新项目（判断触发条件）
2. 完成最小定义（Step 0A 级别：项目名称、一句话定义、层级归位、优先级）
3. 做项目归位（G·集团级 / B·业务线级 / F·功能模块级）
4. 确认优先级（与现有活跃项目的关系与排序）

**【中枢停止边界】——完成最小定义后必须停止**
> 一旦完成最小定义，中枢必须立即停止深入讨论，不得在中枢层继续推进该项目的业务细节、执行方案或内容设计。

**【触发动作】——停止即触发**
> 最小定义完成 → 立即创建该项目的 PCS（项目中枢系统）→ 后续所有推进转移至该项目专属对话组进行。

### 1.6 六类 AI 工作空间分类体系

为了支撑中枢与各层级的运作，Synexa iS 体系下共设六类 AI 工作空间，各有明确的职责边界与触发条件：

1. **智核中枢（iS-Core）· 董事会**：基线治理 · 项目孵化与裁决（L1）
2. **智权枢纽（iS-Hub）· 情报室**：智能体资源库 · 内外部 Agent 案例、工具与平台的汇聚与参照（L1 延伸）
3. **枢机经纬（iS-SCO）· 策略室**：推演辅助 · 战略推演与决策支持（L2）
4. **智核矩阵（iS-Matrix）· 研究培训室**：结构化产出引擎 · SOP / 规程 / 模板 / 数字员工指令的生产与固化（L3）
5. **各 PCS 项目（iS-[代号]）· 项目组**：具体项目全生命周期推进（L5）
6. **智核实验场（iS-Lab）· 灵感前测室**：灵感容器 · 未成熟想法的最小验证场（L1 前置）

> **知识生产闭环**：iS-SCO（推演） → iS-Core（裁决） → iS-Matrix（生产 SOP/规程） → iS-[PCS]（执行反馈） → iS-SCO（新一轮推演）。

**三条规则的意义**：防止中枢因承接过多项目细节而失焦，确保中枢始终保持全局视野与治理清明。中枢是所有项目的孵化器，不是任何单一项目的执行场。

---

### 1.6 核心目的

这套体系的建设目的，不是单点提效，而是系统性解决组织在引入 AI 与多项目协同时常见的五类问题：
1. 认知分散
2. 项目失焦
3. 能力浪费
4. 协同低效
5. 规模化后失序

换句话说，这套体系的真正目标，是在项目增多、资料累积、角色扩展、智能体并行后，仍然保持：结构清明、认知统一、信息可交接、执行可持续、质量可复制。

### 1.7 体系核心逻辑

SSADS 的核心逻辑是：
* 以 SOP 固化方法与流程
* 以 Skills 资产化具体能力
* 以 Agent Matrix 组织多角色协同
* 以 Digital Employee 承接持续执行
* 以 Project Context System（PCS） 落实到具体业务战场

因此，它不是若干模块的并列堆叠，而是一套从规则层 → 能力层 → 协同层 → 执行层 → 项目落地层逐层贯通、闭环进化的体系。

### 1.8 总纲 / Context OS / PCS 三者边界表

本表用于明确总纲、Context OS 与 PCS 的角色边界，避免上位原则、全局状态与项目实例三者混线。

## 第二章：SSADS｜五层协同架构

本章用于定义集团智能协同体系的五层基础骨架，以及各层之间的职能分工与运行关系。

### 2.1 架构总述

SSADS 五层协同架构是 Synexa iS 的基础骨架，用于定义组织级智能协同系统的核心组成单元、相互关系及运行机制。

这五层不是五个孤岛，而是同一系统中的五种不同职能：有的负责定规则，有的负责供能力，有的负责编排协同，有的负责长期执行，有的负责落地到真实项目。

它们共同服务于一个目标：让每一个重要项目都能被清晰定义、快速建模、稳定协同、持续运行、长期交接。

### 2.2 五层结构定义

**第一层：L1·治认中枢（治理与认知中枢层）**
负责定义整个体系的：总体战略、系统边界、模块定位、统一命名、权威版本、项目全景、决策记录、AI交接规则。
这一层是整个体系的“总脑”与“总图纸”，它的职责不是参与每一个细节执行，而是确保所有模块都运行在统一坐标系下。

**第二层：L2·知识推演（方法与规则层 / SOP）**
负责将组织经验、作业路径、关键步骤、质量要求与风险控制沉淀为标准流程。
SOP 关注的重点不是“谁来做”，而是：事情应该如何被正确完成、每一步的输入输出是什么、合格标准是什么、常见偏差如何规避。
SOP 是组织经验的结构化沉淀，也是后续 Skills、Agents、Digital Employee 和项目系统运行的流程底板。

**第三层：L3·技能规程（能力资产层 / Skills）**
负责将各种高频、可复用、可组合的能力单元模块化。
例如：信息提炼、战略拆解、研究整理、结构化分析、文档生成、任务推进、质量校对。
Skills 构成的是体系的能力库与工具箱，它们不是流程本身，也不是角色本身，而是被不同流程、角色和项目调用的能力积木。

**第四层：L4·Agent矩阵（角色协同与执行层）**
这一层由两部分组成：
* **4.1 Agent Matrix**：负责定义需要哪些智能角色、各角色职责边界是什么、角色之间如何协同、谁主导/复核/整合/交付。它解决的是复杂任务中的多角色协同问题，本质上偏组织设计与协同编排。
* **4.2 Digital Employee**：负责将相对稳定、长期发生的任务交由具备明确职责边界的数字员工持续承接。它解决的是 AI 从“偶尔帮忙”走向“稳定履职”的问题，本质上偏岗位执行与持续运行。

**第五层：L5·项目执行（项目落地层 / PCS）**
这是最贴近业务现场的一层。每个重点项目都应建立自己的项目中枢系统，用来承载：项目定位、当前项目状态、项目目标、架构说明、文件索引、当前任务、决策记录、连接器与资料源配置、AI工作规则。
Project Context System（PCS）的意义，在于让前四层不再停留在抽象层，而真正进入具体战场。

### 2.3 五层运行关系

**自上而下**
* 治理与认知中枢定义总体原则和边界
* SOP 将原则转化为标准流程
* Skills 将工作能力模块化
* Agent Matrix 与 Digital Employee 将流程和能力组织成协同与执行力量
* Project Context System（PCS）承接具体项目推进

**自下而上**
* 项目推进产生经验、问题、偏差与优化建议
* 反馈至 Digital Employee 与 Agent Matrix 的职责设计
* 再反馈至 Skills 的优化与扩充
* 再反馈至 SOP 的修订
* 最终由治理与认知中枢更新总体框架和版本标准

因此，SSADS 不是死结构，而是一个闭环进化系统。

## 第三章：7步建构路径

本章用于规定每一个新项目、新业务实例从定义到落地的标准建构路径。

### 3.1 路径定义

7步建构路径，是面向每一个新项目与新业务系统实例的标准建构方法。
它的目标不是让项目“看起来有结构”，而是确保项目从一开始就具备：清晰定义、现实锚点、可建模业务结构、明确协同配置、可持续治理、可验证运行、可复制扩展。

### 3.2 七步总览

**Step 0：启动检查（前置动作）**
先确认项目层级与复用可能。
* 输出物：项目层级归位（L1/L2/L3）、是否有可复用的上一代 PCS 模板、确认是否需要走完整 7 步。

**Step 1：对象定义**
先回答“这到底是什么”。
* 输出物：项目名称、一句话定义、项目本质、服务对象、核心问题、不做什么。

**Step 2：价值锚定**
确认这个项目为什么值得做、为谁创造什么价值、凭什么成立。
* 输出物：核心价值主张、战略意义、商业价值、验证假设（建议调用 EKB 进行期望值计算）、成立条件、主要风险（建议调用 EKB 揭示认知陷阱）。

**Step 3：业务结构建模**
将概念转为结构，将愿景转为链条。
* 输出物：业务链条、核心模块、输入输出、关键节点、依赖关系、主要阻塞点。

**Step 4：协同架构映射**
把该项目接到 SSADS 五层协同架构上。
* 输出物：对应 SOP、所需 Skills、所需 Agent 角色、所需 Digital Employee 岗位、Project Context System（PCS）配置方案。

**Step 5：项目运行基线建设**
为该项目建立最小可运行的认知中枢。
* 输出物：项目章程、项目蓝图、当前任务板、决策日志、文件索引、术语表、AI交接规则。

**Step 6：试运行验证**
不靠想象，而用真实任务跑闭环。
* 输出物：首轮试运行任务、运行记录、问题清单、反馈意见、结构修订建议。
* 试运行通过标准：任务链路可跑通、关键角色分工无明显冲突、信息交接无重大失真、输出质量达到预期底线。

**Step 7：固化与复制**
通过验证后，把经验沉淀为模板与标准件。
* 输出物：可复用 SOP、可复用 Skills、角色模板、Digital Employee 岗位模板、PCS 模板、下一类项目迁移方案。

### 3.3 七步核心口诀

“定义对象，锚定价值，建模业务，映射协同，建设中枢，试运行，后复制。”
这句话建议固定下来，作为所有项目启动时的总路线。

### 3.4 七步与五层的关系

7步建构路径不是替代五层协同架构，而是让五层协同架构进入实战的项目化路径。
关系如下：五层协同架构定义组织级底盘，7步建构路径定义项目级生成方法。
换句话说：**五层是母架，七步是走法。**

## 第四章：4组工具集合

本章用于说明支撑项目建构全过程的四类工具组及其配置原则。4组工具集合不是软件清单，而是围绕项目建构全过程配置的工作支持体系。

### 4.1 工具集合定义

原则是：先按阶段需要定义工具组，再按工具组配置具体工具，避免为了工具而工具，避免一上来追求“大而全”。

### 4.2 四组工具总览

**第一组：定义与建模工具组**
* 服务阶段：Step 1–3
* 作用：澄清对象、锁定边界、结构化业务、建立模型
* 典型输出物：项目定义卡、一句话定位、业务链条图、核心模块图、假设清单、非目标清单
* 典型工具类型：文档类、看板类、数据类、连接器类、自动化类

**第二组：协同设计工具组**
* 服务阶段：Step 4
* 作用：角色设计、分工编排、能力映射、路径衔接
* 典型输出物：Agent Matrix、Skills 映射表、Digital Employee 岗位说明、SOP 路径图、任务协同表

**第三组：中枢治理工具组**
* 服务阶段：Step 5
* 作用：资料组织、状态维护、决策留痕、AI交接、权威版本管理
* 典型输出物：项目章程、项目蓝图、当前任务板、决策日志、文件索引、术语表、版本记录

**第四组：运行反馈工具组**
* 服务阶段：Step 6–7
* 作用：试运行、反馈采集、结构修正、模板沉淀、经验复制
* 典型输出物：试运行报告、反馈清单、问题台账、优化建议、模板包、迁移建议

### 4.3 四组工具的配置原则

* 原则一：最小可运行（先配最小闭环，不追求一开始工具繁复齐全）
* 原则二：工具服从路径（工具必须服务于建构路径，而不是反过来改变路径）
* 原则三：工具服从结构（工具应嵌入五层协同架构中，而不是游离在架构之外）
* 原则四：输出优先于工具（优先定义需要产出什么，再决定用什么工具完成）

## 第五章：三者总关系

—— 五层协同架构 · 7步建构路径 · 4组工具集合

### 5.1 关系总述

三者关系不是并列，而是递进：
* 五层协同架构 解决“底盘是什么”
* 7步建构路径 解决“项目怎么生长出来”
* 4组工具集合 解决“每一步用什么支持完成”

一句话概括：**架构定底盘，路径定走法，工具定支撑。**

### 5.2 关系图

```text

        ↓ 为所有项目提供组织级底盘

4组工具集合
        ↓ 为每一步建构活动提供工作支持
项目中枢系统（Project Context System, PCS）
        ↓ 形成具体项目的可运行中枢
```

### 5.3 三者协同价值

通过这三层结构，组织将逐步从“零散提效”转向“系统复利”：项目启动速度更快、对齐成本更低、新智能体接入更顺、已有经验可沉淀复用、长周期项目不容易失真、多项目并行时仍能保持清晰。

## 第六章：Project Context System（PCS）的统一要求

本章用于规定每一个项目中枢系统的统一定位、最小标配、状态字段与运行要求。

### 6.1 Project Context System（PCS）的定位

Project Context System（PCS），是五层协同架构在具体项目中的实例化承载器。
每一个重点项目，都应拥有自己的项目中枢系统，用来承接：项目定位、当前项目状态、结构说明、文件索引、任务状态、决策历史、连接器配置、AI工作规则。

### 6.2 Project Context System（PCS）最小标配

建议所有重点 PCS 至少具备以下七项：
1. 项目章程
2. 项目蓝图
3. 当前任务板
4. 决策日志
5. 文件索引
6. 术语表
7. AI交接协议

**AI 交接协议标准模板**
每次智能体交接时，必须包含以下字段：
* 当前项目/任务名称
* 上一个智能体/协作者做到了哪一步（断点描述）
* 当前生效的 PCS 版本与 Context OS 版本
* 当前核心任务与阻塞项
* 本次交接的目标与预期输出
* 禁止事项（哪些结论不需要重新验证）

**PCS 最小状态字段**
除固定标配外，每个 PCS 还应至少维护以下状态字段：
1. 当前阶段
2. 当前版本
3. 当前负责人
4. 当前目标
5. 当前核心任务
6. 当前阻塞项
7. 下一里程碑
8. 最近更新时间

标配是“有什么”，状态字段是“现在怎样”。上述状态字段应作为每个 PCS 的最小更新单元，发生关键变化时应同步更新，不得长期滞后于实际项目状态。

### 6.3 PCS 与 SSADS 的关系

PCS 不是独立于总基座之外的项目文档，而是：引用 SOP 作为流程依据、调用 Skills 作为能力支撑、实例化 Agent Matrix 作为协同结构、配置 Digital Employee 作为长期执行单元。因此，它是前四层在项目中的汇聚层。

### 6.4 项目动态状态管理原则

在所有集团级中枢模块中，项目状态矩阵属于更新频率最高、管理价值最高的动态模块，应作为项目全景、优先级、依赖关系与当前任务的首要维护对象。

### 6.5 角色模板索引

角色模板索引用于为不同层级的数字员工与智能角色提供统一分级、职责边界与调用标准。

**一、Digital Employee 分级建议**

* **D1｜执行型数字员工**
  * 定位：负责稳定、重复、边界清晰的基础执行任务。
  * 典型职责：文档整理、状态更新、信息录入、任务跟踪、日常归档。
  * 适用场景：高频重复动作、明确输入输出任务、低复杂度标准流程。

* **D2｜协同型数字员工**
  * 定位：负责跨模块、跨任务的协同支撑与中层执行。
  * 典型职责：任务协同推进、状态汇总、资料整合、SOP 调用与衔接、多角色协作支撑。
  * 适用场景：中等复杂度任务、需要多文档/多环节协同的工作、项目运行支撑。

* **D3｜架构型数字员工**
  * 定位：负责项目级结构搭建、规则翻译、系统映射与中枢维护。
  * 典型职责：项目结构设计、规则引擎翻译、中枢系统配置、关键模块建模、治理与更新建议。
  * 适用场景：高复杂度项目、首次建构型工作、体系级或项目级架构任务。

* **D4｜决策辅助型数字员工（如：知算善衡·EKB）**
  * 定位：负责提供多维方案对比、期望值计算、风险揭示与认知迭代。
  * 典型职责：确认问题性质、启用推演模型（期望值计算、凯利分配、贝叶斯更新）、揭示认知陷阱、输出判断建议。
  * 适用场景：重要事务/业务/项目的分析与选择、高不确定性决策、防止个人感性与盲区。

**二、Agent 分级建议**

* **A1｜单点功能型 Agent**：负责某一具体能力模块，如提炼、归纳、校对、分类。
* **A2｜流程协同型 Agent**：负责在 SOP 路径内承接若干连续环节，并与其他 Agent 协同。
* **A3｜策略编排型 Agent**：负责多 Agent 协同编排、任务统筹、规则映射与输出整合。

A 类角色偏能力与协同单元，D 类角色偏长期履职单元。

**三、使用原则**
* 能用 D1 解决的任务，不默认上升到 D2 或 D3。
* D3 不负责替代所有执行，而负责搭结构、定规则、做翻译。
* A 类角色偏能力协作，D 类角色偏长期履职。
* 同一项目中，优先明确 D 角色，再配置 A 角色。

## 第九章：版本与治理建议

本章用于规定文档版本、权威来源、更新纪律、资产回流与协同约束机制。

### 9.1 版本机制建议

所有关键总文档建议固定标注：文件名、版本号、更新时间、当前状态、权威级别、变更摘要。
**版本状态标注规范**：
每个文档的版本状态应明确标注为以下三种之一：
* `Active`（当前生效）
* `Archived`（已归档，仅供参考，并在文件头部注明“已被 [新版本名称] 取代”）
* `Deprecated`（已废弃，禁止调用）

### 9.2 权威来源原则

所有关键对象应坚持“唯一权威来源”原则：总架构（一个主文档）、项目定位（一个主文档）、当前任务（一个主任务板）、决策记录（一个主日志）、术语定义（一个主词典）。
避免聊天记录替代权威文档。聊天适合生成、推演、讨论，不适合承担最终权威。

### 9.3 更新原则

每当发生以下变化，应触发总文档或项目文档更新：项目定位变化、关键边界变化、阶段目标变化、核心任务变化、关键决策形成、模块关系调整、模板升级。

### 9.4 资产回流原则

项目中形成并经验证的通用规则、术语、字段、接口、模板与协同方法，不应停留在项目级文档中，而应按标准回流至集团级治理与认知中枢，形成可被其他项目调用的公共资产。
以下情况可触发模板升级：连续在两个以上项目中复用有效、能显著降低对齐成本、能显著提升交付稳定性、无明显副作用或冲突。

### 9.5 智能协同四项基本纪律

1. 所有智能体与协作者接入任务前，必须先读取最新权威基线。
2. 所有输出必须与当前生效架构、项目定位和决策一致。
3. 关键变化必须触发更新，而非停留在聊天记录中。
4. 项目中形成的通用规则必须回流至集团级中枢。

### 9.6 禁止事项

* 不得以聊天记录替代权威文档。
* 不得在未更新 Context OS/PCS 的情况下默认旧结论仍有效。
* 不得将项目级规则直接冒充集团级规则。
* 不得在未完成对象定义前直接进入工具配置。

### 9.7 信息权威裁决顺序（五顺位）

当总纲、Context OS、PCS、决策日志、任务讨论记录或不同智能体输出之间出现冲突时，应按以下顺序进行裁决：

* **第一顺位：已生效的集团智能协同体系总纲**
  用于裁决体系级结构、命名、路径、工具组、治理原则等上位规则问题。凡属母架定义、制度边界、统一规范，以总纲为最高依据。
* **第二顺位：Context OS 当前生效版本**
  用于裁决集团当前有效项目状态、优先级、关键决策、全局基线等动态运行问题。凡属集团级运行状态与当前全局安排，以 Context OS 为最高依据。
* **第三顺位：对应项目的 PCS 当前版本**
  用于裁决单一项目的定位、任务、状态、角色配置、文件索引与推进细节。凡属项目实例层的具体运行问题，以该项目当前生效 PCS 为最高依据。
* **第四顺位：已记录的决策日志**
  当存在局部变更、例外处理或阶段性调整，且尚未完全同步至总纲、Context OS 或 PCS 时，以已记录并标明生效状态的决策日志为补充依据。
* **第五顺位：当前任务中的临时讨论结论**
  聊天记录、讨论结论、临时共识与口头判断，仅可作为待确认输入，不得直接替代正式生效文档。除非完成正式更新，否则不得上升为权威依据。

**冲突处理原则**：
1. 上位规则优先于下位实例。
2. 已生效版本优先于未归档讨论。
3. 明确记录优先于口头推断。
4. 若出现跨层冲突且无法直接判定，应先暂停扩展性推演，回到上位文档进行核定与修订。
5. 一切冲突的最终处理结果，都应回写至对应层级的权威文档中，避免重复冲突。

## 第十章：总收束

本章用于对整套体系做最终归纳，并固定其核心表达与命名共识。

### 10.1 总结定义

SSADS｜五层协同架构，是Synexa iS 的组织级底盘；
7步建构路径，是每个项目从定义到落地的标准生成路径；
4组工具集合，是支持这一建构过程的工作支持系统。

三者共同构成：一个可长期运转、持续更新、支持多智能体与人类协作者共同工作的组织级智能操作框架。

### 10.2 最终口诀

你可以把整个体系压缩成这三句话：

```text
五层定底盘，七步定路径，四组定支撑。
架构定秩序，路径定生成，工具定效率。
先有母架，再跑项目，再由项目反哺母架。
```

### 10.3 建议固定命名

建议当前先锁定如下表达：
* 体系总名：Synexa iS（智核中枢） / OIOS（组织级智能操作系统）
