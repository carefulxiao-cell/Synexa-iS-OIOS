状态：🟢 活跃
归属：Layer 4 · 全局治理层
最后更新：2026-06-08

## 1. 核心原则
本规范是 Synexa iS 体系全局文件治理的最高标准。
核心原则：**建档即登记，命名即摘要，定期必查核，历史必入库。**

---

## 2. 命名规则体系
所有新文件必须严格遵循以下命名结构：
`[域前缀]_[内容类型]_[版本].[扩展名]`

### 2.1 域前缀（归属）
| 前缀 | 含义 |
|---|---|
| `IS` | iS 体系全局（跨模块） |
| `CORE` | iS-Core 治理中枢 |
| `MATRIX` | iS-Matrix 能力矩阵 |
| `SCO` | iS-SCO 战略推演 |
| `HUB` | iS-Hub 资源情报 |
| `NEX` | Engine Layer 各引擎通用 |
| `FLOW` | NexFlow 项管引擎 |
| `CHEF` | NexChef 餐食引擎 |
| `LENS` | NexLens 数据引擎 |

### 2.2 内容类型（功能）
| 类型码 | 含义 | 示例 |
|---|---|---|
| `ARCH` | 架构图（图形） | `IS_ARCH_v1.7.png` |
| `ARCH_SRC` | 架构图源文件 | `IS_ARCH_SRC_v1.7.d2` |
| `CONTEXT` | 全局状态账本 | `IS_CONTEXT_v2.1.md` |
| `INDEX` | 索引/目录 | `IS_INDEX_v1.0.md` |
| `PRINCIPLES` | 原则/规范 | `IS_PRINCIPLES_v1.0.md` |
| `SKILL` | 可执行能力模块 | `IS_SKILL_TRIGGER_v1.1.md` |
| `SOP` | 标准作业规程 | `IS_SOP_FILE_GOVERNANCE_v1.1.md` |
| `PCS` | 项目控制单 | `FLOW_PCS_v1.0.md` |
| `ATOMS` | 能力原子定义 | `MATRIX_ATOMS_v1.0.md` |
| `REGISTRY` | 注册表 | `IS_REGISTRY_WORKSPACE_v2.1.md` |
| `TRACKER` | 任务/执行追踪 | `IS_TRACKER_EXECUTION_v1.0.md` |
| `PROTOCOL` | 协议/机制定义 | `IS_PROTOCOL_ITER_v1.0.md` |

### 2.3 版本号
格式为 `vX.Y`：
- `X`：大版本（结构性变更、重写）
- `Y`：小版本（内容增删改）

## 3. 建档规范（三步法）
任何智能体在创建新文件时，必须强制执行以下三步：
1. **按规则命名**：严格使用上述命名规则。
2. **注入元数据头**：文件前三行必须包含版本、状态、归属。
3. **同步登记**：文件写入后，必须立即在 `REPO_INDEX.md` 中新增一行记录。**不登记等于不存在。**

---

## 4. 查核与废弃机制
为防止文件失控与版本混淆，建立三层查核机制：

| 层级 | 频率 | 动作 | 触发方式 |
|---|---|---|---|
| **日常** | 每次建档后 | 更新 REPO_INDEX 一行 | 强制习惯 |
| **周期** | 每月一次 | 扫描 REPO_INDEX，标记废弃文件 | 触发词 `文件审查` |
| **里程碑** | 体系版本升级时 | 全仓库清理，旧版本移入 `99-archive/` | 触发词 `全面审查 iS-Core` |

### 4.1 废弃流程
当新版本文件生成时，旧版本文件必须：
1. 在文件内将状态改为 `⚪️ 废弃`
2. 在 `REPO_INDEX.md` 中将其状态改为 `⚪️ 废弃`
3. 按第 5 节归档标准移入 `99-archive/`，原路径文件删除

---

## 5. 历史文件归档机制

### 5.1 归档目录结构
所有历史文件统一归入仓库根目录下的 `99-archive/`，子目录结构与原目录对应：

```
99-archive/
  00-master/          ← 原 00-master/ 的历史文件
  00-overview/        ← 原 00-overview/ 的历史文件
  01-master-blueprint/
  02-context-os/
  03-projects/
  ...（按需创建，与原目录名一致）
```

### 5.2 归档触发条件

| 触发情形 | 说明 |
|----------|------|
| 新版本文件取代旧版本 | 如 v1.0 → v2.0，旧版本入库 |
| 推演/分析类文档结论已被写入正式文件 | 推演过程文档入库，正式文件为 SSOT |
| 定位或架构发生重大升级，旧版整体失效 | 旧版全体入库 |
| 里程碑审查时发现无人引用的孤立文件 | 经确认后入库 |

### 5.3 归档入库标准流程（四步）

**Step 1：在原文件头注入归档标记**
```
> ⚠️ 已归档 · ARCHIVED
> 归档日期：YYYY-MM-DD
> 归档原因：[被哪个文件/版本取代，或推演过程留存]
> 取代文件：[新版本文件名或 SSOT 文件名]
```

**Step 2：将文件移入 `99-archive/[对应子目录]/`**
原路径文件删除，不留副本。

**Step 3：在 `REPO_INDEX.md` 中更新该文件状态**
将状态标记改为 `🗄️ 已归档`，并在备注栏注明归档路径。

**Step 4：在 `CONTEXT_OS.md` 文件变更记录中补一行**
格式：`YYYY-MM-DD | [文件名] 归档 | 原因：[简述] | 取代文件：[新文件名]`

### 5.4 归档文件管理原则
- 归档文件**只读**，不再更新，不得被任何工作空间引用为 SSOT
- 归档目录本身不设版本，只做历史存档
- 任何智能体在引用文件时，若发现文件状态为 `🗄️ 已归档`，必须停止引用并切换至取代文件

---

**【迁移说明】**：本规范发布前建立的历史文件，暂不强制重命名。在下次该文件发生版本升级时，新版本必须采用本规范命名，旧版本按废弃流程处理。
