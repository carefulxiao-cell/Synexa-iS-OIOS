## 核心认知：动态基线是 AI 协同的唯一前提

在多智能体（Multi-Agent）协同网络中，各个 AI 工作空间本质上是**无状态的（Stateless）**。如果没有一套强制的、可读写的动态基线管理机制，系统将迅速陷入熵增：共识流失、规范漂移、重复造轮子。

**动态基线管理不是系统建设的基础，而是系统存在的唯一前提。**

## 第一维度：智能体协同定位与工作流架构

超智系统基座的协同架构遵循严格的五节点知识生产闭环，每个节点都有明确的职能边界：

| 节点 | 智能体代号 | 职能定位 | 核心输出物 |
| :--- | :--- | :--- | :--- |
| **1. 战略发起** | `iS-SCO` (枢机经纬) | 策略室：战略推演、需求定义、价值锚定 | 战略意图、需求文档 (PRD) |
| **2. 全局裁决** | `iS-Core` (智核中枢) | 董事会：基线治理、项目孵化、跨域调度 | 体系基线、SOP、裁决记录 |
| **3. 结构转化** | `iS-Matrix` (智核矩阵) | 研究室：非结构化知识转化为机器可读规则 | 规程、模板、数字员工指令 |
| **4. 执行交付** | `iS-PCS` (各项目组) | 项目组：具体项目的全生命周期开发与推进 | 代码包、系统产物、TBF 报告 |
| **5. 验证闭环** | `iS-SCO` (枢机经纬) | 策略室：验收产物是否符合初始战略意图 | 验收结论、迭代建议 |

**工作流转路径**：`SCO` (发起) → `Core` (裁决/立项) → `Matrix` (规则化) → `PCS` (执行) → `SCO` (验收)

## 第二维度：动态基线管理体系 (Dynamic Baseline Management)

基线管理必须覆盖从全局到局部的所有层级，确保信息不流失、可追溯、可验证。

### 1. 全局状态基线 (Global Context)
- **载体**：`CONTEXT_OS.md`
- **内容**：体系版本、活跃项目全景、全局决策日志、待同步事项。
- **机制**：任何跨项目的重大变更必须回写至此，作为所有智能体接入的"0号文件"。

### 2. 跨平台同步基线 (ISYNC Protocol)
- **载体**：`06-isync/` 目录下的各工作空间同步日志。
- **内容**：Manus / GPT / GitHub 三端的状态差异与同步记录。
- **机制**：分级指令汇总机制（L1 强制归档 + L2 被动聚合 + L3 事件回写）与双轨制（定期全量 + 机动增量），确保不同平台的 AI 拥有相同的上下文。

### 3. 项目功能基线 (Functional Baseline, FBL)
- **载体**：各项目 `docs/FBL_vX.X.md`
- **内容**：该项目所有历史指令、约束条款、功能预期的汇总快照。
- **机制**：FBR 审查机制的唯一基准。指令积累 → 代码比对 → 验证闭环。

### 4. 任务目标基线 (Task Baseline File, TBF)
- **载体**：各项目 `docs/TBF_vX.X.md`
- **内容**：单次迭代的具体任务清单、非功能性需求 (NFR)、架构约束。
- **机制**：三态门禁（✅通过 / ⚠️待验证 / ❌未通过），强制阻断未完成生产验证的下一阶段推进。

## 第三维度：核心原则与交叉工作架构

系统的运作必须遵循一套严密的咬合机制，确保"既精准又不累赘，接受科学冗余但不过度"。

### 原则一：强制门禁原则 (Gatekeeping Principle)
所有规范不能仅停留在"文档建议"层面，必须转化为流程中的"硬卡点"。
- **例**：执行框提交代码，必须附带生产数据库 `SHOW COLUMNS` 截图，否则 PCS 审查框有权直接拒收（SOP_003）。

### 原则二：唯一事实来源原则 (SSOT - Single Source of Truth)
任何决策、共识、指令，只要未写入 GitHub 中央仓的对应 Markdown 文件，即视为"不存在"。AI 严禁依赖聊天记录作为执行依据。
- **L1 强制归档规则**：每次下发指令包或达成新共识，必须在产生的那一刻立即保存为文件并推送至 GitHub 项目目录。未推送到 GitHub 的指令视为"未生效"。

### 原则三：正反向双重验证机制 (Bi-directional Validation)
- **正向验证**：指令/需求 → 是否在代码和生产环境中被准确实现？
- **反向验证**：代码/产物 → 是否有对应的指令记录和架构授权？（防止执行框私自加戏或架构漂移）

### 原则四：生命周期与版本退役机制 (Lifecycle & Retirement)
基线文件必须有明确的版本号。新版本生效时，旧版本必须明确标记为"已作废"或移入归档目录，防止 AI 错误引用历史约束。

### 原则五：人机协作边界显性化 (Human-AI Boundary)
明确定义哪些决策必须由人（用户）做出，哪些可以由 AI 自主执行，边界模糊会导致 AI 在不该决策的地方决策，或在该决策的地方等待。

| 决策类型 | 责任方 | 说明 |
| :--- | :--- | :--- |
| 体系架构变更、新项目立项 | **人（用户）** | Core 可提案，但必须经用户确认 |
| 跨项目优先级裁决 | **人（用户）** | Core 可建议排序，但用户最终拍板 |
| 文件回写、SOP 执行、指令汇总 | **AI 自主执行** | 无需等待用户确认，执行后告知 |
| 代码提交、技术方案选择 | **AI 自主执行** | 在已有约束范围内自主决策 |
| 超出现有约束的架构变更 | **人（用户）** | AI 必须停止并请示 |

### 原则六：跨平台一致性主动保障 (Cross-Platform Consistency)
Manus / GPT / GitHub 三端的状态同步不能依赖手动记忆，必须有主动的触发机制和可查询的同步日志。
- **载体**：`06-isync/GPT_Sync_Log.md`（双轨制：定期全量 + 机动增量）
- **规则**：每次 Core 完成重大裁决后，必须在 `GPT_Sync_Log.md` 记录变更文件清单，并在回复末尾附加 GPT 同步提醒，直至用户确认。

## 第四维度：指令生命周期标准协议 (Instruction Lifecycle Protocol, ILP)

> **核心问题**：一条指令从产生到失效，在什么阶段、以什么形式、存放在哪里？如果没有标准答案，指令就会在各工作空间之间"悬空"，造成可见性缺失（如 SOP_003 在 NexFlow 工作空间不可见的问题）。

### 1. 指令的五个生命阶段

| 阶段 | 名称 | 定义 | 责任方 | 存放位置 |
| :--- | :--- | :--- | :--- | :--- |
| **P1** | **产生** | 在对话中达成共识、下发指令包、完成裁决 | 任意工作空间 | 聊天记录（临时） |
| **P2** | **归档** | 立即保存为 Markdown 文件并推送至 GitHub | 产生该指令的工作空间 | `L1`：项目 `docs/` 目录 |
| **P3** | **汇总** | 触发 `汇总指令`，将 L1 文件聚合写入工作空间 ISYNC 文件 | 各工作空间 | `L2`：`06-isync/[工作空间]_ISYNC.md` |
| **P4** | **生效** | 指令被目标工作空间读取并纳入执行基线 | 目标工作空间 | 工作空间的 Project Instructions |
| **P5** | **退役** | 新版本生效后，旧指令被标记为 `[已作废]` 并移入归档区 | Core 或产生该指令的工作空间 | `L1` 文件内的归档区 |

**关键规则**：P1（产生）→ P2（归档）之间的时间窗口必须趋近于零。停留在 P1 的指令视为"未生效"。

### 2. 指令的三种类型与归档路径

| 类型 | 定义 | 归档路径 | 示例 |
| :--- | :--- | :--- | :--- |
| **体系级指令** | 影响全局架构、所有工作空间均需遵守 | `00-master/` 或 `05-sop/` | ISYNC 协议、SOP_003、TBF 模板 |
| **项目级指令** | 仅影响特定项目，由该项目工作空间遵守 | `03-projects/[项目代号]/docs/` | NexFlow 指令包、TBF V3.1 |
| **临时裁决** | 单次问题的处理决定，不形成长期约束 | `CONTEXT_OS.md` 决策日志 | 技术债处理决定 |

### 3. 跨工作空间指令可见性规则

> **根因**：SOP_003 在 OIOS 中央仓，但 NexFlow 工作空间只读取 nexflow 项目仓库，导致可见性缺失。

**规则**：所有工作空间在执行任何任务前，必须按以下优先级读取指令来源：

```
优先级 1：carefulxiao-cell/Synexa-iS-OIOS/00-master/     （体系级协议）
优先级 2：carefulxiao-cell/Synexa-iS-OIOS/05-sop/        （体系级 SOP）
优先级 3：carefulxiao-cell/Synexa-iS-OIOS/03-projects/   （项目基线）
优先级 4：carefulxiao-cell/[项目仓库]/docs/               （项目级指令包）
```

当工作空间在项目仓库中找不到某个规范文件时，**必须主动向上查找 OIOS 中央仓**，而不是报告"文件不存在"。

### 4. 指令健康度评估（定期审查触发）

每次触发 `全面审查 [项目代号]` 时，除代码比对外，还需输出该项目的**指令健康度报告**：

| 指标 | 健康标准 | 检查方法 |
| :--- | :--- | :--- |
| 归档完整率 | 所有历史指令包均有对应 Markdown 文件 | 比对聊天记录与 `docs/` 目录 |
| 版本一致性 | 工作空间使用的 SOP/TBF 版本与 OIOS 最新版一致 | 比对版本号 |
| 退役标记完整率 | 所有旧版指令均已标记 `[已作废]` | 检查 `docs/` 目录中的历史文件 |
| 跨仓库可见性 | 工作空间能正确读取 OIOS 中央仓的体系级 SOP | 读取测试 |

## 第五维度：生态级知识联动机制 (Ecological Knowledge Synergy)

> **核心问题**：当某个项目（如 NexFlow）在实践中摸索出了优秀的机制（如 SOP_003 提交规范），如何确保这个经验不被局限在单一项目中，而是能自动反哺全局，并同步给其他所有项目？

超智系统不是单向的"自上而下"发号施令，而是一个**双向流动的生态闭环**。任何局部的成功经验，都必须通过机制转化为全局的共同财富。

### 1. 知识流动的双向闭环

| 阶段 | 动作 | 责任方 | 载体/路径 |
| :--- | :--- | :--- | :--- |
| **1. 局部涌现** | 项目在执行中发现问题，并建立有效的局部规范 | `iS-PCS` (各项目组) | 项目内的 `docs/` 目录 |
| **2. 提炼上报** | 识别局部规范的全局价值，上报 Core 裁决 | `iS-PCS` (各项目组) | 跨工作空间通报文档 |
| **3. 全局升维** | Core 裁决通过，将局部规范升维为全局标准 | `iS-Core` (智核中枢) | 写入 `05-sop/` 或 `00-master/` |
| **4. 结构转化** | 将新标准转化为可执行的机器指令模板 | `iS-Matrix` (智核矩阵) | 更新工作空间指令模板 |
| **5. 全局同步** | 所有项目组读取新标准，纳入各自的执行基线 | `iS-PCS` (所有项目组) | 触发 `跨工作空间指令可见性规则` |

### 2. 联动触发机制

- **主动上报触发**：当 PCS 工作空间在项目中建立了一项新规范，且判断其具有跨项目复用价值时，必须主动生成一份《经验提炼与升维建议书》，并通知 iS-Core。
- **定期收割触发**：iS-Core 在每月的定期审查中，主动扫描各活跃项目的 `docs/` 目录，寻找具有全局价值的隐性知识，提取并升维。

### 3. 知识的"降维打击"

一旦某项经验被升维为全局 SOP（如 SOP_003），它将通过 `跨工作空间指令可见性规则` 瞬间对所有项目生效。这意味着：**一个项目踩过的坑，其他所有项目将自动免疫；一个项目发明的利器，其他所有项目将自动装备。** 这正是超智系统生态联动的终极威力。

## 第六维度：全局18步工作流标准 (Global 18-Step Workflow Standard)

> **核心问题**：超智体系的每一次协作推进，应遵循怎样的完整标准流程？从一个模糊想法到最终全局对齐，每一步的责任方、产出物和进入条件是什么？

全局18步工作流是超智体系所有项目推进的**方法总线**，覆盖从问题识别到全局对齐的完整闭环。18步分为三大阶段：**分析层**（建立共识）、**执行层**（落地交付）、**沉化层**（固化提升）。

---

### 阶段一：分析层（步骤 1–5）

> **目标**：在任何执行动作发生之前，确保各方对问题、目标和路径拥有共同的清晰认知。

| 步骤 | 名称 | 定义 | 责任方 | 核心产出 |
| :---: | :--- | :--- | :--- | :--- |
| **1** | **描述情况** | 完整、客观地陈述当前现状、背景信息与已知约束条件，不加判断，只呈现事实 | 发起方（用户/SCO） | 情况说明文档 |
| **2** | **推演可能** | 基于当前情况，系统推演所有可能的路径、风险与机会，输出多方案对比 | iS-SCO / iS-Core | 推演报告 / 方案对比表 |
| **3** | **目标制定** | 在推演基础上，明确本次推进的具体目标、成功标准（DoD）与优先级排序 | 用户 / iS-Core | 目标定义文档（含 DoD） |
| **4** | **交流互补** | 各角色（用户、SCO、Core、PCS）就目标与路径进行结构化交流，补充遗漏视角，消除盲区 | 所有相关方 | 交流记录 / 补充意见 |
| **5** | **对齐理解** | 确认所有参与方对目标、路径、约束与分工达成一致，形成书面共识 | iS-Core | 共识确认文档 |

---

### 阶段二：执行层（步骤 6–11）

> **目标**：将共识转化为可执行的指令，并通过严格的归档与门禁机制确保执行质量。

| 步骤 | 名称 | 定义 | 责任方 | 核心产出 |
| :---: | :--- | :--- | :--- | :--- |
| **6** | **生成指令** | 基于共识，将目标分解为具体的、可执行的指令包，每条指令须包含：目标、约束、验收标准 | iS-SCO / iS-Core | 指令包（Instruction Package） |
| **7** | **审核指令** | 对指令包进行质量审核：完整性（是否覆盖所有目标）、一致性（是否与体系基线冲突）、可执行性（是否足够具体） | iS-Core | 审核结论（通过/退回修改） |
| **8** | **汇总推进** | 将审核通过的指令包汇总，生成本次迭代的 TBF（任务目标基线文件），确立执行优先级与时序 | iS-Core / iS-SCO | TBF 文件 |
| **9** | **入仓留存** | 将指令包与 TBF 立即推送至 GitHub 中央仓对应目录，完成 L1 强制归档（P1→P2 时间窗口趋近于零） | 产生指令的工作空间 | GitHub commit 记录 |
| **10** | **下发执行** | 将指令包正式下发至执行框（PCS），执行框按 SOP_003 规范启动执行 | iS-SCO / iS-Core | 执行启动确认 |
| **11** | **反查完善** | 执行过程中，执行框发现问题或偏差时，必须主动上报并触发反查：正向验证（指令→实现）+ 反向验证（实现→指令） | iS-PCS | 偏差报告 / 补充指令 |

---

### 阶段三：沉化层（步骤 12–18）

> **目标**：将执行结果固化为体系资产，更新全局状态，并为下一轮循环做好准备。

| 步骤 | 名称 | 定义 | 责任方 | 核心产出 |
| :---: | :--- | :--- | :--- | :--- |
| **12** | **阶段完成** | 执行框完成交付后，按 SOP_003 提交完整的 TBF 回写报告，SCO 完成验收核查，三态门禁全部通过 | iS-PCS / iS-SCO | TBF 回写报告（含验收截图） |
| **13** | **整理汇总** | 对本次迭代的所有产出物（代码、文档、决策记录）进行整理归类，确保目录结构整洁、版本号正确 | 执行框 / iS-SCO | 整理后的文件目录 |
| **14** | **状态审查** | 触发 FBR（功能基线审查）：以 FBL 为基准，扫描代码包，确认指令→实现的完整性与一致性 | iS-SCO / iS-Core | FBR 审查报告 |
| **15** | **跟踪推进** | 识别本次迭代中未完成的事项、新发现的技术债与下一步优先级，更新项目 Backlog | iS-SCO | 更新后的 Backlog / 待办清单 |
| **16** | **整洁清理** | 清理过时文件（标记旧版本为「已作废」）、删除临时文件、关闭已完成的 Issue，保持仓库整洁 | 执行框 / iS-SCO | 清理记录 |
| **17** | **更新通报** | 将本次迭代的关键决策、状态变更与新产出物，回写至 `CONTEXT_OS.md` 决策日志，并触发 GPT 同步提醒 | iS-Core | CONTEXT_OS.md 更新 / GPT 同步提醒 |
| **18** | **全局对齐** | 确认 Manus / GPT / GitHub 三端状态一致，所有相关工作空间已读取最新基线，体系进入下一轮就绪状态 | iS-Core | 全局对齐确认 |

---

### 18步工作流与五节点架构的映射关系

| 工作流阶段 | 覆盖步骤 | 主导节点 | 说明 |
| :--- | :--- | :--- | :--- |
| 分析层 | 步骤 1–5 | SCO → Core | 战略发起与全局裁决共同完成共识建立 |
| 执行层（前半段） | 步骤 6–9 | Core → SCO | 指令生成、审核与归档，确保 SSOT 完整 |
| 执行层（后半段） | 步骤 10–11 | SCO → PCS | 指令下发与执行中的动态反查 |
| 沉化层（前半段） | 步骤 12–14 | PCS → SCO | 交付验收、整理归档与 FBR 审查 |
| 沉化层（后半段） | 步骤 15–18 | SCO → Core | 跟踪推进、清理、全局状态更新与对齐 |

> **关键原则**：18步工作流不是线性的瀑布流程，而是**可嵌套的迭代单元**。每个 PCS 项目的每次版本迭代，都是一次完整的18步循环。步骤可以加速，但不能跳过。

## 结语

超智系统基座不是一个静态的文档库，而是一个**由协议、门禁和触发词构成的动态操作系统**。它的终极目标是：让任何一个新接入的智能体，只需读取基线文件，就能在 5 秒内无缝融入当前的复杂协作网络，且不会犯历史已解决的错误。

**六个维度的关系**：智能体协同定位（谁做什么）→ 动态基线管理（信息如何保存）→ 核心原则（如何保证质量）→ 指令生命周期（信息如何流动）→ 生态知识联动（经验如何升维）→ 全局工作流标准（流程如何标准化）。六者缺一不可，共同构成超智系统的基座。
