> **版本**：v1.0
> **生效日期**：2026-04-16
> **维护主体**：iS-Matrix（智核矩阵）
> **定位**：定义超智体系所有系统级项目的标配机制——功能基线与审查机制（FBR 机制），确保系统迭代过程中的功能稳定性，防止“功能遗忘”、“回归错误”及“AI 幻觉导致的虚假完成”。

---

## 1. 机制概述

**FBR (Functional Baseline & Review) 机制** 是为每个系统建立一个动态功能基线（Functional Baseline），并配合正反向审查测试机制，以确保系统功能的长期可维护性和稳定性。它是 TBF（任务目标基线文件）机制在功能维度的自然延伸和深化。

### 1.1 核心载体：功能列表文件 (FBL)

- **定义**：FBL (Functional Baseline List) 是记录系统所有核心功能模块预期状态与实际审查结果的动态文件。
- **存放位置**：作为每个系统 PCS（项目控制系统）的核心附件，存放在对应项目的 `docs/` 目录下。
- **命名规范**：`[Project_Code]_FBL_v[X.X].md` (例如：`NexFlow_FBL_v3.0.md`)
- **模板参考**：`05-sop/FBL_Template_v1.0.md`

---

## 2. 运行机制：正反向审查测试 (Review & Test Cycle)

### 2.1 正向审查（开发后验证）

- **触发条件**：每次版本迭代或功能模块开发完成（对应 TBF 节点完成时）。
- **执行动作**：开发 Agent（如 iS-NexFlow）必须对照 FBL 中的新增/修改条目进行逐项测试，并将测试结果回写至 FBL。
- **卡点**：未通过正向审查的功能，不得标记为“已完成”。

### 2.2 反向审查（定期/回归测试）

- **触发条件**：定期（如每周/每双周）或进行重大底层重构前。
- **执行动作**：由治理 Agent（如 iS-SCO 或专门的测试 Agent）根据 FBL 进行全量或核心链路的回归测试，确保新代码没有破坏原有功能。
- **卡点**：发现状态异常（🟡）的功能，必须生成修复任务并优先排期。

---

## 3. 标准触发词与执行序列 (SOP)

### 3.1 标准触发词

为了在各工作空间中快速激活审查机制，统一使用以下标准触发词：

**`全面审查 [系统代号]`**

例如：`全面审查 NexFlow`、`全面审查 Nex2U`、`全面审查 Nexsply`

### 3.2 触发后的标准执行序列

当 Agent 收到 `全面审查 [系统代号]` 时，必须按以下顺序执行：

| 步骤 | 动作 | 产出 |
| :--- | :--- | :--- |
| 1 | 读取该系统最新 FBL 文件 | 获取功能基线 |
| 2 | 逐条核查每项功能当前状态（正向：新增/修改项；反向：全量回归） | 功能健康度快照 |
| 3 | 输出「系统状态确认」：健康功能数 / 异常项 / 待开发项 | 可视化状态报告 |
| 4 | 对所有 🟡 异常项，生成修复任务并标注优先级 | 修复任务清单 |
| 5 | 将审查结论回写至 FBL 对应条目的「最后审查记录」字段 | FBL 更新 |

### 3.3 扩展变体（可选标准化）

如需区分审查深度，可进一步约定：

| 指示词 | 含义 |
| :--- | :--- |
| `审查 [系统代号]` | 默认：核心链路快速审查 |
| `全面审查 [系统代号]` | 所有功能条目逐项回归 |
| `审查 [系统代号] [模块名称]` | 指定模块审查（例如：`审查 NexFlow 文件中心`） |

---

*注：本 SOP 适用于超智体系下所有系统级项目，各项目组在初始化时必须基于 FBL 模板建立首版功能基线。*
